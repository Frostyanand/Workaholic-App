# 1. Purpose

This document defines the business rules that govern Workaholic behavior.

Business rules describe what the system MUST do, MUST NOT do, or MAY do when specific domain conditions occur.

These rules are independent of:

- UI implementation
- database technology
- API framework
- client platform
- external provider implementation

A UI, API, background job, synchronization process, or local client MUST NOT violate these rules.

---

# 2. Rule Language

The following terms are normative:

- **MUST**: mandatory behavior.
- **MUST NOT**: prohibited behavior.
- **SHOULD**: recommended behavior unless a documented exception exists.
- **SHOULD NOT**: discouraged behavior unless explicitly justified.
- **MAY**: optional behavior.

Rules are identified using stable IDs.

---

# 3. Identity and Ownership Rules

## BR-ID-001: Native Identity

Every persistent Workaholic domain entity MUST have a stable native identifier.

---

## BR-ID-002: External Identity Separation

External provider identifiers MUST NOT replace native Workaholic identifiers.

A Google Calendar event, for example, MUST retain its Google identifier separately from its Workaholic identifier.

---

## BR-ID-003: Authentication vs Authorization

Successful authentication MUST NOT automatically imply authorization to access every resource.

Resource access MUST be evaluated against ownership, workspace membership, role, permissions, and applicable sharing relationships.

---

## BR-ID-004: Resource Isolation

A user MUST NOT access resources belonging to another workspace or user unless an explicit authorization relationship permits access.

---

## BR-ID-005: Workspace Membership

Workspace access MUST be mediated through membership.

Removing a user's membership MUST remove the permissions granted solely through that membership.

---

# 4. Task Rules

## BR-TASK-001: Task Independence

A Task is actionable work and MUST remain conceptually distinct from a Calendar Event.

---

## BR-TASK-002: Optional Project

A Task MAY exist without belonging to a Project.

---

## BR-TASK-003: Optional Board

A Task MAY exist without belonging to a Board.

---

## BR-TASK-004: Parent Task

A Task MAY have a parent Task.

A Task MUST NOT directly or indirectly become its own ancestor.

Circular task hierarchies are prohibited.

---

## BR-TASK-005: Parent Completion

Completing every child Task MUST NOT automatically complete the parent Task.

Parent completion is an explicit state transition.

---

## BR-TASK-006: Parent Deletion

Deleting a parent Task MUST NOT silently cause irreversible deletion of all descendants unless an explicit user action and documented deletion policy permits it.

---

## BR-TASK-007: Overdue State

A Task becomes overdue when its applicable due date/time has passed while the Task remains incomplete.

---

## BR-TASK-008: Completion and Due Date

Completing a Task does not automatically modify or remove its due date.

Historical due-date information SHOULD remain available.

---

## BR-TASK-009: Reopening

A completed Task MAY be reopened.

Reopening MUST restore an incomplete state without silently changing unrelated properties.

---

## BR-TASK-010: Priority Independence

Changing Task priority MUST NOT automatically change Task status.

Changing Task status MUST NOT automatically change priority unless an explicit configurable workflow rule exists.

---

# 5. Task Dependency Rules

## BR-DEP-001: Dependency Distinction

A dependency is not equivalent to a parent/subtask relationship.

---

## BR-DEP-002: Circular Dependencies

A dependency graph MUST NOT contain prohibited circular dependency chains.

Example:

```text
A blocks B
B blocks C
C blocks A
````

This MUST be rejected.

---

## BR-DEP-003: Dependency Does Not Automatically Block Editing

A blocked Task MAY still be edited.

Dependency relationships describe logical workflow constraints rather than database-level immutability.

---

## BR-DEP-004: Dependency Completion

Completing a prerequisite Task does not automatically complete the dependent Task.

---

# 6. Board Rules

## BR-BOARD-001: Board Column Ownership

A Board Column MUST belong to a specific Board.

---

## BR-BOARD-002: Board Task Association

A Task associated with a Board MUST reference a valid Board context.

---

## BR-BOARD-003: Column Movement

Moving a Task between Board Columns MAY change its workflow status according to the Board's configured mapping.

The exact status-mapping implementation MUST remain deterministic.

---

## BR-BOARD-004: Bulk Operations

Bulk actions MUST apply only to resources for which the acting user has authorization.

A partially authorized bulk operation MUST NOT silently modify unauthorized resources.

---

# 7. Project Rules

## BR-PROJECT-001: Project Independence

Deleting or archiving a Project MUST NOT automatically delete Tasks unless an explicit destructive action is requested.

---

## BR-PROJECT-002: Project Completion

A Project's completion state is independent from individual Task completion states.

---

## BR-PROJECT-003: Project Resources

Notes, files, Tasks, Boards, and Events associated with a Project MUST retain their own identities and lifecycle.

---

# 8. Calendar Rules

## BR-CAL-001: Event Identity

Every Calendar Event MUST have a stable native identity when represented as a Workaholic-native object.

---

## BR-CAL-002: Event Time Validity

A timed Event MUST have a valid start and end relationship.

The end MUST NOT precede the start.

---

## BR-CAL-003: Timezone

Events with timezone-sensitive times MUST preserve sufficient timezone information to interpret their intended local time correctly.

---

## BR-CAL-004: All-Day Events

An all-day Event MUST be distinguishable from a timed Event.

---

## BR-CAL-005: Calendar Source

Every calendar event requiring provenance MUST identify its source.

---

## BR-CAL-006: Source-Specific Operations

Operations targeting one Calendar Source MUST NOT modify unrelated sources.

Example:

```text
End Semester
    ↓
DAY_ORDER generated events
    ↓
Remove/invalidate applicable future events
```

It MUST NOT remove:

```text
Personal events
Google events
Birthdays
Unrelated bookings
```

---

# 9. Task Scheduling Rules

## BR-SCHED-001: Task vs Work Block

A Task's due date is not equivalent to its Scheduled Work Block.

---

## BR-SCHED-002: Multiple Work Blocks

A Task MAY have multiple Scheduled Work Blocks.

---

## BR-SCHED-003: Work Block Association

A Scheduled Work Block MUST reference the Task it represents work for.

---

## BR-SCHED-004: Calendar Representation

A Scheduled Work Block MAY be represented in the calendar while remaining conceptually distinct from the underlying Task.

---

## BR-SCHED-005: Overlapping Work

The system SHOULD identify conflicting Scheduled Work Blocks where the user's configured scheduling rules require conflict detection.

---

# 10. Academic Scheduling Rules

## BR-DO-001: Day Order Is Sequence-Based

Day Order assignment MUST be calculated from the academic working-day sequence rather than from a simple weekday calculation.

---

## BR-DO-002: Weekend Handling

Saturday and Sunday MUST NOT normally advance the Day Order sequence.

---

## BR-DO-003: Special Working Days

An explicitly configured special working Saturday, Sunday, or other non-standard date MAY advance the Day Order sequence.

---

## BR-DO-004: Holiday Handling

An academic holiday MUST NOT consume a Day Order unless explicitly configured to do so.

---

## BR-DO-005: Holiday Shift

When a holiday is inserted into the academic calendar, subsequent Day Order assignments MUST shift according to the resulting working-day sequence.

Example:

```text
Before:

Mon → DO 1
Tue → DO 2
Wed → DO 3
Thu → DO 4

Holiday added on Wednesday:

Mon → DO 1
Tue → DO 2
Wed → Holiday
Thu → DO 3
Fri → DO 4
```

---

## BR-DO-006: Schedule Recalculation

Changes to the academic calendar that affect working-day status MUST trigger recalculation of affected Day Order assignments and generated academic schedule occurrences.

---

## BR-DO-007: Reusable Schedule

A Class Schedule definition MUST remain reusable independently of generated calendar occurrences.

---

## BR-DO-008: Generated Event Provenance

Every generated Day Order class event MUST retain enough provenance to determine:

* semester
* Day Order
* schedule
* schedule entry
* generation source

---

## BR-DO-009: Semester Boundary

A generated academic occurrence MUST be associated with the Semester that generated it.

---

## BR-DO-010: End Semester

Ending a Semester MUST prevent that Semester's future generated academic schedule occurrences from continuing to appear as active future schedule occurrences.

---

## BR-DO-011: Historical Preservation

Ending a Semester MUST NOT destroy historical academic schedule information.

Past generated occurrences SHOULD remain available as history where required.

---

## BR-DO-012: Reusable Mapping Preservation

Ending a Semester MUST NOT delete the reusable Day Order/Class Schedule mapping.

---

## BR-DO-013: Unrelated Calendar Preservation

Ending a Semester MUST NOT delete or modify unrelated calendar events.

---

## BR-DO-014: Cancellation

A cancelled class MUST be distinguishable from a normal holiday.

---

## BR-DO-015: Rescheduling

A rescheduled class MUST preserve sufficient information to distinguish the original schedule from the replacement occurrence.

---

## BR-DO-016: Special Working Day

A special working day MUST be explicitly represented in the academic calendar.

It MUST NOT be inferred solely from the fact that a calendar date falls on a weekend.

---

# 11. Recurrence Rules

## BR-REC-001: Series Identity

A recurring object MUST have a conceptual series identity separate from individual occurrences.

---

## BR-REC-002: Occurrence Independence

An individual occurrence MAY be modified or cancelled without necessarily changing the entire recurring series.

---

## BR-REC-003: Recurrence Expansion

The system MUST be able to determine whether a requested occurrence belongs to a recurring series.

---

## BR-REC-004: Recurrence Boundary

A recurrence series MUST respect its configured start/end conditions.

---

# 12. Reminder Rules

## BR-REM-001: Reminder Independence

A Reminder is independent from the object that triggers it.

Deleting or changing the associated object MUST cause the Reminder to be re-evaluated according to explicit lifecycle rules.

---

## BR-REM-002: Multiple Reminders

A Task or Event MAY have multiple Reminders.

Example:

```text
Task deadline: 20:00

Reminder 1: 24 hours before
Reminder 2: 1 hour before
Reminder 3: exact time
```

---

## BR-REM-003: Exact-Time Reminder

An exact-time Reminder MUST trigger according to its configured timezone interpretation.

---

## BR-REM-004: Relative Reminder

A relative Reminder MUST calculate its trigger time from the relevant source Event, Task, Booking, or other supported object.

---

## BR-REM-005: Snooze

Snoozing a Reminder MUST change the recipient's next notification timing without altering the underlying Task/Event unless explicitly intended.

---

## BR-REM-006: Recipient Independence

When a Reminder has multiple recipients, one recipient snoozing or dismissing it MUST NOT snooze or dismiss it for other recipients.

Example:

```text
Owner       → snoozed until 21:00
Parent      → dismissed
Phone       → still eligible for delivery
```

Recipient state is independent.

---

## BR-REM-007: Shared Reminder Authorization

A Reminder MUST NOT be sent to another person unless the recipient is explicitly authorized to receive it.

---

## BR-REM-008: Alarm-Level Delivery

Alarm-level reminders SHOULD use the strongest appropriate supported local notification mechanism on each platform.

---

# 13. Notification Rules

## BR-NOTIF-001: Notification Is Delivery State

A Notification represents an alert generated for a recipient/channel/device.

It is not the same as the underlying Reminder.

---

## BR-NOTIF-002: Delivery Independence

Delivery failure on one device/channel MUST NOT imply delivery success on another device/channel.

---

## BR-NOTIF-003: Device Availability

A push token becoming invalid MUST NOT invalidate the underlying Reminder.

---

## BR-NOTIF-004: Local Reminder Reliability

The client MUST be capable of maintaining scheduled local reminders required for supported offline behavior.

---

# 14. Note Rules

## BR-NOTE-001: Notes Are Not Tasks

A Note checklist item MUST NOT automatically create a Task.

---

## BR-NOTE-002: Explicit Conversion

A checklist item MAY be explicitly converted into a Task.

Such conversion MUST be an intentional operation.

---

## BR-NOTE-003: Note Relationships

Deleting a relationship between a Note and another object MUST NOT delete the Note or the related object.

---

# 15. Attachment and Drive Rules

## BR-FILE-001: Attachment Relationship

An Attachment represents the relationship between Workaholic and a file.

---

## BR-FILE-002: External File Independence

A Google Drive file MUST remain independent of its Workaholic Attachment relationship.

---

## BR-FILE-003: Remove Attachment

Removing an attachment from Workaholic MUST NOT automatically delete the corresponding Google Drive file.

---

## BR-FILE-004: Explicit Drive Deletion

Deletion of the external Drive file MUST require an explicit operation with appropriate authorization.

---

## BR-FILE-005: External File Ownership

Workaholic MUST NOT assume that every externally linked file is owned by the current Workaholic user.

Permissions and provider ownership MUST be respected.

---

# 16. Google Calendar Rules

## BR-GCAL-001: Two-Way Synchronization

Where two-way synchronization is enabled, supported Google Calendar changes MUST be capable of propagating to Workaholic and supported Workaholic changes MUST be capable of propagating to Google.

---

## BR-GCAL-002: Native Identity Preservation

A Google Calendar Event MUST retain its external Google identifier independently of its Workaholic identity.

---

## BR-GCAL-003: External Deletion

If a synchronized Google event is deleted externally, Workaholic MUST detect the deletion and update its local representation according to synchronization policy.

---

## BR-GCAL-004: Conflict Detection

Concurrent changes from Workaholic and Google MUST be handled according to explicit conflict rules.

A silent last-write-wins assumption MUST NOT be introduced without being specified.

---

## BR-GCAL-005: Disconnecting Google

Disconnecting the Google integration MUST NOT delete native Workaholic objects.

---

# 17. Google Tasks Rules

## BR-GTASK-001: External Mapping

Google Tasks objects MUST retain separate external identifiers.

---

## BR-GTASK-002: Two-Way Synchronization

Where enabled, changes MUST be synchronized according to the synchronization specification.

---

## BR-GTASK-003: Native Extensions

Workaholic-specific task properties that Google Tasks cannot represent MUST remain native Workaholic data.

They MUST NOT be discarded merely because the object is synchronized.

---

# 18. Public Calendar Rules

## BR-PUBCAL-001: Public Link Is Not Account Access

A public calendar link MUST NOT grant access to the user's authenticated Workaholic account.

---

## BR-PUBCAL-002: Private Event Privacy

A private Event exposed through a public calendar MUST reveal only the permitted busy/availability representation.

Example:

```text
Private Event:
"Doctor Appointment"

Public view:
"Busy"
```

---

## BR-PUBCAL-003: Public Event Data

Public events MAY expose configured public information such as:

* title
* start time
* end time

Private metadata MUST NOT be exposed.

---

## BR-PUBCAL-004: Revocation

A public calendar link MUST be revocable.

---

## BR-PUBCAL-005: Regeneration

A revoked public link MAY be replaced by a newly generated link.

The old link MUST cease functioning according to the revocation model.

---

## BR-PUBCAL-006: Search Indexing

Public calendar links SHOULD NOT be search-engine indexed unless the owner explicitly enables indexing.

---

# 19. Booking Rules

## BR-BOOK-001: Guest Account

A guest MUST be able to book through a public booking page without creating a Workaholic account.

---

## BR-BOOK-002: Availability

A booking slot MUST be offered only when the slot satisfies the applicable availability and booking rules.

---

## BR-BOOK-003: Calendar Conflicts

Existing calendar busy periods MUST be considered when determining availability.

---

## BR-BOOK-004: Private Event Privacy

A booking system MUST use the existence of a private event to determine availability without exposing the private event's details to the guest.

---

## BR-BOOK-005: Duration

A Booking MUST respect the configured Booking Type duration.

---

## BR-BOOK-006: Buffer

Configured pre-booking and post-booking buffers MUST be included when determining slot availability.

---

## BR-BOOK-007: Minimum Notice

A Booking MUST NOT be accepted earlier than the configured minimum notice period.

---

## BR-BOOK-008: Maximum Horizon

A Booking MUST NOT be accepted beyond the configured maximum booking horizon.

---

## BR-BOOK-009: Cancellation Deadline

A Booking cancellation MUST respect the configured cancellation deadline.

---

## BR-BOOK-010: Double Booking Prevention

Two mutually exclusive bookings MUST NOT be confirmed for the same unavailable time range.

This rule MUST be enforced atomically at the authoritative data layer.

Client-side availability checks alone are insufficient.

---

## BR-BOOK-011: Booking Confirmation

A booking is not considered confirmed merely because a client displayed an available slot.

Confirmation requires successful authoritative persistence.

---

# 20. Trusted Sharing Rules

## BR-SHARE-001: Explicit Trust

A user MUST explicitly establish a Trusted Relationship before protected resources may be shared through that relationship.

---

## BR-SHARE-002: Share Code

A share code is an onboarding mechanism and MUST NOT function as a permanent password.

---

## BR-SHARE-003: Account Association

Where authenticated trusted access is required, the trusted person MUST be associated with their own authenticated Workaholic identity.

---

## BR-SHARE-004: Granular Permissions

Trusted access MUST support permissions narrower than unrestricted account access.

---

## BR-SHARE-005: Revocation

The owner MUST be able to revoke a Trusted Relationship.

---

## BR-SHARE-006: Session Revocation

Revoking trusted access MUST be capable of invalidating applicable active sessions/devices.

---

## BR-SHARE-007: Shared Reminder Recipients

Trusted users MUST NOT automatically receive every reminder.

Reminder sharing requires explicit recipient association.

---

# 21. Device and Session Rules

## BR-DEVICE-001: Device Registration

A client installation MUST be associated with a user before it can participate in authenticated synchronization.

---

## BR-DEVICE-002: Session Expiration

Sessions MUST respect their configured lifetime.

---

## BR-DEVICE-003: Session Revocation

A user with appropriate authorization MUST be able to revoke an individual session.

---

## BR-DEVICE-004: Global Revocation

Where supported, a user MUST be able to revoke all applicable sessions.

---

## BR-DEVICE-005: Persistent Trusted Device

A trusted personal device MAY remain associated with the user's account according to the device trust policy.

---

# 22. Offline Rules

## BR-OFF-001: Local Availability

Supported clients MUST maintain sufficient local state to perform supported offline operations.

---

## BR-OFF-002: Local Mutation

A user action performed offline MUST be persisted locally before being considered successfully accepted by the local client.

---

## BR-OFF-003: Synchronization Queue

Offline mutations MUST be retained until successfully synchronized or explicitly resolved as failed/conflicted.

---

## BR-OFF-004: No Silent Loss

Temporary loss of network connectivity MUST NOT silently discard accepted local mutations.

---

## BR-OFF-005: Reconnection

When connectivity returns, queued mutations MUST be synchronized according to synchronization rules.

---

## BR-OFF-006: Conflict

A conflict MUST NOT silently overwrite meaningful concurrent user changes without following the defined conflict-resolution policy.

---

# 23. Data Lifecycle Rules

## BR-DATA-001: Soft Deletion

Important domain resources SHOULD support recoverable deletion where practical.

---

## BR-DATA-002: Trash

Trashed resources MUST NOT normally appear as active resources.

---

## BR-DATA-003: Recovery

Recoverable resources MAY be restored if they remain within their retention period and dependency constraints permit restoration.

---

## BR-DATA-004: Permanent Deletion

Permanent deletion MUST be an explicit operation.

---

## BR-DATA-005: Historical Data

Historical information required for audit, synchronization, or user-visible history MUST NOT be destroyed merely because an active relationship was removed.

---

# 24. Collaboration Rules

## BR-COLLAB-001: Authorization

Every collaborative operation MUST be authorized against the relevant workspace/resource permissions.

---

## BR-COLLAB-002: Assignment

A Task MUST NOT be assigned to a user who is not authorized to participate in the relevant workspace/resource context.

---

## BR-COLLAB-003: Comments

Users MUST have appropriate access to the parent resource before they can add comments to it.

---

## BR-COLLAB-004: Activity

Meaningful state changes SHOULD produce activity records where activity tracking is enabled.

---

## BR-COLLAB-005: Mentions

A mention MUST resolve to an authorized/known participant where the collaboration model requires identity resolution.

---

# 25. Search Rules

## BR-SEARCH-001: Source of Truth

Search indexes MUST NOT become authoritative sources of domain state.

---

## BR-SEARCH-002: Authorization

Search results MUST respect the same authorization rules as direct resource access.

A user MUST NOT discover an object through search that they could not access directly.

---

## BR-SEARCH-003: Deleted Objects

Deleted or inaccessible resources MUST NOT continue appearing as active search results.

---

# 26. Integration Credential Rules

## BR-SEC-001: Secret Storage

OAuth client secrets, refresh credentials, encryption keys, database credentials, and equivalent secrets MUST remain server-side.

---

## BR-SEC-002: Client Exposure

Sensitive integration credentials MUST NOT be embedded in client applications.

---

## BR-SEC-003: Scope

External integrations SHOULD request only the permissions required for their supported functionality.

---

## BR-SEC-004: Disconnect

Disconnecting an external integration MUST invalidate or retire its applicable authorization state without destroying native data.

---

# 27. Authorization Rules

## BR-AUTHZ-001: Server Enforcement

Authorization MUST be enforced server-side.

Client-side UI restrictions alone are insufficient.

---

## BR-AUTHZ-002: Resource-Level Authorization

Authorization MUST be evaluated at the resource level where required.

Being a workspace member does not automatically grant every possible operation on every resource.

---

## BR-AUTHZ-003: Least Privilege

Users and integrations SHOULD receive only the permissions required for their intended operations.

---

# 28. AI Future-Extension Rules

AI functionality is a future subsystem.

When implemented:

## BR-AI-001: Controlled Actions

AI MUST interact with the application through controlled application actions/tools.

---

## BR-AI-002: No Direct Database Manipulation

An AI model MUST NOT directly manipulate the database.

---

## BR-AI-003: Authorization

AI-triggered actions MUST execute under explicit user authorization and the same permission model as equivalent human actions.

---

## BR-AI-004: Validation

AI-generated actions MUST be validated by application-level business rules before execution.

---

# 29. Chat Future-Extension Rules

Chat is a future subsystem.

When implemented:

* messages MUST belong to conversations
* conversation membership MUST determine access
* attachments MUST follow existing file authorization rules
* mentions MUST follow collaboration rules
* deleted/revoked users MUST not retain unauthorized access

Chat MUST NOT bypass the existing workspace and authorization model.

---

# 30. Cross-Platform Consistency

## BR-PLAT-001: Shared Domain Semantics

The same domain operation MUST have equivalent business meaning on:

* Web
* Windows
* Android
* future supported platforms

---

## BR-PLAT-002: Client Differences

Platform-specific implementation MAY differ.

Business semantics MUST NOT differ merely because an operation originated on a different platform.

---

# 31. Failure and Retry Rules

## BR-FAIL-001: Retry Safety

Operations that may be retried MUST be designed to avoid unintended duplicate effects.

---

## BR-FAIL-002: Idempotency

Operations such as synchronization, booking confirmation, and external integration actions MUST use idempotency mechanisms where duplicate execution could cause incorrect state.

---

## BR-FAIL-003: Partial Failure

A failure in one subsystem MUST NOT silently roll back unrelated successfully committed domain operations unless an explicit transaction boundary requires it.

---

# 32. Audit Rules

## BR-AUDIT-001: Security-Sensitive Actions

Security-sensitive operations SHOULD be auditable.

Examples:

* permission changes
* member removal
* trusted access revocation
* session termination
* integration connection
* integration disconnection
* public link regeneration

---

## BR-AUDIT-002: Historical Integrity

Audit records SHOULD remain immutable after creation except through explicitly defined retention/deletion mechanisms.

---

# 33. Critical Invariants

The following invariants are considered especially important.

```text
1. Native IDs and external IDs are separate.

2. Authentication does not equal authorization.

3. Tasks and Events are separate domain concepts.

4. Task deadlines and scheduled work blocks are separate concepts.

5. Reminders and notifications are separate concepts.

6. Parent/subtask relationships are separate from dependencies.

7. Day Order is calculated from academic working-day sequence.

8. Holidays shift subsequent Day Orders when applicable.

9. Semester termination affects future generated academic occurrences,
   not reusable schedule definitions or unrelated calendar data.

10. External Drive files are not deleted merely because an attachment
    relationship is removed.

11. Public calendar access exposes only permitted information.

12. Booking availability checks alone cannot prevent double booking.
    Authoritative atomic enforcement is required.

13. Shared reminder recipient state is independent per recipient.

14. Offline accepted mutations must not be silently lost.

15. Search never becomes a source of truth.

16. Client-side authorization is never sufficient.

17. External integration credentials remain server-side.

18. AI, when introduced, operates through controlled application actions.
```

# 34. Rule Change Policy

A change to a business rule MAY affect:

* database constraints
* API behavior
* synchronization
* background jobs
* UI behavior
* notifications
* tests
* existing user data

Therefore changes to this document MUST be evaluated for downstream impact.

Any material rule change SHOULD:

1. identify affected requirements
2. identify affected domain entities
3. identify affected technical components
4. update affected tests
5. document migration implications
6. update relevant specifications
