# `NOTIFICATION-SPECIFICATION.md`

**Status:** FINAL
**Version:** 1.0
**Product:** Workaholic
**Scope:** Reminders, notifications, delivery, snoozing, shared reminders, alarms, and notification lifecycle

---

## 1. Purpose

The Workaholic Notification subsystem is responsible for informing users about events, tasks, reminders, bookings, collaboration activity, synchronization state, and other actionable changes.

The subsystem MUST distinguish between:

```text
Reminder
= a scheduled instruction to notify someone

Notification
= a delivered informational/actionable message

Delivery
= one attempt to deliver a notification through a channel
```

A reminder is therefore an **intent to notify**, while a notification is the resulting communication.

---

# 2. Authority Model

The Notification subsystem does not own the underlying domain object.

For example:

```text
Task
  ↓
Reminder
  ↓
Notification
```

The task remains authoritative for task state.

Similarly:

```text
Calendar Event
  ↓
Reminder
  ↓
Notification
```

The event remains authoritative for event state.

This prevents notification records from becoming a second, conflicting source of truth.

---

# 3. Notification Sources

Notifications MAY originate from:

```text

REMINDER
BOOKING
COLLABORATION
COMMENT
MENTION
TRUSTED_RELATIONSHIP
SYNC
SYSTEM
ACADEMIC_SCHEDULE
```

The source MUST be identifiable.

# 4. Notification Channels

Initial supported channels:

```text
IN_APP
PUSH
WINDOWS_DESKTOP
ANDROID_LOCAL
```

Future channels MAY include:

```text
EMAIL
SMS
WEB_PUSH
OTHER
```

The channel implementation MUST remain separate from notification generation.

---

# 5. Notification Delivery Architecture

Conceptually:

```text
Domain Event
     ↓
Notification Decision
     ↓
Notification
     ↓
Delivery Attempts
     ↓
Channel
     ↓
User
```

For example:

```text
Meeting starts in 15 minutes
        ↓
Reminder triggered
        ↓
Notification created
        ↓
Push delivery
        ↓
Windows popup
```

A single notification MAY have multiple delivery attempts/channels.

---

# 6. Reminder Model

A Reminder contains:

* Source object
* Trigger definition
* Recipient(s)
* Priority
* Enabled/disabled state
* Delivery preferences
* Snooze state where applicable
* Lifecycle metadata

Examples:

```text
Reminder:
15 minutes before meeting
```

```text
Reminder:
September 10 at 20:00
Task: Submit assignment
```

```text
Reminder:
Every Monday at 09:00
```

---

# 7. Reminder Trigger Types

Initial trigger types SHOULD include:

```text
ABSOLUTE_TIME
BEFORE_EVENT
BEFORE_DEADLINE
RECURRING_TIME
```

Future trigger types MAY include:

```text
AFTER_EVENT
LOCATION
CONDITION
SMART
```

Condition-based and intelligent triggers remain deferred.

---

# 8. Absolute-Time Reminder

An absolute reminder triggers at a specific timestamp.

Example:

```text
September 10
20:00
```

The reminder MUST respect its configured timezone semantics.

---

# 9. Event-Relative Reminder

An event-relative reminder is calculated from an event.

Example:

```text
Event:
Meeting at 15:00

Reminder:
15 minutes before
```

Trigger:

```text
14:45
```

If the event moves to 16:00, the reminder MUST move with it.

---

# 10. Deadline-Relative Reminder

A task deadline MAY have reminders.

Example:

```text
Deadline:
September 10, 23:59

Reminder:
1 day before
```

Trigger:

```text
September 9, 23:59
```

Changing the deadline MUST recalculate the reminder trigger.

---

# 11. Recurring Reminders

Recurring reminders MAY trigger repeatedly.

Example:

```text
Every weekday
09:00
```

The recurrence model MUST respect timezone and daylight-saving semantics where applicable.

---

# 12. Reminder Priority

Reminder priority SHOULD support:

```text
LOW
NORMAL
HIGH
CRITICAL
```

Priority affects delivery behavior, not the underlying task/event priority.

A high-priority reminder does not automatically make its task high priority.

---

# 13. Alarm-Level Reminders

Critical reminders MAY use an alarm-style delivery.

Examples:

* Exam
* Important deadline
* Critical personal reminder
* High-importance appointment

Alarm-level delivery MAY:

* Play sound
* Display a prominent notification
* Appear above normal notifications
* Remain visible until acknowledged
* Use platform-supported alarm behavior

Platform limitations MUST be respected.

---

# 14. Notification Lifecycle

A notification SHOULD follow:

```text
CREATED
   ↓
PENDING
   ↓
DELIVERED
   ↓
READ / ACKNOWLEDGED
```

Delivery failures MAY produce:

```text
RETRYING
FAILED
```

Notifications MUST NOT be considered successfully delivered merely because they were generated.

---

# 15. Notification State

The system SHOULD distinguish:

```text
UNREAD
READ
DISMISSED
```

These states are user-specific.

If a notification is sent to multiple users, one user's read state MUST NOT change another user's state.

---

# 16. Notification Delivery

A notification MAY have multiple delivery records.

Example:

```text
Notification
├── In-App Delivery
├── Android Push
└── Windows Desktop
```

Each delivery MUST track its own state.

Conceptually:

```text
PENDING
SENT
DELIVERED
FAILED
RETRYABLE
```

The exact provider-specific status mapping belongs to implementation.

---

# 17. Delivery Failure

Temporary failures SHOULD be retried.

Examples:

* Network outage
* Temporary push-provider failure
* Device unavailable
* Backend transient failure

Permanent failures MUST NOT retry indefinitely.

---

# 18. Retry Policy

Retry behavior SHOULD use bounded retry attempts with increasing delay.

The initial system does not require a distributed queue infrastructure.

Managed/background jobs MAY process pending deliveries.

---

# 19. Push Notifications

Push notifications are appropriate when:

* The user is not currently viewing Workaholic
* A reminder becomes due
* A shared event changes
* A booking is confirmed/cancelled
* Important collaboration activity occurs

Push delivery MUST NOT be the sole source of truth.

The notification remains available in-app where appropriate.

---

# 20. Windows Notifications

The Windows application SHOULD support desktop notifications for:

* Due reminders
* Upcoming events
* Important tasks
* Booking updates
* Shared reminders
* Relevant collaboration notifications

The application MAY continue operating in the background/tray to support timely local notifications.

---

# 21. Android Notifications

Android SHOULD support:

* Push notifications
* Local scheduled reminders
* Alarm-level reminders where platform APIs permit
* Notification actions
* Snooze actions
* Open-to-object navigation

Notification permission MUST be requested contextually rather than assumed.

---

# 22. Web Notifications

The Web application MAY use:

* Browser notifications
* Service-worker-supported push
* In-app notifications

Browser permission MUST be explicit.

The system MUST continue functioning when browser notification permission is denied.

---

# 23. In-App Notification Center

Workaholic SHOULD provide a centralized notification center.

It SHOULD support:

```text
All
Unread
Reminders
Tasks
Calendar
Bookings
Collaboration
System
```

Users SHOULD be able to:

* Read
* Mark unread
* Dismiss
* Open source object
* Snooze eligible reminders

---

# 24. Notification Navigation

A notification SHOULD contain enough structured information to navigate to its source.

Example:

```text
Notification
    ↓
Task ID
    ↓
Task detail screen
```

The client MUST still perform authorization checks.

A notification cannot grant access to an otherwise inaccessible resource.

---

# 25. Snoozing

Eligible reminders MUST support snoozing.

Examples:

```text
10 minutes
30 minutes
1 hour
Tomorrow
Custom time
```

The available options MAY vary by reminder type.

---

# 26. Snooze Semantics

Snoozing changes the **next trigger time**.

It MUST NOT modify:

* Task deadline
* Calendar event time
* Event recurrence
* Task priority
* Underlying domain object

Example:

```text
Task deadline:
18:00

Reminder:
17:00

Snooze:
30 minutes

New reminder trigger:
17:30
```

The deadline remains 18:00.

---

# 27. Repeated Snoozing

Users MAY snooze a reminder multiple times unless the reminder policy prohibits it.

The system SHOULD retain sufficient history for debugging/audit purposes.

Repeated snoozing MUST NOT silently move the underlying deadline.

---

# 28. Dismissal

Dismissal means:

> Do not show this currently-triggered reminder again.

Dismissal MUST NOT automatically:

* Complete the task
* Cancel the event
* Delete the reminder
* Delete the booking

For recurring reminders, dismissal of one occurrence MUST NOT necessarily disable future occurrences.

---

# 29. Reminder Completion

For reminders associated with tasks:

```text
Task completed
      ↓
Pending task reminder
      ↓
No longer actionable
```

The system SHOULD suppress future reminders that no longer make sense because the underlying task has been completed.

The task itself remains authoritative.

---

# 30. Overdue Reminders

If a task becomes overdue while a reminder is pending, the notification system SHOULD evaluate whether the reminder remains relevant.

Example:

```text
Deadline:
18:00

Reminder:
17:30

Task completed:
17:15
```

No 17:30 reminder should be delivered.

---

# 31. Event Rescheduling

When an event moves:

```text
Event:
15:00 → 16:00

Reminder:
14:45
```

the reminder MUST be recalculated:

```text
Reminder:
15:45
```

unless the user explicitly converted it to an absolute-time reminder.

---

# 32. Event Cancellation

If an event is cancelled:

```text
Event cancelled
       ↓
Future event reminders
       ↓
Suppress
```

Previously delivered notifications remain part of notification history where appropriate.

---

# 33. Shared Reminders

A reminder MAY have multiple explicit recipients.

Example:

```text
Reminder:
Parent's appointment

Recipients:
Owner
Trusted User A
Trusted User B
```

Recipients MUST be explicit.

A reminder MUST NOT automatically notify every trusted relationship or workspace member.

---

# 34. Independent Recipient State

Each recipient owns their own notification state.

Example:

```text
Owner:
Snoozed 30 min

Trusted User:
Dismissed
```

These actions MUST NOT modify the owner's reminder state.

The underlying reminder remains shared.

---

# 35. Shared Reminder Permissions

The creator MUST have permission to share the reminder.

Recipients MUST have sufficient access to receive it.

The system MUST verify permissions server-side when:

* Creating the share
* Delivering the notification
* Opening the underlying object

---

# 36. Trusted User Notifications

Trusted users MAY receive important/shared reminders according to the trusted relationship permissions.

A trusted relationship MUST NOT automatically grant access to all notifications.

---

# 37. Revoked Trusted Relationship

If a trusted relationship is revoked:

```text
Relationship revoked
        ↓
Future shared notifications
        ↓
Must not be delivered
```

Existing notifications MUST be handled according to resource authorization and revocation policy.

The revoked user MUST NOT regain access through an old notification.

---

# 38. Notification Privacy

Notifications themselves can leak information.

Therefore:

```text
Private task title
```

MUST NOT appear in a notification delivered to a user who cannot access that task.

Likewise, public booking availability MUST NOT expose private event details.

---

# 39. Lock-Screen Privacy

The system SHOULD support notification privacy settings.

Possible modes:

```text
SHOW_FULL_CONTENT
SHOW_LIMITED_CONTENT
HIDE_CONTENT
```

Example limited notification:

```text
Workaholic
You have an upcoming reminder.
```

instead of:

```text
Submit confidential project proposal to Company X
```

---

# 40. Notification Preferences

Users SHOULD be able to configure preferences by:

* Channel
* Notification category
* Priority
* Quiet hours
* Device

Example:

```text
Calendar reminders:
Push = ON
Windows = ON
Email = OFF
```

---

# 41. Quiet Hours

Users MAY configure quiet hours.

Example:

```text
22:00 → 07:00
```

Normal notifications SHOULD be suppressed or deferred during quiet hours.

Critical/alarm-level reminders MAY bypass quiet hours if explicitly configured.

The policy MUST be transparent to the user.

---

# 42. Device-Specific Preferences

Preferences MAY differ by device.

Example:

```text
Windows:
Desktop notification ON

Android:
Push ON

Web:
Browser notification OFF
```

The backend MUST NOT assume every user's devices have identical capabilities.

---

# 43. Local vs Server Reminder Scheduling

Reminder processing SHOULD use a hybrid model.

### Server

Responsible for:

* Authoritative reminder state
* Shared reminders
* Cross-device consistency
* Persistent scheduling
* Push generation

### Client

Responsible for:

* Local scheduled alarms
* Offline reminder execution
* Platform-specific notification APIs
* Local snooze interaction

---

# 44. Offline Reminders

Previously synchronized reminders SHOULD continue working offline where the client has enough information to schedule them locally.

Example:

```text
Reminder:
Tomorrow 08:00

Device goes offline:
23:00

Local alarm:
Still fires at 08:00
```

When connectivity returns, the client MUST reconcile local state with the server.

---

# 45. Offline Reminder Safety

If an offline reminder depends on changed server state, the client MUST reconcile before treating it as authoritative.

Example:

```text
Task completed on another device
        ↓
Phone offline
        ↓
Old local reminder fires
        ↓
Client reconnects
        ↓
State reconciled
```

The system SHOULD suppress stale reminders after synchronization.

---

# 46. Duplicate Notification Prevention

The same logical reminder occurrence MUST NOT generate uncontrolled duplicate notifications.

The system SHOULD use deterministic notification/occurrence identity or idempotency keys.

Example:

```text
Reminder R1
Occurrence O5
```

must correspond to one logical notification event even if the background job runs twice.

---

# 47. Multi-Device Delivery

A user may have:

```text
Windows Laptop
Android Phone
Web Browser
```

The same reminder MAY be delivered to multiple configured channels/devices.

The system MUST avoid confusing:

```text
three devices
```

with:

```text
three independent reminders
```

There is one reminder with multiple deliveries.

---

# 48. Notification Actions

Where supported, notifications SHOULD expose contextual actions.

Examples:

```text
Reminder:
Submit assignment

Actions:
Open
Snooze
Mark Complete
```

```text
Calendar event:

Actions:
Open
Snooze Reminder
```

Actions MUST invoke authorized application operations rather than directly mutating client-local state without server reconciliation.

---

# 49. Notification Deep Links

Notifications SHOULD deep-link to the relevant Workaholic object.

Examples:

```text
Task → Task Details
Event → Calendar Event
Booking → Booking Details
Note → Note
Comment → Comment
```

If the object no longer exists or is inaccessible, the client MUST show an appropriate fallback instead of exposing stale/private data.

---

# 50. Booking Notifications

Booking-related notifications MAY include:

### Guest

* Booking confirmed
* Booking cancelled
* Booking rescheduled

### Owner

* New booking
* Booking cancelled
* Booking rescheduled
* Upcoming booking

Notification content MUST respect guest privacy and booking permissions.

---

# 51. Collaboration Notifications

Collaboration notifications MAY include:

* Task assignment
* Comment
* Mention
* Project update
* Shared event change
* Permission change

Users SHOULD be able to control notification preferences by category.

---

# 52. Sync Notifications

Synchronization errors MAY generate notifications when user action is required.

Examples:

```text
Google Calendar authorization expired
```

```text
A synchronization conflict requires review
```

Routine successful synchronization SHOULD NOT create noisy user-facing notifications.

---

# 53. Academic Notifications

Academic schedules MAY generate reminders for:

* Classes
* Exams
* Academic deadlines
* Important schedule changes

A change caused by Day Order recalculation SHOULD NOT generate a notification for every regenerated event unless the product explicitly determines that the change is significant.

The system SHOULD avoid notification storms.

---

# 54. Notification Storm Prevention

Bulk operations MUST be capable of suppressing redundant notifications.

Example:

```text
Holiday inserted
     ↓
100 academic events shifted
```

The system SHOULD NOT automatically send:

```text
100 separate notifications
```

unless explicitly required.

Instead, it MAY generate a summarized notification:

```text
Academic schedule updated due to holiday.
18 upcoming classes changed.
```

---

# 55. Notification Batching

Low-priority notifications MAY be grouped.

Example:

```text
5 project updates
```

may become:

```text
5 updates in Project X
```

Critical reminders SHOULD remain individually visible.

---

# 56. Notification Ordering

Notifications SHOULD be ordered using:

1. Urgency
2. Trigger time
3. Priority
4. Recency

The exact ranking algorithm MAY evolve.

---

# 57. Notification Retention

Notifications SHOULD have a finite retention policy where appropriate.

Important domain history MUST NOT depend solely on notification records.

Deleting an old notification MUST NOT delete:

* Task
* Event
* Booking
* Reminder
* Comment
* Project

---

# 58. Notification Auditability

The system SHOULD retain enough delivery information to diagnose:

```text
Why did I receive this?
Why did I not receive this?
Which device received it?
Was it delivered?
Was it dismissed?
Was it snoozed?
```

Audit data MUST avoid storing unnecessary sensitive notification content indefinitely.

---

# 59. Security Requirements

Notification APIs MUST enforce:

* Authentication
* Authorization
* Recipient validation
* Resource access validation
* Rate limiting
* Input validation
* Device/session validity

A notification ID MUST NOT be usable as a privilege-escalation mechanism.

---

# 60. Notification API Principles

The API layer SHOULD separate:

```text
Reminder CRUD
Notification retrieval
Notification state changes
Delivery management
Preference management
Device registration
```

Clients MUST NOT directly create arbitrary system notifications pretending to originate from privileged domains.

---

# 61. Device Registration

Each notification-capable device SHOULD register:

* Device identity
* Platform
* Application version
* Push token where applicable
* Capability information
* Last-seen information

Push tokens MUST be treated as sensitive operational credentials.

---

# 62. Invalid Device Tokens

If a push provider reports that a device token is invalid:

```text
Delivery fails permanently
        ↓
Device token marked invalid
        ↓
Future delivery skipped
```

The system SHOULD not repeatedly retry permanently invalid tokens.

---

# 63. Permission Revocation

When access to a resource is revoked:

```text
Permission revoked
      ↓
Pending notifications
      ↓
Re-evaluate authorization
```

The system MUST prevent future delivery of information the recipient is no longer entitled to receive.

---

# 64. Reminder and Notification Distinction

The following distinction is mandatory:

| Concept       | Meaning                                        |
| ------------- | ---------------------------------------------- |
| Reminder      | Instruction to trigger a notification          |
| Notification  | User-facing informational/actionable object    |
| Delivery      | Attempt to send notification through a channel |
| Snooze        | Change next reminder trigger                   |
| Dismiss       | Stop current notification presentation         |
| Complete task | Change task state                              |

These operations MUST NOT be conflated.

# 69. Acceptance Criteria

The Notification subsystem is considered complete when:

* Reminders can be created, edited, disabled, and deleted.
* Event-relative reminders move when their events move.
* Deadline-relative reminders follow task deadlines.
* Snoozing never changes the underlying domain object.
* Recurring reminders behave correctly across occurrences.
* Notifications have independent per-user state.
* Delivery attempts are independently tracked.
* Windows and Android notification paths are supported.
* Offline-capable reminders reconcile correctly.
* Shared reminders use explicit recipients.
* Recipient snooze/dismiss actions are independent.
* Revoked users cannot receive future protected notifications.
* Private information cannot leak through notification content.
* Duplicate deliveries are controlled.
* Delivery failures are recoverable.
* Notification preferences are respected.
* Critical reminders can use stronger delivery behavior.
* Bulk changes do not create uncontrolled notification storms.
* All notification actions enforce authorization.
* Tests cover the above behaviors.

# 70. Final Notification Model

```text
                 ┌─────────────────────┐
                 │   Domain Object     │
                 │ Task / Event / etc. │
                 └──────────┬──────────┘
                            │
                            ▼
                    ┌───────────────┐
                    │    Reminder   │
                    │   definition  │
                    └───────┬───────┘
                            │
                     trigger occurs
                            │
                            ▼
                  ┌──────────────────┐
                  │   Notification   │
                  └────────┬─────────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
           In-App       Android       Windows
           Delivery      Push         Desktop
              │            │            │
              └────────────┼────────────┘
                           ▼
                         User
                           │
                  ┌────────┴────────┐
                  ▼                 ▼
                Read             Snooze
                                    │
                                    ▼
                             Next Trigger
```

The central principle is:

> **A reminder determines when a user should be informed. A notification records what the user was told. Delivery determines how it reached them. None of these replaces the underlying task, event, booking, or other domain object as the source of truth.**
