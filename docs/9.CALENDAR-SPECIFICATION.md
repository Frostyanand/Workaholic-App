# `CALENDAR-SPECIFICATION.md`

**Status:** FINAL
**Version:** 1.0
**Product:** Workaholic
**Scope:** Calendar, scheduling, academic scheduling, recurrence, availability, public calendar projection, and calendar-integrated workflows

---

## 1. Purpose

The Workaholic Calendar subsystem provides a unified temporal representation of:

* Native Workaholic calendar events
* Imported and synchronized external calendar events
* Tasks scheduled onto specific dates or times
* Time-blocked work
* Recurring events
* Event occurrences and occurrence exceptions
* Academic class schedules driven by Day Order
* Holidays and special working days
* Reminders associated with events
* Booking availability and confirmed bookings
* Public calendar availability projections

The Calendar subsystem is responsible for representing **when work or other calendar-relevant activity occurs**.

It MUST NOT become the authority for unrelated domain concepts. Tasks remain task-domain objects, bookings remain booking-domain objects, and academic schedules remain academic-domain objects. The calendar provides their temporal representation where appropriate.

---

# 2. Calendar Authority Model

## 2.1 Calendar as a container

A **Calendar** is a logical container for calendar events.

A calendar MAY represent:

* Personal calendar
* Work calendar
* College calendar
* Academic calendar
* Birthday calendar
* Holiday calendar
* Imported Google Calendar
* Other future external calendar sources

A user MAY have multiple calendars.

A workspace MAY also contain shared calendars depending on permissions.

---

## 2.2 Event as the temporal object

A **Calendar Event** represents a specific scheduled occurrence or event series.

An event MAY contain:

* Title
* Description
* Start
* End
* Timezone
* All-day status
* Calendar
* Source
* Visibility
* Recurrence
* Location
* URL
* Attendees
* Related tasks
* Related projects
* Related academic schedule entry
* External provider identifiers
* Reminder configuration
* Provenance metadata

An event MUST have exactly one primary calendar.

---

## 2.3 Calendar is not the same as source

A calendar answers:

> "Which calendar does this event belong to?"

A source answers:

> "Where did this event originate?"

For example:

```text
Calendar:
College

Source:
Workaholic Academic Scheduler
```

or:

```text
Calendar:
Personal

Source:
Google Calendar
```

or:

```text
Calendar:
Work

Source:
Workaholic Native
```

This distinction is required for synchronization and safe source-specific operations.

# 3. Terminology

| Term              | Definition                                                                     |
| ----------------- | ------------------------------------------------------------------------------ |
| Calendar          | Container holding events                                                       |
| Calendar Source   | Origin/provenance of calendar data                                             |
| Event             | Temporal object representing scheduled activity                                |
| Event Series      | Recurring event definition                                                     |
| Occurrence        | One concrete instance of a recurring event                                     |
| Exception         | Modification or cancellation affecting one occurrence                          |
| Work Block        | Explicit block of time reserved for performing work                            |
| All-Day Event     | Event associated with calendar dates rather than clock times                   |
| Busy Interval     | Time interval considered unavailable                                           |
| Free Interval     | Time interval not occupied by blocking calendar objects                        |
| Native Event      | Event whose authoritative representation is in Workaholic                      |
| External Event    | Event whose authoritative representation is maintained by an external provider |
| Generated Event   | Event produced by another Workaholic subsystem                                 |
| Academic Event    | Event generated from academic scheduling rules                                 |
| Public Projection | Privacy-filtered representation of calendar availability                       |

# 4. Calendar Source Taxonomy

The system MUST distinguish event provenance.

Initial supported source categories:

```text
NATIVE
GOOGLE_CALENDAR
ACADEMIC_SCHEDULE
HOLIDAY
BIRTHDAY
IMPORTED
BOOKING
SYSTEM
```

Future sources MAY include:

```text
COLLEGE
TRAVEL
BOOKING_PROVIDER
DEVICE_CALENDAR
OTHER_EXTERNAL
```

The source taxonomy MUST be extensible.

---

## 4.1 Native source

`NATIVE` represents objects directly created and managed within Workaholic.

Example:

```text
Team meeting
Created in Workaholic
```

Workaholic is authoritative.

---

## 4.2 Google Calendar source

`GOOGLE_CALENDAR` represents events originating from Google Calendar.

The event MUST retain the external provider identity required for synchronization.

Example:

```text
Workaholic Event ID:
evt_123

Google Event ID:
abc123
```

The identifiers MUST remain separate.

---

## 4.3 Academic schedule source

`ACADEMIC_SCHEDULE` represents events generated from:

* Semester
* Academic calendar
* Day Order sequence
* Class schedule
* Schedule entry

These events MUST retain sufficient provenance to identify the rules that generated them.

---

## 4.4 Booking source

`BOOKING` represents calendar events created as a result of confirmed bookings.

The booking remains authoritative for booking-specific state.

The event MUST NOT be treated as the booking itself.

---

# 5. Native and External Calendar Coexistence

Workaholic MUST support simultaneous native and external calendars.

Example:

```text
Personal
├── Workaholic Personal
├── Google Personal
└── Birthdays

College
├── Academic Schedule
├── Holidays
└── Google College Calendar
```

The UI MAY display multiple calendars together.

The backend MUST retain calendar identity and source identity separately.

# 6. Event Lifecycle

An event follows:

```text
Create
  ↓
Active
  ↓
Edit / Reschedule / Exception
  ↓
Completed by time passage
  ↓
Optional cancellation
  ↓
Optional deletion
```

Time passage MUST NOT automatically delete historical events.

Past events SHOULD remain queryable according to retention policies.

---

## 6.1 Create

An event creation request MUST validate:

* Calendar access
* Start/end validity
* Timezone
* Recurrence configuration
* Source-specific permissions
* Related-resource permissions
* Attendee permissions where applicable

---

## 6.2 Edit

Editing behavior depends on whether the event is:

* Non-recurring
* A recurring series
* A single occurrence
* External
* Generated

The UI MUST clearly distinguish:

```text
Edit this occurrence
Edit this and future occurrences
Edit entire series
```

where applicable.

---

## 6.3 Delete

Deletion MUST respect source authority.

A native event MAY be deleted by an authorized user.

An external event MUST be handled according to synchronization rules.

Deleting an external representation from Workaholic MUST NOT implicitly mean that the external provider object should be deleted unless the synchronization contract explicitly defines that operation.

---

# 7. Event Visibility

Initial visibility states:

```text
PRIVATE
SHARED
PUBLIC
```

## 7.1 PRIVATE

Private events:

* Are visible only to authorized users
* MUST NOT expose title/details through public calendar projection
* SHOULD appear as busy to users who only have availability access

---

## 7.2 SHARED

Shared events are visible to users granted the necessary permissions.

Visibility does not automatically grant editing permission.

For example:

```text
Can view = YES
Can edit = NO
```

is valid.

---

## 7.3 PUBLIC

Public events MAY expose:

* Title
* Start
* End
* Basic public information

They MUST NOT expose:

* Private notes
* Internal IDs
* Private attendees
* Internal permissions
* Sensitive metadata
* Hidden relationships

---

# 8. Time and Timezone Model

Timezone handling is a core calendar requirement.

## 8.1 Stored timestamps

Instant-based event times MUST represent an unambiguous point in time.

Timezone information MUST be retained where user-facing calendar semantics depend upon it.

The system MUST NOT treat local wall-clock time as universally equivalent to UTC.

---

## 8.2 User timezone

Each user SHOULD have a preferred timezone.

Calendar rendering SHOULD default to the user's preferred timezone unless the event/calendar explicitly requires another interpretation.

---

## 8.3 Event timezone

An event MAY have an explicit timezone.

Example:

```text
Meeting:
2026-09-10 10:00
Timezone:
Asia/Kolkata
```

The UI MUST render the event correctly when the user changes timezone.

---

## 8.4 Daylight Saving Time

Recurring events MUST respect timezone rules.

For example, a recurring event defined as:

```text
Every Monday at 09:00
America/New_York
```

must continue to mean **09:00 local time**, rather than simply adding a fixed UTC duration.

DST transitions MUST therefore be handled using timezone-aware recurrence processing.

---

# 9. All-Day Events

All-day events represent calendar dates rather than a specific clock interval.

Example:

```text
2026-09-15
Holiday
```

An all-day event MUST NOT be represented merely as:

```text
00:00 → 23:59
```

because this creates incorrect semantics across timezone changes.

All-day events MUST preserve date-based semantics.

---

# 10. Event Duration

For timed events:

```text
end > start
```

Zero-duration events MAY be supported for future use cases such as:

* Milestones
* Deadlines
* Reminders

However, normal calendar events SHOULD have positive duration.

---

# 11. Recurring Events

Recurring events consist of:

```text
Series Definition
        ↓
Occurrence Expansion
        ↓
Occurrence Exceptions
```

The recurring series is the authoritative definition.

Individual occurrences SHOULD NOT become independent permanent events unless required by the implementation.

---

## 11.1 Recurrence properties

A recurrence definition MAY include:

* Frequency
* Interval
* Days of week
* Day of month
* Month
* Start date
* End condition
* Count
* Timezone

Examples:

```text
Every Monday at 10:00
```

```text
Every weekday at 09:00
```

```text
Every month on the 15th
```

```text
Every 2 weeks on Monday and Wednesday
```

---

# 12. Occurrence Expansion

The system MUST be able to determine whether a recurring event occurs within a requested date range.

Example:

```text
Calendar query:
2026-09-01 → 2026-09-30
```

The system expands only the relevant recurrence range rather than permanently materializing an unlimited number of events.

---

## 12.1 Expansion boundaries

Occurrence generation MUST respect:

* Series start
* Series end
* Recurrence count
* Exception dates
* Timezone
* Calendar query range

---

# 13. Occurrence Exceptions

A recurring series MAY have occurrence-specific exceptions.

Supported exception types:

```text
CANCELLED
RESCHEDULED
MODIFIED
```

Example:

```text
Normal:
Every Monday 10:00

September 14:
Cancelled
```

The series remains unchanged.

Only the affected occurrence changes.

---

# 14. Conflict and Busy-Time Semantics

Calendar conflicts are based on time intervals, not event names.

Two timed events conflict when their occupied intervals overlap according to the calendar's blocking policy.

Example:

```text
Event A:
10:00 → 11:00

Event B:
10:30 → 11:30

Conflict:
YES
```

Where:

```text
Event A:
10:00 → 11:00

Event B:
11:00 → 12:00
```

there is no overlap.

---

## 14.1 Busy classification

Calendar objects MAY be classified as:

```text
FREE
BUSY
TENTATIVE
```

The exact external provider mapping belongs to synchronization implementation.

Private events MUST still contribute to availability as busy intervals when configured to do so.

---

# 15. Tasks in Calendar

A task is not automatically a calendar event.

The following concepts remain separate:

```text
Task
= work that needs completion

Deadline
= latest required completion time/date

Work Block
= reserved time for working on a task

Calendar Event
= scheduled temporal occurrence
```

---

## 15.1 Task with deadline

Example:

```text
Task:
Submit DBMS assignment

Deadline:
September 10, 23:59
```

This does not necessarily reserve calendar time.

---

## 15.2 Task with work block

Example:

```text
Task:
Prepare DBMS assignment

Work Block:
September 8
18:00 → 20:00
```

The task remains the task-domain object.

The work block represents scheduled execution time.

---

# 16. Work Blocks

A Work Block reserves time for completing a task or project-related activity.

A work block MAY reference:

* Task
* Project
* Board
* User
* Calendar

A work block SHOULD appear in calendar views.

It MUST NOT automatically mark the task complete when the block ends.

---

# 17. Calendar Views

The calendar subsystem MUST support the conceptual model required by the following views:

```text
Day
Week
Workweek
Month
Agenda
Year
```

The initial implementation MAY phase these views, but the underlying calendar model MUST support them.

---

## 17.1 Day view

Displays:

* Timed events
* Work blocks
* Conflicts
* Current time
* Relevant tasks
* All-day events

---

## 17.2 Week view

Displays seven consecutive dates.

Timed events SHOULD be positioned according to start/end time.

---

## 17.3 Workweek view

Displays configured working days.

The default SHOULD be Monday through Friday, but this MUST NOT be hardcoded for academic scheduling.

---

## 17.4 Month view

Displays:

* All-day events
* Event summaries
* Task deadlines
* Academic events
* Holidays
* Recurring events

---

## 17.5 Agenda view

Provides a chronological event list.

This view SHOULD be efficient for long ranges.

---

## 17.6 Year view

Provides high-level temporal overview.

The year view SHOULD prioritize:

* Density
* Event presence
* Holidays
* Important dates
* Deadlines

rather than attempting to display every event detail.

---

# 18. Today View Integration

The Today view is the primary daily command center.

It SHOULD combine:

```text
Current time
Upcoming calendar events
Scheduled work blocks
Tasks due today
Overdue tasks
Important tasks
Unscheduled tasks
Relevant reminders
```

Calendar data MUST therefore be queryable efficiently for a single day.

---

# 19. Academic Calendar Subsystem

Academic scheduling is a specialized calendar generator.

The authoritative conceptual chain is:

```text
Semester
   ↓
Academic Calendar
   ↓
Working / Non-working Days
   ↓
Day Order Sequence
   ↓
Class Schedule
   ↓
Schedule Entries
   ↓
Generated Calendar Events
```

The academic subsystem MUST NOT model Day Order as simply another recurring weekday pattern.

---

# 20. Semester

A Semester defines an academic scheduling context.

It MAY contain:

* Name
* Institution
* Start date
* End date
* Timezone
* Academic calendar
* Day Order configuration
* Class schedules
* Lifecycle state

Lifecycle:

```text
UPCOMING
ACTIVE
ENDED
```

---

# 21. Academic Calendar

An academic calendar maps dates to scheduling behavior.

Each relevant date MUST be capable of representing:

```text
WORKING_DAY
HOLIDAY
SPECIAL_WORKING_DAY
OTHER_NON_WORKING_DAY
```

The system MUST retain the reason/source where useful.

---

# 22. Weekends and Day Order

Saturday and Sunday MUST NOT automatically advance Day Order.

However, a weekend MAY explicitly be configured as a working day.

Example:

```text
Saturday:
Special Working Day
DO = 5
```

The system MUST therefore derive Day Order from the academic calendar, rather than simply from weekday arithmetic.

---

# 23. Holidays and Day Order

A holiday does not consume a Day Order.

Example:

```text
Monday → DO 1
Tuesday → DO 2
Wednesday → Holiday
Thursday → DO 3
```

If a holiday is inserted after schedules have been generated, subsequent Day Order assignments MUST be recalculated.

This recalculation MUST propagate to DO-linked class schedule events.

---

# 24. Day Order Sequence

A Day Order sequence defines the mapping between academic working dates and Day Order values.

Example:

```text
Date        Day Order
Sep 1       1
Sep 2       2
Sep 3       Holiday
Sep 4       3
Sep 5       4
```

The system MUST NOT assume:

```text
Day Order = weekday
```

Day Order is an academic sequence.

---

# 25. Class Schedule Template

A class schedule is a reusable mapping from Day Order to scheduled classes.

Example:

```text
DO 1
  09:00 → 10:00 Mathematics
  10:00 → 11:00 Networks

DO 2
  09:00 → 10:00 DBMS
  11:00 → 12:00 OOP
```

The schedule MUST be reusable independently of a particular semester where appropriate.

This allows a schedule mapping to survive semester transitions.

---

# 26. Schedule Entry

A Schedule Entry identifies a specific class/activity within a schedule.

It MAY include:

* Subject
* Instructor
* Room
* Start time
* End time
* Day Order
* Schedule
* Metadata

A schedule entry is a **rule/template**.

It is not itself a historical calendar event.

---

# 27. Generated Academic Events

Calendar events generated from a class schedule MUST retain provenance.

Conceptually:

```text
Event
 ├── source = ACADEMIC_SCHEDULE
 ├── semester_id
 ├── class_schedule_id
 ├── schedule_entry_id
 ├── day_order
 └── academic date
```

This provenance is mandatory for safe recalculation and semester lifecycle operations.

---

# 28. Academic Schedule Generation

When an active semester has a valid academic calendar and class schedule:

```text
Academic Calendar
        ↓
Determine Day Order
        ↓
Match Schedule Entries
        ↓
Generate Events
```

Generation MUST be deterministic.

Given identical:

```text
Semester
Academic Calendar
Schedule
Schedule Entries
```

the same event set SHOULD be produced.

---

# 29. Academic Recalculation

When an academic calendar changes:

```text
Holiday inserted
       ↓
Recalculate Day Order
       ↓
Identify affected future dates
       ↓
Update generated events
```

The system MUST NOT blindly regenerate or delete all calendar events.

Only events whose provenance indicates that they were generated by the affected academic schedule SHOULD be modified.

---

# 30. Idempotent Academic Generation

Repeated generation MUST NOT create duplicate events.

Example:

```text
Generate schedule
Generate schedule again
```

must produce:

```text
One event per valid generated occurrence
```

rather than duplicate copies.

Generation SHOULD use deterministic identifiers or equivalent uniqueness constraints.

---

# 31. Academic Exceptions

Academic scheduling MUST distinguish:

### Holiday

The academic day does not count toward Day Order.

### Cancelled class

The academic day remains valid, but a particular class occurrence does not happen.

### Rescheduled class

A specific class occurrence moves to another date/time.

### Special working day

A normally non-working date is explicitly treated as a working academic date.

These states MUST NOT be collapsed into a single "exception" meaning.

---

# 32. Cancelled Classes

A cancelled class MUST preserve academic-calendar history.

Example:

```text
DO 4:
Mathematics
10:00 → 11:00

Status:
Cancelled
```

The system MUST NOT convert the entire day into a holiday.

---

# 33. Rescheduled Classes

A rescheduled class SHOULD be represented as an occurrence-specific exception.

The original schedule template remains unchanged.

Example:

```text
Normal:
DO 5 → Mathematics → 10:00

Exception:
Sep 12 → Mathematics → 14:00
```

---

# 34. Semester End

Ending a semester is an explicit lifecycle operation.

When the user selects:

> **End Semester**

the system MUST:

1. Mark the semester as ended.
2. Stop future generation from that semester.
3. Remove or invalidate future generated academic occurrences belonging to that semester.
4. Preserve past academic history.
5. Preserve the reusable class schedule/template.
6. Preserve Day Order mappings as historical data.
7. Preserve unrelated personal/work/external calendar events.

The operation MUST NOT perform a broad calendar wipe.

---

# 35. Semester-End Safety

The operation MUST identify generated events using provenance.

Conceptually:

```text
source = ACADEMIC_SCHEDULE
semester_id = semester_123
```

Only matching future generated events are candidates for invalidation/removal.

An event such as:

```text
Personal dentist appointment
```

MUST remain untouched.

---

# 36. Calendar Event and Reminder Integration

Events MAY have reminders.

Examples:

```text
Meeting
Reminder:
15 minutes before
```

```text
Exam
Reminder:
1 day before
```

Reminder behavior is defined in `NOTIFICATION-SPECIFICATION.md` and related domain rules.

The Calendar subsystem only defines the temporal trigger relationship.

---

# 37. Google Calendar Integration

Google Calendar is an external calendar source.

Workaholic MUST support coexistence between:

```text
Workaholic native calendars
+
Google calendars
```

where the integration is authorized.

---

## 37.1 Calendar mapping

A Google calendar SHOULD map to a Workaholic calendar representation.

Conceptually:

```text
Workaholic Calendar
        ↕
Google Calendar ID
```

The mapping MUST be persistent.

---

## 37.2 Event mapping

A synchronized event MUST maintain:

```text
Workaholic event ID
Google event ID
Google calendar ID
sync metadata/version information
```

The IDs MUST NOT be conflated.

| Timezone    | Time zone                     |

# 39. Google Synchronization Authority

Native Workaholic events are authoritative within their native domain.

Google-originated events remain externally authoritative unless explicitly converted/copied into native Workaholic objects.

Two-way synchronization MUST follow the rules defined in `SYNC-SPECIFICATION.md`.

The calendar specification does not redefine conflict resolution.

---

# 40. Google Calendar Deletion

External deletion MUST be represented as an external deletion state and propagated through synchronization.

The system MUST distinguish:

```text
External event deleted
```

from:

```text
Workaholic user deleted local representation
```

No ambiguous deletion behavior is permitted.

---

# 41. Disconnecting Google Calendar

Disconnecting Google Calendar MUST NOT cause unrelated native Workaholic calendar data to be deleted.

Depending on product policy, synchronized Google events MAY:

* Remain as last-known imported data
* Become read-only
* Be removed from active synchronization

The selected behavior MUST preserve user data and remain consistent with `SYNC-SPECIFICATION.md`.

---

# 42. Public Calendar Projection

Public calendar access MUST NOT expose the internal calendar database directly.

Instead:

```text
Private Calendar
      ↓
Privacy Projection
      ↓
Public Calendar Link
```

The projection contains only explicitly permitted information.

---

## 42.1 Private event projection

A private event SHOULD appear publicly as:

```text
Busy
10:00 → 11:00
```

without revealing:

```text
Title
Description
Attendees
Notes
Task relationships
Project
```

---

## 42.2 Public event projection

A public event MAY expose:

```text
Title
Start
End
```

subject to public-calendar policy.

---

# 43. Public Calendar Link Security

Public calendar links MUST be:

* Unpredictable
* Revocable
* Regeneratable
* Independently permissioned
* Non-indexed by default

A revoked public link MUST immediately stop providing current public data.

Public access MUST NOT require a Workaholic account unless explicitly configured otherwise.

---

# 44. Booking and Calendar Interaction

Booking availability is calculated against relevant calendar busy intervals.

Conceptually:

```text
Booking Page
     ↓
Availability Rules
     +
Calendar Busy Intervals
     ↓
Bookable Slots
```

---

## 44.1 Private events and booking

Private events MUST still block booking where configured.

The booking guest MUST NOT learn the details of the private event.

Example:

```text
Calendar:
Private meeting
14:00 → 15:00

Public booking page:
14:00 → 15:00 unavailable
```

No private title is exposed.

---

# 45. Booking Confirmation

A confirmed booking MAY create a calendar event.

The relationship MUST be explicit:

```text
Booking
   ↕
Calendar Event
```

The calendar event MUST NOT become the sole authoritative booking record.

Booking state remains in the Booking subsystem.

---

# 46. Calendar Permissions

Calendar access MUST follow workspace/user authorization.

Possible capabilities include:

```text
calendar.view
calendar.create
calendar.edit
calendar.delete
calendar.share
calendar.manage_visibility
calendar.manage_public_link
calendar.manage_integrations
```

Permissions MUST be evaluated server-side.

A client MUST NOT be trusted merely because a calendar is visible in its UI.

---

# 47. Cross-Resource Permissions

Calendar events linked to tasks/projects MUST NOT bypass authorization.

For example:

```text
User can view calendar
User cannot view private project
```

The calendar MUST NOT expose project information through the event.

Similarly:

```text
User can view event
User cannot view linked private task
```

The task's private information MUST remain protected.

---

# 48. Calendar Queries

The backend MUST support efficient range queries.

Primary query dimensions include:

```text
calendar
start date/time
end date/time
source
visibility
user/workspace
```

Typical query:

```text
Give all calendar activity for:
2026-09-05 00:00
→
2026-09-06 00:00
```

---

# 49. Occurrence Query Performance

Recurring events SHOULD be expanded only within requested ranges.

The system SHOULD avoid:

```text
Generate every occurrence for the next 10 years
```

when the client only requests:

```text
This week
```

The implementation MAY use cached/materialized occurrences later if justified by measured performance.

---

# 50. Calendar Pagination

Long-range agenda queries MUST support pagination or equivalent bounded retrieval.

The system MUST avoid returning an unbounded number of events.

---

# 51. Calendar Caching

Caching MAY be introduced where measurements justify it.

Initial architecture MUST NOT require Redis or a distributed cache.

Correctness and synchronization take precedence over aggressive caching.

---

# 52. Offline Calendar Behavior

Previously synchronized calendar data MAY remain available offline.

Offline users MAY:

* View cached events
* View cached schedules
* Create native events
* Edit eligible native events
* Schedule tasks/work blocks

Mutations MUST enter the local synchronization queue.

---

## 52.1 Offline external operations

Operations requiring authoritative external state MUST NOT pretend to have succeeded offline.

Examples:

* Confirming a booking
* Performing an external Google mutation requiring current provider state
* Publishing a public calendar link
* Certain conflict-sensitive operations

The UI MUST distinguish:

```text
Saved locally
```

from:

```text
Synchronized successfully
```

---

# 53. Calendar Data Integrity

The following invariants MUST hold:

1. Every event belongs to exactly one calendar.
2. Every event has a valid source classification.
3. Timed events have valid start/end values.
4. All-day events use date semantics.
5. Recurring events have valid recurrence definitions.
6. Occurrence exceptions reference valid series/occurrences.
7. Generated academic events retain provenance.
8. Academic generation is idempotent.
9. Semester end cannot delete unrelated events.
10. Private event details cannot leak through public projections.
11. External identifiers remain separate from native identifiers.
12. Booking confirmation cannot rely solely on a calendar event.
13. Calendar visibility cannot override resource authorization.
14. Historical events are not silently destroyed through ordinary temporal progression.

---

```text
Academic schedule regenerated
Class occurrence cancelled
```

The activity record MUST NOT expose information to users who lack permission to view the underlying object.

Calendar operations MAY produce notifications for:

* Booking confirmation

Notification delivery is handled by the notification subsystem.

A trusted relationship MUST NOT automatically grant access to all calendars.

Example:

```text
Trusted User:
Can view academic calendar
Can view availability
Cannot view personal private events
```

This is valid.

# 60. Calendar and Collaboration

Workspace calendars MAY support:

Collaboration permissions remain resource-specific.

# 61. Calendar Deletion and Recovery

Important native calendar objects SHOULD support soft deletion/trash where appropriate.

Deletion MUST distinguish:

```text
Delete native event
Cancel occurrence
Delete recurring series
Remove external mapping
Disconnect external calendar
```

These are different operations.

---

# 62. Calendar Source-Specific Operations

Operations MUST be scoped to their source.

Examples:

```text
End Semester
→ affects academic generated events

Disconnect Google
→ affects Google synchronization

Revoke Public Link
→ affects public projection

Delete Native Event
→ affects native event
```

No generic "delete all events" operation SHOULD be used for normal lifecycle operations.

# 63. Academic Recalculation Safety Example

Given:

```text
Monday  → DO 1
Tuesday → DO 2
Wednesday → DO 3
Thursday → DO 4
Friday → DO 5
```

If Wednesday becomes a holiday:

```text
Monday  → DO 1
Tuesday → DO 2
Wednesday → Holiday
Thursday → DO 3
Friday → DO 4
```

The academic scheduler MUST update future generated class events accordingly.

It MUST NOT:

* Delete personal meetings
* Modify Google-originated events
* Modify unrelated native events
* Destroy the reusable class schedule
* Destroy historical completed classes

---

# 64. Academic Schedule Reuse Example

A user may define:

```text
Class Schedule:
DO 1 → Networks
DO 2 → DBMS
DO 3 → OOP
```

At semester end:

```text
Semester A → ENDED
```

The schedule mapping remains available.

A new semester MAY later reuse or clone the mapping:

```text
Semester B
   ↓
Existing schedule template
   ↓
New generated events
```

The new semester MUST have its own generated-event provenance.

### CAL-T04: All-day event

Verify all-day event semantics across timezone changes.

### CAL-T05: Recurrence

### CAL-T06: Recurrence exception

Cancel one occurrence without changing the series.

### CAL-T07: Conflict

Detect overlapping busy intervals.

### CAL-T08: Private event

Verify private details are inaccessible to unauthorized users.

### CAL-T09: Public projection

Verify private events appear only as busy intervals.

### CAL-T10: Public link revocation

Revoke a public link and verify access immediately fails.

### CAL-T11: Google mapping

Verify native and external IDs remain distinct.

### CAL-T12: External deletion

Verify Google deletion propagates correctly.

### CAL-T13: Offline mutation

Create an event offline and synchronize it after reconnection.

### CAL-T14: Academic holiday

Insert a holiday and verify subsequent Day Orders shift.

### CAL-T15: Weekend exception

Mark a Saturday as a special working day and verify it advances Day Order.

### CAL-T16: Class cancellation

Cancel one class without converting the academic day into a holiday.

### CAL-T17: Class rescheduling

### CAL-T18: Semester end

### CAL-T19: Semester isolation

Verify semester-end cleanup does not affect unrelated events.

### CAL-T20: Idempotent generation

Run academic event generation repeatedly and verify no duplicates.

### CAL-T21: Booking conflict

# 69. Final Calendar Model

The complete conceptual model is:

```text
                         ┌─────────────────┐
                         │    Calendar     │
                         │   container     │
                         └────────┬────────┘
                                  │
                                  ▼
                         ┌─────────────────┐
                         │     Events      │
                         └────────┬────────┘
                                  │
                 ┌────────────────┼────────────────┐
                 │                │                │
                 ▼                ▼                ▼
             Native          External          Generated
             Events          Events             Events
                 │                │                │
                 │          Google Calendar       │
                 │                               Academic
                 │                               Scheduler
                 │                                   │
                 │                         ┌─────────┴─────────┐
                 │                         ▼                   ▼
                 │                    Semester          Day Order
                 │                         │                   │
                 │                         └────────┬──────────┘
                 │                                  ▼
                 │                           Class Schedule
                 │                                  │
                 │                                  ▼
                 │                          Generated Events
                 │
                 ├──────────────┐
                 ▼              ▼
              Tasks          Work Blocks
                 │              │
                 └───────┬──────┘
                         ▼
                    Today / Calendar
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          Reminders   Availability  Public
                                  Projection
                                      │
                                      ▼
                                  Booking
```

The central principle is:

> **The calendar represents temporal reality, while each originating domain remains authoritative for its own meaning and lifecycle.**

This separation is what allows Workaholic to combine personal scheduling, tasks, Google Calendar, academic Day Order scheduling, bookings, reminders, and future collaboration without turning the calendar into an unsafe "delete everything that looks related" system.
