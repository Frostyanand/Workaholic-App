# `ARCHITECTURE-DECISIONS.md`

**Status:** FINAL
**Purpose:** Consolidate the small set of architectural decisions that must remain consistent during implementation. This document intentionally replaces separate ADR files.

---

## 1. Decision: Modular Monolith

Workaholic will initially be implemented as a **modular monolith**.

The backend will have clear domain modules, but these modules will run within one application.

Initial logical boundaries include:

* Authentication
* Users and Workspaces
* Tasks
* Projects
* Boards
* Calendar
* Academic Scheduling
* Notes
* Notifications
* Bookings
* Integrations
* Synchronization
* Collaboration
* Public Access

These boundaries are intended to preserve separation of concerns without introducing microservice infrastructure.

### Rationale

The initial deployment is expected to serve approximately 10 to 20 users, while the architecture should remain capable of scaling to thousands.

Microservices, message brokers, Kubernetes, and independently deployed services are unnecessary at the initial scale.

The system may be decomposed later if measurable operational or scaling requirements justify it.

---

# 2. Decision: PostgreSQL Is the System of Record

PostgreSQL is the authoritative persistent datastore for Workaholic's native domain.

Native Workaholic entities include, among others:

* Users
* Workspaces
* Memberships
* Tasks
* Projects
* Boards
* Calendar entities
* Notes
* Reminders
* Bookings
* Permissions
* Synchronization state
* External-resource mappings

External providers are **not** the authoritative source for Workaholic's richer native domain.

---

# 3. Decision: Native Domain + External Integrations

Workaholic will maintain its own domain model while integrating with external services.

For Google integrations:

```text
Workaholic Entity
       |
       +---- Native ID
       |
       +---- External Provider
       |
       +---- External ID
```

External IDs must not replace Workaholic's own identifiers.

This allows Workaholic to:

* Maintain richer functionality than external providers.
* Support synchronization.
* Preserve relationships between native resources.
* Potentially support additional providers later.
* Continue functioning when an external integration is unavailable.

---

# 4. Decision: Google Calendar and Google Tasks Use Hybrid Synchronization

Google Calendar and Google Tasks integration will use the synchronization model defined in `SYNC-SPECIFICATION.md`.

The architecture is neither:

```text
Google is always authoritative
```

nor:

```text
Workaholic completely ignores Google state
```

Instead, synchronization explicitly tracks:

* External IDs.
* Provider state.
* Synchronization direction.
* Synchronization cursors/state.
* Conflicts.
* Deletions.
* Mapping relationships.
* Last-known synchronization state.

Workaholic's richer native domain remains authoritative for Workaholic-only functionality.

---

# 5. Decision: Google Drive Stores Integrated Attachments

When Google Drive integration is authorized, Workaholic may associate attachments with Google Drive files.

Workaholic stores the relationship and relevant metadata rather than unnecessarily duplicating the underlying binary.

Removing a Workaholic attachment relationship does **not** automatically delete the Drive file.

Explicit deletion from Drive is a separate operation.

This protects user data and avoids unnecessary duplicate storage.

---

# 6. Decision: Academic Day Order Is a Scheduling Engine

College Day Order scheduling is not implemented as a collection of unrelated calendar events.

The conceptual model is:

```text
Semester
   ↓
Academic Calendar
   ↓
Working / Non-working Days
   ↓
Day Order Sequence
   ↓
Schedule Template
   ↓
Class Schedule Entries
   ↓
Generated Calendar Occurrences
```

Generated events retain sufficient provenance to determine:

* Which semester generated them.
* Which Day Order generated them.
* Which schedule entry generated them.

Therefore:

* Holidays can shift the DO sequence.
* Working Saturdays can be explicitly represented.
* Cancelled classes can be distinguished from holidays.
* Rescheduled classes can be represented independently.
* Ending a semester can invalidate/remove future generated occurrences without destroying reusable schedule definitions or historical records.

This prevents academic scheduling logic from corrupting ordinary personal calendar data.

# 7. Decision: Server Authority With Offline Clients

Workaholic will support offline-capable clients, particularly Windows and Android.

The server remains authoritative for synchronized application state.

Clients may maintain:

* Local state.
* Local pending operations.
* Cached data.
* Locally scheduled reminders.
* Offline-created/modified resources.

Conceptually:

```text
                 Server
              authoritative
                   ↑
                   │ sync
        ┌──────────┼──────────┐
        │          │          │
       Web       Windows    Android
        │          │          │
       local      local      local
       state      state      state
```

Offline operations shall eventually reconcile according to the synchronization rules.

Offline support must not create a second permanent source of truth.

---

# 8. Decision: Notifications Are Server-Defined, Client-Executed Where Appropriate

Reminder configuration is stored as authoritative application state.

Where platform capabilities permit, clients may schedule local notifications/alarms.

Examples:

```text
Server reminder configuration
          ↓
Windows local scheduler
          ↓
Windows notification/alarm
```

and:

```text
Server reminder configuration
          ↓
Android local scheduler
          ↓
Android notification/alarm
```

The server remains responsible for synchronization and reminder state.

This avoids unnecessary server polling while supporting reliable platform-specific notification behavior.

---

# 9. Decision: No Dedicated Chat Infrastructure Yet

Chat is explicitly **Coming Soon**.

The initial implementation will not include:

* Direct chat.
* Group chat.
* Project chat.
* Chat message storage.
* Chat-specific realtime infrastructure.

The architecture should avoid making assumptions that would prevent future chat functionality.

Firebase/Firestore or another realtime/document-oriented technology may be evaluated later if chat requirements justify it.

No chat infrastructure should be introduced merely to prepare for a future feature.

---

# 10. Decision: AI Is Deferred

AI/NLP functionality is explicitly **Coming Soon**.

The initial application will not depend on an LLM for core functionality.

Future AI functionality may include:

* Understanding natural-language scheduling requests.
* Finding available time.
* Creating or modifying tasks.
* Rescheduling work.
* Inspecting the user's schedule.
* Performing controlled application actions.

When implemented, AI must operate through controlled application actions/tools.

Conceptually:

```text
LLM
 ↓
Validated application action
 ↓
Authorization
 ↓
Domain/business rules
 ↓
Database
```

The LLM must never receive unrestricted direct database manipulation capabilities.

---

# 11. Decision: PostgreSQL Before Specialized Search

Initial global search will use PostgreSQL/native application search capabilities.

A dedicated search engine will only be introduced if actual scale or functionality demonstrates that database-native search is insufficient.

The initial architecture therefore avoids:

* Elasticsearch.
* OpenSearch.
* Dedicated search clusters.

Search quality and performance should first be improved through appropriate schema design, indexes, query design, and pagination.

---

# 12. Decision: No Premature Cache Infrastructure

Caching is not a mandatory initial architectural layer.

The system should first optimize:

1. Database queries.
2. API response sizes.
3. Client state management.
4. HTTP/browser caching.
5. Pagination.
6. Indexing.

Redis or another dedicated caching system may be introduced only when a measurable workload justifies it.

Cache data must never become the authoritative source of application state.

---

# 13. Decision: No Premature Message Broker

Kafka, RabbitMQ, and equivalent infrastructure are not part of the initial architecture.

Asynchronous processing should initially use managed background/scheduled execution and database-backed state where appropriate.

A message broker may be introduced later if workload characteristics justify it.

---

# 14. Decision: Managed Infrastructure First

The initial deployment will favor managed infrastructure.

The intended architecture is approximately:

```text
Web
 ↓
Vercel

Backend
 ↓
Managed execution

Database
 ↓
Managed PostgreSQL

Background work
 ↓
Managed scheduled/background execution

External services
 ↓
Google APIs

Clients
 ↓
Windows + Android + Web
```

The project should minimize infrastructure administration.

---

# 15. Decision: Cost Optimization Through Simplicity

Workaholic targets minimal initial operating cost.

Cost optimization shall primarily come from:

* Managed infrastructure.
* Efficient database access.
* Incremental synchronization.
* Client-side processing where appropriate.
* Reusing Google Drive storage.
* Avoiding unnecessary API calls.
* Controlled background execution.
* Controlled observability volume.

Cost reduction must not compromise:

* Security.
* Data integrity.
* Backups.
* Synchronization correctness.
* Reminder reliability.
* Authorization.
* Privacy.

---

# 16. Decision: Security Boundaries Are Mandatory

Authentication and authorization remain separate concerns.

```text
Authentication
    ↓
Who is this?
    ↓
Authorization
    ↓
What may this user access/do?
```

Every protected resource must be authorized according to the applicable workspace, membership, ownership, role, or granular permission.

External integrations must also have their own authorization lifecycle.

OAuth credentials and refresh credentials must remain server-side and must never be embedded into clients.

---

# 17. Decision: Public Access Is Deliberately Restricted

Public calendar and booking functionality does not make the user's entire calendar public.

Public calendar views expose only the information explicitly permitted by the public-calendar rules.

Private events are represented as busy without exposing private metadata.

Public links must be:

* Revocable.
* Regeneratable.
* Unpredictable.
* Independently controllable.

Public access does not bypass normal internal authorization.

---

# 18. Decision: Data Is Soft-Deleted Where Appropriate

Important application objects should use recoverable deletion/trash semantics where appropriate.

The application must distinguish:

```text
Deleted
```

from:

```text
Permanently destroyed
```

External resources such as Google Drive files must have their own deletion semantics and must not be accidentally destroyed because a Workaholic relationship was removed.

---

# 19. Decision: Documentation Is Now Frozen

The following documents are authoritative specifications for implementation.

The project should **not continue generating documentation simply for the sake of documentation**.

New documentation should only be created when:

* A genuinely new architectural requirement appears.
* An important implementation decision cannot be represented clearly in existing documentation.
* A significant behavior changes.

Small implementation decisions should live with the code rather than generating another specification document.

---

# 20. Decision: Code Must Follow the Specifications

During implementation, the existing specifications are the source of truth.

If implementation reveals a genuine contradiction or impossible requirement:

```text
Discover conflict
      ↓
Stop affected implementation
      ↓
Identify actual issue
      ↓
Make deliberate decision
      ↓
Update affected authoritative documentation
      ↓
Continue
```

The implementation must not silently invent behavior that contradicts the specifications.

---

# 21. Decision: Build Incrementally

Workaholic will be developed in independently verifiable phases.

Every implementation task should be capable of being:

1. Implemented.
2. Compiled/type-checked.
3. Tested.
4. Run locally where applicable.
5. Reviewed against the relevant requirements.
6. Verified before proceeding.

Testing is part of implementation, not a final phase added after all features.

---

# 22. Final Architectural Position

The initial Workaholic architecture is intentionally:

```text
                         ┌─────────────┐
                         │    Web      │
                         └──────┬──────┘
                                │
                         ┌──────▼──────┐
                         │   Backend   │
                         │   Modular   │
                         │   Monolith  │
                         └──────┬──────┘
                                │
                         ┌──────▼──────┐
                         │ PostgreSQL  │
                         │   Source    │
                         │   of Truth  │
                         └──────┬──────┘
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
       ┌──────▼──────┐   ┌──────▼──────┐   ┌─────▼──────┐
       │ Background  │   │   Google    │   │  Clients   │
       │    Jobs     │   │ Integrations│   │Win/Android │
       └─────────────┘   └─────────────┘   └────────────┘
```

With deliberate future extension points for:

```text
        ┌───────────────┐
        │     Chat      │  Coming Soon
        └───────────────┘

        ┌───────────────┐
        │      AI       │  Coming Soon
        └───────────────┘
```

The guiding principle is:

> **Start simple, preserve strong boundaries, build correctly, and introduce complexity only when the product or measured scale demands it.**
