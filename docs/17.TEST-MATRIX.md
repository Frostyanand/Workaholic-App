## 1. Purpose

This document maps Workaholic requirements to the tests required to verify them.

The matrix provides traceability between:

```text
Requirement
    ↓
Feature / Domain
    ↓
Business Rule
    ↓
Implementation Surface
    ↓
Test Type
    ↓
Platform
    ↓
Test Status
````

The matrix complements `TESTING-STRATEGY.md`.

`TESTING-STRATEGY.md` defines **how** Workaholic is tested.

`TEST-MATRIX.md` defines **what must be covered**.

---

# 2. Status Definitions

Each test entry uses one of the following statuses:

| Status           | Meaning                                                |
| ---------------- | ------------------------------------------------------ |
| `PLANNED`        | Test is defined but not implemented                    |
| `IN_PROGRESS`    | Test implementation is underway                        |
| `PASSING`        | Test exists and currently passes                       |
| `BLOCKED`        | Test cannot yet run because a dependency is incomplete |
| `DEFERRED`       | Test intentionally postponed                           |
| `NOT_APPLICABLE` | Requirement does not apply to current implementation   |

A release must not treat `PLANNED` as equivalent to `PASSING`.

---

# 3. Priority Definitions

| Priority | Meaning                             |
| -------- | ----------------------------------- |
| `P0`     | Critical. Release-blocking behavior |
| `P1`     | High. Core product behavior         |
| `P2`     | Important but non-critical          |
| `P3`     | Lower-priority behavior             |

# 4. Test Type Definitions

| Code            | Test Type                             |
| --------------- | ------------------------------------- |
| `UNIT`          | Isolated deterministic logic          |
| `DOMAIN`        | Business-rule/domain behavior         |
| `DB`            | Database persistence/integrity        |
| `AUTHZ`         | Authorization/resource isolation      |
| `API`           | API endpoint behavior                 |
| `CONTRACT`      | API contract/schema compatibility     |
| `INTEGRATION`   | Multiple internal/external components |
| `E2E`           | Complete user workflow                |
| `PLATFORM`      | Web/Windows/Android-specific behavior |
| `SYNC`          | Synchronization and convergence       |
| `NOTIFICATION`  | Reminder/notification behavior        |
| `SECURITY`      | Security-specific verification        |
| `PERFORMANCE`   | Performance/resource behavior         |
| `ACCESSIBILITY` | Accessibility behavior                |
| `MIGRATION`     | Database/schema migration             |
| `RECOVERY`      | Backup/failure/recovery behavior      |
| `REGRESSION`    | Regression test for known defects     |
| `SMOKE`         | Post-deployment basic verification    |

# 35. Requirement Coverage Rule

A requirement is considered test-covered only when:

1. at least one appropriate automated or documented manual test exists;
2. the test validates the actual requirement;
3. authorization is tested where relevant;
4. failure behavior is tested where relevant;
5. the test is mapped to a stable requirement ID;
6. the test status is tracked.

A superficial test that only checks whether a page loads does not count as coverage for the underlying business requirement.

---

# 36. Platform Coverage Rule

Platform-independent domain behavior should be tested once at the shared domain/backend level wherever possible.

Platform-specific behavior must additionally be tested on the affected platform.

For example:

```text
Recurring calculation
→ shared unit/domain tests

Android alarm delivery
→ Android platform test

Windows tray reminder
→ Windows platform test
```

This avoids duplicating identical business-logic tests across every client.

---

# 37. Synchronization Coverage Rule

Any feature that can exist on multiple devices or external systems must include synchronization testing.

The minimum state model is:

```text
Server
Client A
Client B
External Provider
```

Where applicable, tests must cover changes originating from each relevant participant.

The suite must explicitly test:

```text
Create
Update
Delete
Conflict
Retry
Offline
Reconnect
Duplicate prevention
```

---

# 38. Data-Safety Coverage Rule

Any operation capable of modifying or deleting multiple resources requires explicit tests proving that unrelated resources remain unaffected.

Particular attention is required for:

* End Semester;
* project deletion;
* workspace deletion;
* calendar deletion;
* synchronization deletion;
* Drive operations;
* bulk operations.

---

# 39. Test Matrix Maintenance

The matrix must be updated whenever:

* a requirement is added;
* a requirement changes;
* a requirement is removed;
* a new platform is introduced;
* a major business rule changes;
* a defect reveals missing coverage;
* a test is removed or replaced.

Requirement IDs must remain stable unless the underlying requirement itself is intentionally replaced.

---

# 40. Final Coverage Invariant

The Workaholic test suite must maintain traceability from requirements through implementation to verification.

The minimum acceptable chain is:

```text
REQUIREMENTS.md
      ↓
Business Rule
      ↓
Implementation
      ↓
Test
      ↓
CI / Release Gate
```

No critical requirement should exist without an identifiable verification path.

The test matrix is therefore a living engineering artifact and must evolve with the product while preserving stable requirement identifiers and historical regression coverage.
