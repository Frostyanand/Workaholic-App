# Workaholic

## 1. Project Overview

Workaholic is a cross-platform personal productivity and work-management application designed to bring tasks, projects, boards, calendars, scheduling, reminders, notes, academic scheduling, collaboration, bookings, and external integrations into one coherent ecosystem.

Workaholic is personal-first in its user experience while being architecturally prepared for multi-user workspaces, collaboration, and future commercial-scale usage.

The application is designed around a simple principle:

> Workaholic should help the user understand what they need to do, when they need to do it, and what requires their attention next.

The system must remain useful without an internet connection. Cloud services primarily provide synchronization, backup, cross-device continuity, collaboration, integrations, and remote capabilities rather than being a hard dependency for ordinary application usage.

---

## 2. Product Goals

### 2.1 Primary Goals

Workaholic should:

1. Provide a unified task and work-management system.
2. Provide a powerful but understandable calendar and scheduling system.
3. Provide reliable reminders and notifications.
4. Work reliably offline for previously synchronized data and locally supported operations.
5. Synchronize user data across devices when connectivity is available.
6. Integrate with Google Calendar, Google Tasks, and Google Drive.
7. Support personal productivity as well as future collaborative workspaces.
8. Support academic scheduling, including Day Order-based schedules.
9. Provide public calendar and booking capabilities.
10. Protect user data through strong authentication, authorization, privacy, and resource isolation.
11. Preserve user ownership and portability of their data.
12. Provide a clean, modern, premium, and comfortable user experience.

---

## 3. Product Philosophy

### 3.1 Personal-First

The primary experience is designed around an individual user managing their own work and life.

Collaboration is supported without allowing collaborative features to overwhelm the personal productivity experience.

### 3.2 Offline-Capable

The client application maintains persistent local state.

The user should be able to continue performing supported operations when the internet is unavailable.

Connectivity should primarily affect synchronization and remote functionality, not basic application usability.

### 3.3 Cloud-Synchronized

The cloud provides a shared, durable representation of synchronized application state.

Multiple devices should eventually converge toward the same state through the synchronization system.

### 3.4 Scale-Ready, Not Scale-Heavy

The architecture must be capable of evolving toward thousands of users without requiring a redesign of the core domain model.

However, unnecessary infrastructure must not be introduced prematurely.

The initial system should not depend on:

- Redis
- Kafka
- Kubernetes
- Elasticsearch
- microservices
- dedicated worker fleets
- complex distributed infrastructure

These may be introduced later when actual scale, performance, or reliability requirements justify them.

### 3.5 Data Ownership

Users should not be unnecessarily locked into Workaholic.

The system should eventually provide appropriate export mechanisms and should avoid destructive behavior when integrating with external services.

### 3.6 Explicit Behavior

Important actions must have predictable and documented semantics.

The application must not silently:

- reschedule overdue tasks
- delete unrelated calendar events
- delete external Google Drive files
- destroy reusable academic schedules
- expose private calendar information
- remove historical information unnecessarily

## 5. High-Level Technology Direction

### Client

Flutter.

### Local Storage

A persistent local database will be used by clients to support offline operation.

The exact local database technology is an implementation decision to be finalized during technical architecture.

### Core Cloud Database

PostgreSQL.

The exact PostgreSQL provider is intentionally independent from the application domain model and will be selected based on reliability, cost, availability, connectivity, and operational requirements.

### Firebase

Firebase is used selectively for:

- Authentication
- Firebase Cloud Messaging
- Firestore where a document/realtime model is appropriate

Firebase is not the canonical storage location for Workaholic's core relational domain.

### Google

Workaholic integrates with:

- Google Calendar
- Google Tasks
- Google Drive

### Web Hosting

Vercel is the initial web deployment target.

### Backend

A lightweight backend/API layer will mediate access to the PostgreSQL database, Firebase administrative services, and Google APIs.

The backend will remain a modular monolith initially.

## 7. Core Product Areas

Workaholic consists of the following major product areas.

### 7.1 Tasks

Tasks are first-class actionable objects.

They support:

- title
- description
- rich text
- subtasks
- priority
- labels
- status
- due dates
- estimated duration
- scheduled work blocks
- recurrence where appropriate
- attachments
- links
- dependencies
- comments
- activity
- project relationships
- board relationships

Tasks can exist independently through an Inbox.

### 7.2 Projects

Projects organize related work.

A project may contain or relate to:

- tasks
- boards
- notes
- files
- calendar information
- people
- activity

Tasks do not require a project.

### 7.3 Boards

Boards provide customizable Kanban-style workflows.

Boards support:

- multiple custom columns
- task drag-and-drop
- filtering
- sorting
- bulk operations
- custom statuses
- project relationships

Different boards may have completely different workflow structures.

### 7.4 Calendar

Calendar is a first-class scheduling system.

It should eventually support:

- day view
- hour/time-grid view
- week view
- workweek view
- month view
- agenda view
- year view

Calendar data may originate from multiple sources.

### 7.5 Reminders

Reminders are first-class objects.

They support:

- exact-time reminders
- deadline reminders
- pre-event reminders
- recurring reminders
- snooze
- custom snooze
- attention-grabbing alarms
- shared reminders

Local reminder scheduling is required so that synchronized reminders can function without an internet connection.

### 7.6 Notes

Notes provide a central knowledge/workspace area.

They support:

- rich text
- headings
- lists
- checklists
- links
- images
- attachments
- code blocks
- tables
- tags
- search
- pinning
- favorites
- archive
- backlinks
- relationships to tasks, projects, and events

A note checkbox is not automatically a task.

Explicit conversion is required.

### 7.7 Academic Scheduling

Workaholic includes a dedicated academic scheduling subsystem supporting:

- semesters
- academic calendars
- working days
- holidays
- Day Orders
- reusable class schedules
- generated class events
- cancelled classes
- rescheduled classes
- special working days

Day Order schedules retain their reusable definitions independently of generated calendar occurrences.

### 7.8 Collaboration

Workspaces support:

- members
- roles
- granular permissions
- projects
- tasks
- assignment
- comments
- activity
- mentions
- attachments
- notifications

Chat is not part of the initial implementation.

### 7.9 Public Calendar

Users may publish a controlled public calendar.

Private events are represented as busy time without exposing private titles or details.

Public events expose only information explicitly allowed by the public-calendar rules.

Public links are revocable and regeneratable.

### 7.10 Booking

Users may expose availability through a public booking page.

Guests do not require Workaholic accounts.

Bookings support:

- availability windows
- appointment duration
- buffers
- minimum notice
- maximum booking horizon
- cancellation rules
- rescheduling
- timezone handling
- conflict prevention

Bookings automatically create calendar events.

Optional task creation may also be supported.

## 8. Google Integration

Workaholic integrates with Google's ecosystem without making Google the canonical Workaholic data model.

### Google Calendar

Two-way synchronization.

Users can select which Google calendars participate in synchronization.

### Google Tasks

Two-way synchronization.

Workaholic tasks maintain separate Workaholic IDs and Google IDs.

### Google Drive

Used for external attachment storage.

Removing an attachment relationship from Workaholic must not automatically delete the corresponding Google Drive file.

Explicit deletion from Drive is required for destructive Drive operations.

## 9. Identity and Authentication

Workaholic authentication and Google API authorization are separate concepts.

### Authentication

Answers:

> Who is this user?

Firebase Auth provides the authentication foundation.

### Authorization

Answers:

> What may this authenticated user access or modify?

Authorization is controlled by Workaholic's own permissions model.

### Google API Authorization

Separately answers:

> Has the user granted Workaholic permission to access Google Calendar, Tasks, or Drive?

Google OAuth credentials and refresh credentials must be handled through secure server-side mechanisms and must never be exposed as client-side secrets.

## 10. Offline and Synchronization Philosophy

Workaholic uses a local persistent state plus cloud synchronization model.

The device should:

1. Read and display local state immediately.
2. Apply supported changes locally.
3. Record changes that require synchronization.
4. Synchronize when connectivity is available.
5. Resolve conflicts according to documented synchronization rules.
6. Converge toward the authoritative shared state.

The application should avoid making every interaction dependent on a round trip to the cloud.

Offline support is a core product requirement, not merely a performance optimization.

## 23. Initial Infrastructure Philosophy

The initial infrastructure should remain inexpensive and simple.

The target is approximately 10–20 initial users, while maintaining architectural paths toward substantially larger usage.

The architecture should therefore use managed services where they reduce operational complexity but should avoid unnecessary distributed infrastructure.

The system should be able to evolve progressively:

```text
Initial
  ↓
More users
  ↓
Measure actual bottlenecks
  ↓
Optimize database/API
  ↓
Introduce caching if needed
  ↓
Introduce queues/workers if needed
  ↓
Introduce dedicated search if needed
  ↓
Scale individual components independently
```

Scale should be driven by evidence.

## 25. Non-Goals for the Initial Release

The initial release does not attempt to build:

* a microservice architecture
* a large-scale distributed infrastructure
* a dedicated search cluster
* an AI assistant
* built-in chat
* advanced predictive scheduling
* a complex enterprise billing system
* every possible calendar provider
* every possible platform simultaneously

The initial goal is a **reliable, polished, offline-capable productivity ecosystem with a strong core architecture**.

---

## 26. Core Architectural Principle

The most important architectural principle of Workaholic is:

> **Keep the application simple for the user and the infrastructure simple enough to operate, while keeping the internal architecture structured enough to evolve.**

The user should experience one coherent application.

Internally, the system should maintain clear boundaries between:

* local state
* synchronization
* core relational data
* authentication
* notifications
* external integrations
* future flexible/realtime data
* platform-specific functionality

This separation allows Workaholic to begin small without painting itself into a corner as the product grows.
