# 1. Purpose

This document defines the logical PostgreSQL database design for Workaholic.

It specifies:

- database domains
- table responsibilities
- primary and foreign key relationships
- ownership boundaries
- important constraints
- lifecycle representation
- synchronization metadata
- external-provider mappings
- academic scheduling representation
- reminder and notification state
- booking concurrency requirements
- indexing principles

This document intentionally defines a logical relational model rather than locking the implementation to a specific PostgreSQL hosting provider.

---

# 2. Database Authority

PostgreSQL is the authoritative datastore for core Workaholic relational domain state.

The database is authoritative for:

- Workaholic users
- workspaces
- memberships
- tasks
- projects
- boards
- calendars
- events
- reminders
- notes
- bookings
- academic scheduling
- collaboration
- trusted relationships
- integration metadata
- synchronization metadata

External systems remain authoritative for their own external objects.

---

# 3. Database Design Principles

## DB-001: Native Identity

Every persistent Workaholic entity MUST have a native primary key.

---

## DB-002: Foreign Keys

Relationships between relational entities SHOULD be represented using foreign keys.

---

## DB-003: Referential Integrity

The database SHOULD enforce relationships that can safely be enforced at the database layer.

---

## DB-004: Business Rules

Application-level business rules remain authoritative where a rule cannot be represented safely through a database constraint.

---

## DB-005: Tenant Isolation

Workspace-scoped resources MUST have sufficient ownership/context information to enforce tenant isolation.

---

## DB-006: Soft Deletion

Important recoverable resources SHOULD use explicit lifecycle fields rather than immediate physical deletion.

---

## DB-007: Timestamps

Persistent entities SHOULD retain creation and modification timestamps.

Where useful, deletion and archival timestamps SHOULD also be retained.

---

# 4. Identifier Strategy

The database SHOULD use stable opaque identifiers rather than exposing sequential business identifiers as public resource identity.

Conceptually:

```text
id
├── stable
├── unique
└── provider-independent
````

The exact identifier representation may be UUID, UUID-compatible representation, or another suitable PostgreSQL-supported strategy.

The final physical choice belongs to implementation.

## 18.3 `task_occurrences`

Represents explicit, sparse overrides and completion states for recurring task occurrences (Phase 10.13 remediation).

```text
task_occurrences
├── id (UUID, PK)
├── workspace_id (UUID, FK -> workspaces.id, CASCADE)
├── task_id (UUID, FK -> tasks.id, CASCADE)
├── occurrence_key (TEXT, nominal occurrence identifier)
├── is_all_day (BOOLEAN)
├── original_due_at (TIMESTAMPTZ, NULL for all-day)
├── original_due_date (DATE, NULL for timed)
├── override_due_at (TIMESTAMPTZ, NULL if not rescheduled or all-day)
├── override_due_date (DATE, NULL if not rescheduled or timed)
├── status (TEXT: 'TODO', 'COMPLETED', 'CANCELLED')
├── completed_at (TIMESTAMPTZ, NULL if not completed)
├── created_at (TIMESTAMPTZ)
└── updated_at (TIMESTAMPTZ)
```

Invariants:
- `(task_id, occurrence_key)` MUST be unique.
- Absence of row represents implicit dynamic nominal `TODO` occurrence.
- Master task `tasks.due_at` is baseline series anchor and is NEVER mutated by individual occurrence state transitions (satisfies **BR-TASK-008**).
- All-day occurrences maintain pure `YYYY-MM-DD` date semantics via `original_due_date` and `override_due_date`.
- Rescheduled occurrences preserve canonical `occurrence_key` and populate `override_due_at` or `override_due_date`.

# 35. Booking Concurrency

Availability queries alone MUST NOT guarantee booking uniqueness.

The authoritative database MUST enforce the no-double-booking invariant.

For mutually exclusive booking resources, the implementation SHOULD use PostgreSQL transaction/constraint mechanisms capable of preventing overlapping confirmed bookings.

A PostgreSQL exclusion constraint over an appropriate time-range representation is a preferred implementation candidate.

Conceptually:

```text
Booking A
09:00 ───────── 10:00

Booking B
09:30 ───────── 10:30

                ↓

Rejected if same resource is mutually exclusive.
```

The exact SQL implementation belongs to the physical schema.

---

# 36. Public Booking Security

Public booking endpoints MUST NOT expose:

* private event titles
* private event descriptions
* private calendar metadata
* unrelated guest information
* internal identifiers where unnecessary

Availability calculations may use private events internally.

Important tables MAY use:

```text
deleted_at
```

instead of immediately deleting rows.

Active queries SHOULD exclude soft-deleted records by default.

Restoration MUST be permission-controlled.

---

# 38. Foreign-Key Deletion Policy

Foreign keys MUST be selected carefully.

The database MUST NOT blindly use:

```text
ON DELETE CASCADE
```

for every relationship.

Cascade deletion is appropriate only where the child has no meaningful independent lifecycle.

Example candidates:

```text
role_permissions
task_labels
project_members
```

Potentially unsafe cascading:

```text
Project → Tasks
User → Tasks
Semester → Generated Events
Task → External Files
```

These require explicit lifecycle policies.

---

# 39. Unique Constraints

Important uniqueness constraints include:

```text
external_identities:
(provider, provider_subject)

workspace_memberships:
(workspace_id, user_id)

role_permissions:
(role_id, permission_id)

task_labels:
(task_id, label_id)

external_object_mappings:
(provider, external_account_id, external_object_type, external_object_id)

share_codes:
appropriate active-code uniqueness

booking page slugs:
appropriate owner/public scope
```

Additional uniqueness constraints MUST be added where domain semantics require them.

---

# 40. Check Constraints

Database-level checks SHOULD enforce simple invariants such as:

```text
event.end_at >= event.start_at

work_block.end_at > work_block.start_at

booking.end_at > booking.start_at

project.due_at >= project.start_at
when both are present

task priority ∈ supported values

known status values are valid
```

Complex workflow validation remains in application logic.

---

# 41. Indexing Strategy

Indexes SHOULD prioritize:

* workspace ownership
* user ownership
* foreign keys
* task status
* task due date
* task project
* task board/column
* calendar/date ranges
* event time ranges
* reminder trigger times
* notification recipient/state
* synchronization state
* external mappings
* booking availability
* academic calendar dates
* Day Order assignments
* public-link lookup

Indexes MUST be added based on actual query patterns rather than indiscriminately indexing every column.

---

# 42. Calendar Indexing

Calendar/event queries will frequently filter by:

```text
calendar_id
start_at
end_at
```

The database design SHOULD support efficient range queries.

PostgreSQL range types and GiST indexes MAY be used where beneficial.

---

# 43. Reminder Indexing

Reminder processing will frequently require:

```text
next_trigger_at <= current_time
status = ACTIVE
```

Appropriate indexes MUST support efficient retrieval of due reminders.

---

# 44. Synchronization Indexing

Synchronization operations will frequently query:

```text
user_id
device_id
status
created_at
entity_id
```

External mappings will frequently query:

```text
provider
external_account_id
external_object_type
external_object_id
```

---

# 45. Academic Scheduling Indexing

Important access patterns include:

```text
semester_id
calendar_date
day_order
class_schedule_id
```

The database SHOULD efficiently retrieve:

* Day Order for a date
* dates for a Day Order
* schedule entries for a Day Order
* generated events for a Semester
* future events generated by a Semester

# 47. Authorization Context

Every protected query MUST be capable of determining the authorization context.

Preferred conceptual pattern:

```text
resource
   ↓
workspace_id / owner_user_id
   ↓
membership / ownership
   ↓
permission
```

The implementation MUST NOT depend solely on the client supplying a workspace ID correctly.

---

# 48. Row-Level Security

If PostgreSQL deployment architecture supports Row-Level Security appropriately, RLS MAY be used as an additional defense-in-depth mechanism.

RLS MUST NOT be treated as a substitute for application authorization design.

The exact RLS strategy is deferred to security/deployment implementation.

---

# 49. Versioning and Concurrency

Core mutable entities SHOULD support a mechanism for detecting stale writes.

Potential approaches include:

```text
version number
updated_at comparison
ETag/version token
```

The selected approach MUST support offline synchronization and concurrent device edits.

---

# 50. JSON / Flexible Fields

JSONB MAY be used for genuinely flexible or provider-specific data.

It SHOULD NOT replace relational structure for core entities with known relationships.

Good candidates:

```text
provider metadata
notification payload metadata
activity metadata
integration-specific configuration
```

Poor candidates:

```text
tasks
users
workspace membership
booking relationships
task dependencies
calendar ownership
```

---

# 51. External Provider Metadata

Provider-specific information SHOULD be isolated from core relational fields where possible.

Example:

```text
Native Event
    ↓
External Mapping
    ↓
Google metadata
```

This prevents Google-specific fields from contaminating the native event model.

---

# 52. Database Transaction Requirements

Transactions MUST be used for operations where partial persistence would violate business rules.

Examples:

```text
booking confirmation

workspace membership changes

permission changes

critical task state transitions

synchronized mutation application

semester termination

academic schedule regeneration
```

Transaction boundaries MUST remain appropriately scoped.

---

# 53. Semester Termination Transaction

Ending a Semester is a multi-step operation.

Conceptually:

```text
BEGIN
    ↓
Validate user permission
    ↓
Lock/validate Semester state
    ↓
Mark Semester ended
    ↓
Identify future generated events
    ↓
Deactivate/remove applicable occurrences
    ↓
Preserve reusable schedules
    ↓
COMMIT
```

Failure before commit MUST NOT leave the system in a partially transitioned semester state.

---

# 54. Academic Recalculation Transaction

Where a calendar change affects Day Order assignments:

```text
BEGIN
    ↓
Update academic calendar
    ↓
Recalculate affected assignments
    ↓
Update generated academic occurrences
    ↓
COMMIT
```

The exact recalculation strategy may use asynchronous processing for large schedules, provided the system exposes a coherent state transition.

---

# 55. Booking Transaction

Conceptually:

```text
BEGIN
    ↓
Validate booking rules
    ↓
Check authoritative conflicts
    ↓
Insert/confirm booking
    ↓
Create/update associated records
    ↓
COMMIT
```

The final conflict check MUST occur inside the authoritative transaction boundary.

---

# 56. Integration Data Isolation

Disconnecting an integration SHOULD update:

```text
integrations
external_accounts
external_object_mappings
```

without deleting:

```text
native Tasks
native Events
native Notes
native Projects
native Attachments
```

unless a separate explicit deletion operation exists.

---

# 57. Backup and Recovery

PostgreSQL data MUST be backed up according to the production backup strategy.

The backup strategy MUST consider:

* point-in-time recovery where supported
* retention
* restoration testing
* disaster recovery
* accidental deletion
* corruption
* provider failure

A backup that has never been restored/tested MUST NOT be assumed reliable.

---

# 58. Migration Strategy

Database changes MUST be performed through version-controlled migrations.

Migrations MUST:

* be deterministic
* be reviewable
* preserve production data
* account for existing rows
* support rollback where practical
* be tested before production execution

Destructive migrations require explicit review.

---

# 59. Seed Data

System-level seed data MAY include:

* default roles
* permissions
* default statuses
* default priorities
* supported notification types

Seed data MUST be distinguishable from user-owned data.

---

# 60. Database Performance Principles

Initial optimization priorities:

```text
Correct schema
    ↓
Correct constraints
    ↓
Correct indexes
    ↓
Query analysis
    ↓
Pagination
    ↓
Selective optimization
```

Premature partitioning, sharding, caching, or denormalization SHOULD NOT be introduced without evidence.

---

# 61. Pagination

Large collections SHOULD use pagination.

Potential collections include:

* tasks
* projects
* notes
* activity
* comments
* notifications
* events
* synchronization operations

The API layer will define the externally visible pagination contract.

---

# 62. Auditability

Security-sensitive changes SHOULD retain sufficient database/application records to determine:

```textwho
what
when
target
result
```

Activity history and security audit history SHOULD remain conceptually distinct where their retention requirements differ.

---

# 63. Database Security

The database layer MUST:

* require authenticated backend access
* use encrypted transport where supported
* restrict credentials
* avoid exposing direct database credentials to clients
* use least-privilege database accounts where practical
* protect backups
* rotate secrets according to security policy

Clients MUST NEVER connect directly to PostgreSQL using privileged application credentials.

---

# 64. Client Database Separation

Client-local databases are separate from the authoritative PostgreSQL database.

```text
Client Local DB
       ↕
Synchronization
       ↕
PostgreSQL
```

A local database MUST NOT be interpreted as an independent authoritative server database.

---

# 65. Database and Firebase Separation

Firebase Auth and FCM remain external platform services.

Core Workaholic relational data MUST NOT be duplicated into Firestore merely to avoid accessing PostgreSQL.

Firestore may be introduced for future workloads that genuinely benefit from a document/realtime model.
