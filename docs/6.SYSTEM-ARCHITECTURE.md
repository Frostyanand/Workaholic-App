````markdown
# 1. Purpose

This document defines the logical architecture of Workaholic.

It specifies:

- application boundaries
- client architecture
- backend architecture
- data ownership
- external service boundaries
- synchronization boundaries
- background processing
- notification architecture
- deployment responsibilities
- security boundaries
- architectural constraints
- scalability strategy

This document defines architecture, not implementation-level database schema or individual API contracts.

---

# 2. Architectural Goals

Workaholic MUST be:

1. Cross-platform.
2. Offline-capable where supported.
3. Cloud-synchronized.
4. Secure.
5. Multi-tenant capable.
6. Scale-ready without premature infrastructure complexity.
7. Modular internally.
8. Maintainable by a small development team.
9. Capable of integrating with external services.
10. Capable of supporting future Chat and AI functionality without architectural replacement.

---

# 3. Architectural Philosophy

The initial architecture follows:

```text
Simple infrastructure
        +
Strong domain boundaries
        +
Explicit synchronization
        +
Clear ownership
        +
Expandable modules
````

The system MUST NOT introduce distributed infrastructure merely because the product may eventually scale.

Initial architecture SHOULD avoid unnecessary:

* microservices
* Kubernetes
* Kafka
* Redis
* Elasticsearch
* dedicated worker fleets
* service meshes
* complex event buses

These MAY be introduced later when actual requirements justify them.

# 5. Client Architecture

Workaholic SHOULD use a shared Flutter codebase for:

* Web
* Windows
* Android

The same domain semantics SHOULD be shared across platforms.

Platform-specific capabilities MAY be implemented behind platform abstractions.

---

# 6. Client Layer Responsibilities

The client is responsible for:

* presentation
* user interaction
* local persistence
* local synchronization queue
* local reminder scheduling
* local validation
* optimistic UI where appropriate
* notification interaction
* platform integration
* rendering synchronized state

The client MUST NOT be treated as the authoritative security boundary.

---

# 7. Client Local Data

Each supported client SHOULD maintain persistent local state.

Conceptually:

```text
Client
│
├── Local Database
│
├── Local Domain State
│
├── Pending Mutations
│
├── Synchronization Metadata
│
├── Reminder Schedule
│
└── Cached Presentation State
```

The exact local database technology is intentionally deferred to the technical design phase.

---

# 8. Offline-First Interaction Model

The client follows:

```text
User Action
    ↓
Local Validation
    ↓
Local Persistence
    ↓
UI Update
    ↓
Queue Mutation
    ↓
Cloud Synchronization
```

The client SHOULD NOT require a successful network round trip before displaying a successfully persisted local mutation when offline support applies.

---

# 9. Backend Architecture

The initial backend MUST use a modular monolith architecture.

Conceptually:

```text
Backend
│
├── Identity
├── Users
├── Workspaces
├── Tasks
├── Boards
├── Projects
├── Calendar
├── Scheduling
├── Academic Scheduling
├── Reminders
├── Notifications
├── Notes
├── Files
├── Bookings
├── Sharing
├── Collaboration
├── Integrations
├── Synchronization
├── Search
└── Administration
```

These modules exist as logical boundaries within one deployable backend.

---

# 10. Why Modular Monolith

A modular monolith provides:

* low operational complexity
* straightforward local development
* simpler transactions
* simpler deployment
* clear domain boundaries
* easier debugging
* lower infrastructure cost

It also leaves the system structurally prepared for future extraction of individual modules if scale requires it.

---

# 11. Backend Module Independence

Modules MUST avoid unnecessary direct coupling.

For example:

```text
Tasks
   ↓
may reference
   ↓
Reminders
```

but Tasks SHOULD NOT directly manipulate notification transport internals.

Instead:

```text
Task Module
    ↓
Reminder Domain
    ↓
Notification Module
    ↓
Delivery Provider
```

# 12. Core Data Architecture

PostgreSQL is the authoritative datastore for core relational Workaholic domain data.

Examples include:

* users/domain profiles
* workspaces
* memberships
* tasks
* projects
* boards
* calendar metadata
* events
* reminders
* notes
* bookings
* academic schedules
* synchronization metadata
* collaboration metadata

The exact PostgreSQL provider remains an infrastructure decision.

---

# 13. Firebase Architecture

Firebase is used selectively.

Initial responsibilities:

```text
Firebase
├── Authentication
└── Firebase Cloud Messaging
```

Firestore MAY be used for future flexible/realtime functionality, particularly:

* Chat
* realtime collaboration state
* presence
* ephemeral state

Firebase MUST NOT become the default datastore for the core relational domain merely for convenience.

---

# 14. Authentication Architecture

Authentication authority:

```text
Firebase Authentication
```

Domain identity:

```text
Workaholic User
```

The relationship is:

```text
Firebase Auth Identity
        ↓
External/Auth Identity Mapping
        ↓
Workaholic User
```

This separation allows Workaholic to maintain its own domain identity independently of the authentication provider.

---

# 15. Authorization Architecture

Authorization is enforced by the backend.

Conceptually:

```text
Request
   ↓
Authenticate
   ↓
Resolve Workaholic User
   ↓
Resolve Workspace / Resource
   ↓
Evaluate Membership
   ↓
Evaluate Role
   ↓
Evaluate Fine-Grained Permission
   ↓
Allow / Reject
```

The client MUST NOT be the final authority for authorization.

---

# 16. Workspace Isolation

The backend MUST enforce tenant/resource isolation.

Conceptually:

```text
Request
    ↓
User
    ↓
Workspace Membership
    ↓
Requested Resource
    ↓
Verify Resource Belongs to Authorized Context
```

A valid user session alone MUST NOT grant access to another workspace's data.

---

# 17. External Integration Boundary

External services MUST be accessed through integration modules.

```text
Workaholic
    │
    ├── Google Calendar Adapter
    ├── Google Tasks Adapter
    └── Google Drive Adapter
```

Domain modules SHOULD NOT contain provider-specific API logic throughout their code.

---

# 18. Google Integration Architecture

```text
                 Workaholic Backend
                        │
                Integration Layer
                        │
             ┌──────────┼──────────┐
             ▼          ▼          ▼
        Calendar      Tasks       Drive
             │          │          │
             └──────────┼──────────┘
                        ▼
                    Google APIs
```

Provider-specific models SHOULD be translated into internal domain representations.

---

# 19. OAuth Credential Boundary

Sensitive credentials remain server-side.

Conceptually:

```text
Client
   │
   │ OAuth authorization
   ▼
Google
   │
   ▼
Backend
   │
   └── Secure credential storage
```

The client MUST NOT contain:

* Google client secrets
* server credentials
* database credentials
* encryption keys
* long-lived server-side refresh credentials

---

# 20. External Object Mapping

Synchronization requires explicit mappings.

```text
Native Workaholic Object
          ↕
External Object Mapping
          ↕
Google Object
```

This prevents provider identifiers from becoming native domain identities.

# 21. Synchronization Architecture

Synchronization is a first-class subsystem.

```text
                 ┌───────────────────────┐
                 │     Cloud State       │
                 └───────────┬───────────┘
                             │
                     Synchronization
                             │
            ┌────────────────┼────────────────┐
            ▼                ▼                ▼
         Windows          Android            Web
```

The same synchronization architecture also interfaces with external providers.

---

# 22. Synchronization Responsibilities

The synchronization subsystem handles:

* local mutations
* mutation queues
* upload
* download
* version tracking
* idempotency
* retry
* conflict detection
* conflict resolution
* external synchronization
* deletion detection
* synchronization failures

Detailed algorithms belong to `SYNC-SPECIFICATION.md`.

---

# 23. Local Mutation Queue

Offline-capable clients maintain a queue conceptually equivalent to:

```text
Pending Mutation
│
├── Mutation ID
├── Entity
├── Operation
├── Payload
├── Base Version
├── Created Time
└── Sync State
```

This is a technical synchronization representation, not a replacement for the domain entity.

---

# 24. Synchronization Flow

```text
Local Change
    ↓
Persist
    ↓
Create Mutation
    ↓
Queue
    ↓
Network Available?
   /        \
 No          Yes
 ↓            ↓
Wait       Submit
              ↓
        Server Validation
              ↓
        Apply / Conflict
              ↓
        Return Canonical State
              ↓
        Update Client
```

---

# 25. Idempotency

Operations that may be retried MUST be safely repeatable where duplicate execution could cause incorrect results.

Important candidates include:

* synchronization mutations
* booking confirmation
* external API writes
* notification jobs
* background processing

---

# 26. Conflict Architecture

Conflicts are handled at the synchronization boundary.

```text
Device A
   │
   ├── Change A
   │
   ▼
Cloud
   ▲
   │
   └── Change B
       Device B
```

The server or synchronization subsystem determines whether:

* changes can merge
* one change supersedes another
* user resolution is required

Conflict behavior MUST be explicitly defined in `SYNC-SPECIFICATION.md`.

The calendar subsystem handles:

* native calendars
* external calendars
* events
* recurrence
* event exceptions
* visibility
* calendar sources

* calendar relationships

Conceptually:

```text
Calendar
│
├── Native Events
├── External Events
```

# 28. Academic Scheduling Architecture

Academic scheduling is a dedicated domain subsystem.

```text
Semester
    ↓
Academic Calendar
    ↓
Working/Non-working Dates
    ↓
Day Order Sequence
    ↓
Class Schedule
    ↓
Schedule Entries
    ↓
Generated Academic Events
```

The scheduling engine MUST NOT treat Day Order as a simple weekday calculation.

---

# 29. Academic Event Provenance

Generated events MUST retain provenance.

```text
Generated Event
│
├── Source = DAY_ORDER
├── Semester
├── Schedule
├── Day Order
└── Schedule Entry
```

This allows targeted regeneration and semester termination.

---

# 30. Semester Termination Architecture

```text
End Semester
      ↓
Mark Semester Ended
      ↓
Identify future generated events
      ↓
Deactivate/remove affected occurrences
      ↓
Preserve historical occurrences
      ↓
Preserve reusable schedule
      ↓
Preserve unrelated events
```

This operation MUST operate using source/provenance boundaries.

---

# 31. Reminder Architecture

Reminder processing consists of:

```text
Reminder Definition
       ↓
Trigger Evaluation
       ↓
Recipient Resolution
       ↓
Notification
       ↓
Delivery
```

Reminder logic MUST remain independent of notification transport.

---

# 32. Local Reminder Scheduler

Supported clients SHOULD maintain a local reminder scheduler.

```text
Local Reminder
      ↓
Local Scheduler
      ↓
Platform Notification
```

This permits supported reminders to function while the device is offline.

---

# 33. Cloud Reminder Processing

Cloud/background processing MAY be used for:

* server-side reminder evaluation
* shared reminders
* cross-device notification coordination
* notification generation
* retry
* recurring reminder processing

The cloud processor MUST NOT assume that a push notification is the only reminder mechanism.

---

# 34. Firebase Cloud Messaging

FCM is a notification transport mechanism.

It is NOT:

* the reminder engine
* the authoritative reminder datastore
* the synchronization system

Conceptually:

```text
Reminder Engine
      ↓
Notification
      ↓
FCM
      ↓
Android / Web
```

Windows may use platform-specific notification mechanisms.

---

# 35. Background Jobs

Initial background processing SHOULD use managed/scheduled infrastructure rather than a dedicated worker fleet.

Jobs may include:

* recurring event processing
* reminder processing
* Google synchronization
* Drive operations
* booking notifications
* cleanup
* indexing
* analytics processing

---

# 36. Job Requirements

Background jobs MUST be:

* retry-safe
* observable
* idempotent where appropriate
* failure-tolerant
* scoped
* auditable where security-sensitive

A failed background job MUST NOT silently corrupt domain state.

---

# 37. Booking Architecture

Booking requires authoritative concurrency control.

```text
Public Booking Request
        ↓
Availability Calculation
        ↓
Final Availability Check
        ↓
Atomic Confirmation
        ↓
Booking Created
        ↓
Optional Calendar Event
```

The authoritative database MUST prevent double booking.

---

# 38. Public Calendar Architecture

Public calendar access is implemented as a restricted projection.

```text
Private Calendar State
        ↓
Visibility Evaluation
        ↓
Privacy Filter
        ↓
Public Calendar Projection
        ↓
Public Link
```

The public endpoint MUST NOT expose unrestricted calendar records.

---

# 39. Trusted Sharing Architecture

Trusted access is represented as an explicit authorization relationship.

```text
Owner
  │
  └── Trusted Relationship
          │
          ├── Trusted User
          ├── Permissions
          └── Status
```

Share codes are onboarding mechanisms, not permanent authentication credentials.

---

# 40. Device and Session Architecture

```text
User

├── Devices
│    ├── Windows
│    ├── Android
│    └── Web
│
└── Sessions
     ├── Active
     ├── Expired
     └── Revoked
```

Session revocation MUST be enforced by the authorization layer.

# 41. Notes Architecture

Notes are part of the core relational domain initially.

They may reference:

* Tasks
* Projects
* Events
* People
* Files

Future realtime/collaborative note functionality MAY use additional infrastructure without changing Note domain identity.

---

# 42. File Architecture

Files are external-storage-aware.

```text
Workaholic
    │
    └── Attachment
           │
           ▼
      Google Drive
```

Workaholic stores the relationship and required external metadata.

Google Drive remains the storage authority for the external file.

# 43. Search Architecture

Initial search SHOULD use PostgreSQL/native database capabilities where sufficient.

```text

    ↓
Database Search

Authorization Filter
    ↓
Results
```

A dedicated search engine is not required initially.

Elasticsearch/OpenSearch or another search infrastructure MAY be introduced if real-world scale or search requirements justify it.

---

# 44. Collaboration Architecture

Initial collaboration remains within the modular monolith.

```text
Workspace
│
├── Members
├── Projects
├── Tasks
├── Comments
├── Activity
└── Notifications
```

Future realtime functionality MAY use Firebase/Firestore.

# 45. Chat Architecture

When implemented:

```text
Client
   ↓
Chat Module
   ↓
Realtime / Flexible Data Layer
   ↓
Conversation / Messages
```

Firestore MAY be used for realtime chat data.

# 46. AI Architecture

AI is explicitly deferred.

Future architecture SHOULD follow:

```text

 ↓
AI Assistant
 ↓
Intent / Planning
 ↓
Controlled Application Tool
 ↓
Authorization
 ↓

 ↓
```

# 47. API Boundary

Clients interact with the backend through an authenticated API.

Conceptually:

```text
Flutter Client
      ↓
API
      ↓
Application Module
      ↓
Domain Rules
      ↓
Persistence
```

The API MUST NOT bypass business rules.

---

# 48. Domain/Application/Persistence Separation

Backend modules SHOULD conceptually separate:

```text
API / Transport
       ↓
Application Services
       ↓
Domain Logic
       ↓
Persistence
```

External providers SHOULD be accessed through adapters.

This prevents provider-specific behavior from leaking throughout the application.

---

# 49. Transaction Boundaries

Database transactions MUST be used when multiple changes form one atomic business operation.

Examples:

* booking confirmation
* permission changes
* critical state transitions
* synchronized mutation application
* resource creation requiring multiple related records

Transactions MUST NOT be used merely for unrelated operations.

---

# 50. Data Consistency Strategy

PostgreSQL provides authoritative consistency for core relational state.

The system distinguishes:

```text
Strong transactional consistency
        ↓
Core database operation

Eventual consistency
        ↓
Cross-device synchronization

External consistency
        ↓
Google / other providers
```

External APIs MUST NOT be assumed to provide the same transactional guarantees as PostgreSQL.

---

# 51. External API Failure Boundary

A Google API failure MUST NOT invalidate an already valid native Workaholic transaction unless the business operation explicitly depends on successful external completion.

Example:

```text
Create native Task
      ↓
Success
      ↓
Google synchronization fails
      ↓
Task remains valid
      ↓
Sync retry
```

# 60. Rate Limiting

Rate limiting SHOULD be applied to:

* authentication-sensitive endpoints
* public booking endpoints
* public calendar endpoints
* public share/onboarding endpoints
* expensive search operations
* integration endpoints

Limits SHOULD account for legitimate application behavior.

# 61. Scalability Strategy

The architecture is scale-ready through structure rather than premature infrastructure.

Initial:

```text
Modular Monolith
      +
PostgreSQL
      +
Managed Jobs
      +
Firebase Auth/FCM
```

If scale increases:

```text
Optimize DB
      ↓
Add caching where justified
      ↓
Separate expensive jobs
      ↓
Add queues where justified
      ↓
Scale backend horizontally
      ↓
Extract services only where justified
```

No infrastructure component should be introduced without a demonstrated requirement.

---

# 62. Horizontal Scaling

The backend SHOULD be designed so that multiple application instances can eventually run concurrently.

Therefore:

* important state MUST reside in shared authoritative infrastructure
* local server memory MUST NOT be treated as durable state
* sessions requiring shared validation MUST not depend solely on process memory
* background processing MUST be safe across multiple instances

---

# 63. Caching Strategy

Caching is intentionally deferred.

Initial system:

```text
Request
  ↓
Authoritative Data
```

Caching MAY later be introduced for:

* read-heavy data
* public calendar projections
* frequently accessed metadata
* external API responses
* expensive derived computations

Caching MUST NOT become an unintended source of truth.

---

# 64. Queue Strategy

No dedicated message broker is required initially.

Managed/background mechanisms are sufficient for initial workloads.

A queue system MAY later be introduced for:

* high-volume synchronization
* notification delivery
* external integration jobs
* large-scale background processing

---

# 65. Database Strategy

PostgreSQL is selected as the core relational model because Workaholic requires strong relationships and transactional behavior across:

* tasks
* projects
* boards
* calendars
* bookings
* academic scheduling
* reminders
* permissions
* synchronization mappings

The exact schema is defined in `DATABASE-DESIGN.md`.

---

# 66. Firebase Boundary

Firebase SHOULD remain deliberately narrow.

Initial responsibilities:

```text
Firebase Auth
FCM
```

Future:

```text
Firestore
    ↓
Chat / realtime / flexible data
```

Core Workaholic relational state SHOULD remain in PostgreSQL.

---

# 67. Provider Independence

Where practical, provider-specific infrastructure SHOULD be abstracted.

Examples:

```text
Authentication Provider
Storage Provider
Calendar Provider
Notification Provider
```

This does not require implementing multiple providers immediately.

The goal is to avoid coupling the entire domain model to one provider's data model.

---

# 68. Architecture for Future Platform Expansion

The architecture permits future:

* iOS
* macOS
* tablets
* additional web clients

without changing the authoritative backend domain model.

A new client should implement:

```text
Presentation
Local State
Synchronization
Platform Capabilities
```

against the existing backend/domain contracts.

---

# 69. Architecture for Future AI

AI should be an application-layer consumer.

It should interact with:

```text
Application Actions
```

rather than:

```text
Database
```

Example:

```text
AI:
"Move my meeting to the first free hour tomorrow."

        ↓

Find Free Slot Tool
        ↓
Calendar Rules
        ↓
Authorization
        ↓
Conflict Validation
        ↓
Update Event
```

This architecture allows AI to be replaced or improved without changing the core domain.

---

# 70. Architecture for Future Chat

Chat can be added as a separate logical module.

Potential future architecture:

```text
Core Backend
     │
     ├── Core relational domain
     │
     └── Chat boundary
             ↓
          Firestore
```

Chat MUST NOT require moving existing Tasks, Projects, Calendar, or Notes into Firestore.

---

# 71. Failure Isolation

Failures SHOULD remain localized.

Examples:

```text
Google API outage
    ↓
Google synchronization affected
    ↓
Native Workaholic usage continues

FCM outage
    ↓
Push notifications affected
    ↓
Local reminders remain where supported

Search failure
    ↓
Search affected
    ↓
Direct resource access continues
```

A non-critical auxiliary service failure MUST NOT unnecessarily disable the core application.

---

# 72. Architecture Decision Principles

When evaluating new infrastructure, the following order SHOULD be used:

```text
1. Can PostgreSQL solve it?
2. Can the modular monolith solve it?
3. Can managed platform functionality solve it?
4. Is a dedicated service actually necessary?
5. Does the operational cost justify it?
6. Does the added complexity solve a demonstrated problem?
```
