**Status:** FINAL

**Product:** Workaholic
**Scope:** Privacy, application security, data protection, secrets, sessions, authorization enforcement, external integrations, public access, logging, backups, and security operations

## 1. Purpose

This document defines the security and privacy requirements for Workaholic.

Security MUST be treated as a cross-cutting property of the entire system rather than as a separate feature.

The system handles potentially sensitive information including:

* Tasks
* Calendar events
* Academic schedules
* Notes
* Attachments
* Projects
* Collaboration data
* Trusted relationships
* Booking information
* External integration credentials
* Notification content
* Session/device information

The system MUST therefore enforce strong isolation between users, workspaces, resources, devices, and external providers.

---

# 2. Core Security Principles

Workaholic MUST follow:

1. **Least privilege**
2. **Deny by default**
3. **Server-side authorization**
4. **Defense in depth**
5. **Secure defaults**
6. **Data minimization**
7. **Explicit consent**
8. **Credential separation**
9. **Auditability**
10. **Safe failure**
11. **No silent destructive operations**
12. **User data ownership and portability**

---

# 3. Security Boundaries

The primary security boundaries are:

```text id="k8f5x1"
Identity
   ↓
Workaholic Account
   ↓
Workspace
   ↓
Resource
   ↓
Operation
```

Additional boundaries:

```text id="8s9l3x"
Workaholic ↔ Google
Workaholic ↔ Public Internet
Workaholic ↔ Trusted Users
Workaholic ↔ Booking Guests
Workaholic ↔ Client Devices
```

Each boundary MUST have explicit authorization rules.

---

# 4. Authentication

Authentication establishes the identity of the user.

Workaholic MUST use an established authentication mechanism rather than implementing custom password cryptography unnecessarily.

Google authentication MAY be used.

The application MUST distinguish:

```text id="1d5b2e"
Authentication
```

from:

```text id="8a7f2c"
Google API authorization
```

---

# 5. Authentication Provider

If Google authentication is used:

```text id="2j6k3m"
Google
   ↓
Identity verification
   ↓
Workaholic account
```

Google's successful authentication MUST NOT automatically determine Workaholic workspace permissions.

---

# 6. External OAuth Authorization

Google API access MUST use a separate authorization flow.

Example:

```text id="8y4h7n"
User authenticated
        ↓
Workaholic account active
        ↓
User chooses "Connect Google Calendar"
        ↓
Google authorization
        ↓
Granted scopes
        ↓
Encrypted server-side credential storage
```

The system MUST request only the scopes required for the enabled functionality.

---

# 7. Credential Storage

Long-lived external credentials such as OAuth refresh tokens MUST NOT be stored in:

* Client source code
* Flutter application binaries
* Browser local storage where avoidable
* Git repositories
* Public configuration
* Logs

They MUST be stored server-side using appropriate secret protection/encryption.

---

# 8. Client Secrets

Secrets that require confidentiality MUST NOT be embedded in:

* Flutter Web
* Android application
* Windows application
* JavaScript bundles
* Public repositories

Anything shipped to a client MUST be considered potentially discoverable by the user.

---

# 9. Transport Security

All production network communication MUST use encrypted transport.

Production application traffic SHOULD use HTTPS/TLS.

The system MUST NOT transmit:

* Authentication credentials
* OAuth credentials
* Sensitive task/note data
* Session credentials

over unencrypted production HTTP.

---

# 10. API Security

Every protected API request MUST establish:

```text id="7sqv6r"
Who is calling?
        ↓
Is the session valid?
        ↓
What workspace/resource?
        ↓
What action?
        ↓
Is the action permitted?
```

The API MUST NOT rely solely on client-side route protection.

---

# 11. Authorization

Authorization requirements are defined in `PERMISSIONS-MODEL.md`.

Security-sensitive implementation MUST assume:

> **Any client can be modified or compromised.**

Therefore:

```text id="2xw0mq"
UI restriction
≠
Security control
```

---

# 12. Multi-Tenant Isolation

Workspace isolation is mandatory.

A query for resources MUST be constrained by the authorized workspace/resource scope.

Conceptually:

```text id="y3f2k8"
SELECT resource
WHERE resource.id = requested_id
AND resource.workspace_id IN authorized_workspaces
```

The exact implementation MAY differ, but equivalent isolation MUST exist.

---

# 13. Direct Object Access

Resource IDs MUST NOT act as authorization credentials.

For example:

```text id="w4k7p2"
GET /tasks/abc
```

must still perform authorization.

Knowing:

```text id="3f9c1a"
abc
```

does not grant access.

---

# 14. Database Security

The database MUST enforce appropriate integrity constraints.

Where supported and useful, database-level policies SHOULD provide an additional security boundary.

Application authorization remains mandatory.

The system MUST NOT rely on database constraints alone to model all authorization decisions.

---

# 15. Input Validation

All externally supplied input MUST be validated.

This includes:

* API parameters
* JSON payloads
* Search queries
* Task content
* Notes
* Calendar data
* Booking information
* File metadata
* Share codes
* Public-link parameters
* OAuth callback data

Validation MUST occur server-side.

---

# 16. Output Validation

Responses MUST expose only fields the requesting principal is authorized to receive.

The system MUST avoid returning complete database records by default when only a subset is required.

This is especially important for:

* Private events
* Trusted relationships
* Session data
* OAuth records
* Internal activity metadata

---

# 17. Injection Protection

The application MUST protect against injection vulnerabilities, including:

* SQL injection
* Command injection
* HTML injection
* Script injection
* Template injection
* Provider-specific injection risks

Parameterized database queries or equivalent safe abstractions MUST be used.

---

# 18. Cross-Site Scripting

User-generated content may contain arbitrary text.

The system MUST safely handle content such as:

```text id="b2k3j1"
Task title
Note body
Comment
Project description
Calendar description
```

Rich-text rendering MUST sanitize unsafe HTML/content according to the chosen representation.

---

# 19. Rich Text Security

Rich text MUST NOT automatically permit arbitrary executable content.

Potentially dangerous content such as:

```text id="x3v8n4"
<script>
javascript:
unsafe embedded HTML
```

must be sanitized or rejected.

Links SHOULD be validated and rendered safely.

---

# 20. File Upload Security

Attachments introduce additional attack surface.

The system MUST validate:

* File size
* File type
* File metadata
* Upload authorization
* Association with parent resource

Where files are processed locally or server-side, content-type validation MUST NOT rely solely on a user-supplied MIME type.

---

# 21. Google Drive Attachments

For Drive-backed attachments:

```text id="9h4s1v"
Workaholic Attachment
        ↓
External Drive File
```

Removing an attachment relationship MUST NOT automatically delete the underlying Drive file.

Explicit deletion from Drive requires an authorized operation.

---

# 22. File Access

A user MUST NOT gain access to an attachment by bypassing the parent resource authorization.

For example:

```text id="c8q3m1"
Private Task
   ↓
Attachment
```

The attachment cannot become publicly readable merely because its URL is known.

---

# 23. Public Calendar Security

Public calendar access MUST use a dedicated public access mechanism.

The system MUST NOT expose an authenticated calendar API directly through a public URL.

---

# 24. Public Link Tokens

Public calendar links MUST use unpredictable tokens.

Tokens SHOULD have sufficient entropy to make guessing impractical.

Public tokens MUST NOT contain easily derivable information such as:

```text id="5m8n2x"
user_id
calendar_id
incrementing integer
```

---

# 25. Public Link Revocation

Users MUST be able to revoke a public calendar link.

Revocation MUST be server-authoritative.

After revocation:

```text id="x7p4c2"
Old token
   ↓
Rejected
```

A client cache MUST NOT continue exposing current public data indefinitely.

---

# 26. Public Calendar Privacy

The public projection MUST be generated from explicitly allowed fields.

Private event:

```text id="r3v9j2"
Title:
Private Meeting

Public:
Busy
10:00 → 11:00
```

The system MUST NOT leak private information through:

* Event titles
* URLs
* HTML
* JSON metadata
* Calendar filenames
* Debug fields
* Related resource IDs

---

# 27. Booking Guest Security

Unauthenticated booking guests MUST have access only to the intended booking workflow.

They MUST NOT gain:

* Workspace access
* Calendar access
* Task access
* Note access
* Project access

through booking APIs.

---

# 28. Booking Abuse Protection

Public booking endpoints SHOULD use:

* Rate limiting
* Validation
* Abuse detection
* Appropriate CAPTCHA/challenge mechanisms where justified
* Request throttling

The system MUST prevent automated booking spam from becoming an operational vulnerability.

---

# 29. Trusted Relationship Security

Trusted sharing is an explicit access relationship.

It MUST NOT bypass:

* Authentication
* Authorization
* Session management
* Revocation
* Resource-level access rules

---

# 30. Share Code Security

Share codes MUST be treated as temporary onboarding credentials.

They SHOULD be:

* Short-lived
* Random
* Rate-limited
* Single-use where practical
* Invalidated after successful redemption

The system MUST NOT treat an old share code as a permanent password.

---

# 31. Session Security

Sessions MUST be:

* Uniquely identifiable
* Revocable
* Expirable where applicable
* Bound to an authenticated identity
* Invalidated when required

The server MUST reject expired/revoked sessions.

---

# 32. Session Revocation

Users SHOULD be able to revoke:

```text id="c4j1m9"
Individual session
```

and:

```text id="n8s2v5"
All other sessions
```

Revocation MUST take effect for subsequent protected requests.

---

# 33. Device Security

Devices MAY be remembered as trusted devices.

However:

```text id="p2f7k1"
Trusted device
≠
Permanent unrestricted access
```

Users MUST be able to revoke device/session access.

---

# 34. Local Client Storage

Clients may maintain local application data for offline operation.

Local storage SHOULD minimize sensitive information.

Sensitive credentials MUST NOT be stored in plaintext where secure platform storage is available.

Examples:

* Android secure storage
* Windows protected credential storage
* Browser-appropriate secure mechanisms

---

# 35. Offline Data

Offline data introduces a special security consideration.

If a user loses authorization while a device is offline:

```text id="m4v9q1"
Server:
Access revoked

Device:
Offline
```

the device may temporarily retain cached data.

Upon reconnection, authorization MUST be revalidated and protected data MUST be reconciled appropriately.

The system MUST NOT use offline cache as a mechanism to permanently bypass revocation.

---

# 36. Sync Queue Security

Pending offline mutations MAY contain sensitive data.

The local mutation queue MUST:

* Be protected by the client storage security model
* Associate mutations with the correct user/account
* Prevent cross-account replay
* Use unique mutation identifiers
* Revalidate authorization server-side

---

# 37. Idempotency and Replay Protection

Security-sensitive operations SHOULD support idempotency where repeated requests could cause harm.

Examples:

```text id="v1x5n7"
Booking creation
Permission change
Share-code redemption
External mutation
```

Repeated submission MUST NOT accidentally create multiple resources or repeat destructive operations.

---

# 38. CSRF Protection

Where browser authentication uses cookie-based credentials, state-changing requests MUST use appropriate CSRF protection.

If a different authentication mechanism is used, the implementation MUST still prevent cross-origin unauthorized state changes.

---

# 39. CORS

Production CORS policy MUST explicitly define permitted origins.

The API MUST NOT use unrestricted wildcard origins together with credentialed requests.

---

# 40. Authentication Abuse

Authentication endpoints SHOULD implement:

* Rate limiting
* Abuse detection
* Secure error responses
* Session invalidation mechanisms
* Provider callback validation

The system MUST avoid revealing whether arbitrary accounts exist through overly specific authentication errors where such information is sensitive.

---

# 41. OAuth Security

OAuth flows MUST validate:

* State
* Redirect URI
* Authorization response
* Provider identity
* Granted scopes
* Token lifecycle

Tokens MUST be stored securely.

The system MUST handle token expiration and revocation gracefully.

---

# 42. Scope Minimization

Google permissions SHOULD follow least privilege.

If Workaholic only needs Calendar read access for a feature, it SHOULD NOT request unrelated Drive write permissions.

Additional permissions SHOULD be requested only when the user enables functionality requiring them.

---

# 43. External Provider Failure

If Google becomes unavailable:

```text id="h7p3s2"
Google failure
   ↓
Google-dependent operation fails gracefully
```

It MUST NOT compromise:

* Native Workaholic tasks
* Native calendars
* Notes
* Local functionality
* Authentication
* Other unrelated domains

---

# 44. Secret Management

Production secrets MUST be managed outside source control.

Examples include:

* OAuth client secrets
* Database credentials
* API keys
* Push-provider credentials
* Encryption keys
* Signing secrets

Secrets SHOULD be supplied through secure deployment configuration.

---

# 45. Environment Separation

At minimum:

```text id="r6p4t1"
Development
Testing
Production
```

MUST have separate security-sensitive configuration.

Production credentials MUST NOT be reused casually in development.

---

# 46. Logging

Logs MUST be useful for diagnosing security and operational problems without becoming a data-exfiltration mechanism.

Logs SHOULD include:

* Request identifiers
* Operation type
* Success/failure
* Relevant resource identifiers where safe
* Error classification
* Authentication/security events

---

# 47. Sensitive Data in Logs

The following MUST NOT be logged in plaintext:

* Passwords
* OAuth refresh tokens
* Session credentials
* Push tokens where unnecessary
* Share codes
* API secrets
* Private note contents
* Private calendar descriptions
* Sensitive attachment contents

---

# 48. Security Audit Events

The system SHOULD record security-sensitive events such as:

```text id="y4p8s1"
Login
Logout
Authentication failure
Session created
Session revoked
Role changed
Permission granted
Permission revoked
Trusted relationship created
Trusted relationship revoked
Public link created
Public link revoked

```

---

# 49. Audit Log Integrity

Security/audit records SHOULD be append-oriented.

Ordinary users MUST NOT be able to arbitrarily modify audit history.

Administrative access to audit information MUST itself be authorized and, where appropriate, audited.

---

# 50. Error Messages

Errors MUST provide enough information for legitimate debugging without leaking internal security details.

Avoid responses such as:

```text id="q5v8t2"
User exists with Google identity X,
database row Y,
workspace Z
```

when that information is unnecessary.

---

# 51. Rate Limiting

Rate limiting SHOULD initially protect high-risk endpoints.

Priority targets include:

```text id="z8p3m6"
Authentication
Share-code redemption
Public calendar
Booking
Password/account operations if applicable
Permission changes
Public APIs
Search
File uploads
```

Rate limiting infrastructure MUST remain simple initially.

Redis or a distributed rate-limit service is not required unless scale demands it.

---

# 52. Denial of Service Considerations

The system SHOULD protect expensive operations against abuse.

Examples:

* Large file uploads
* Extremely broad calendar queries
* Expensive recurrence expansion
* Search queries
* Bulk mutations
* Booking requests
* Public calendar polling

Requests MUST have sensible limits.

---

# 53. Calendar Recurrence Security

Recurrence input MUST be bounded.

The application MUST prevent pathological requests such as:

```text id="s2x6q9"
Infinite recurrence
+
Huge expansion range
+
Thousands of nested operations
```

The system SHOULD limit expansion work per request.

---

# 54. Academic Schedule Security

Academic schedule regeneration MUST be authorized.

A user without permission to modify an academic calendar MUST NOT be able to:

* Insert holidays
* Change Day Order
* Modify class schedules
* End a semester
* Regenerate generated events

---

# 55. Semester-End Security

The End Semester operation is potentially destructive.

It MUST:

* Require appropriate permission
* Clearly identify the affected semester
* Affect only qualifying generated future events
* Preserve historical events
* Preserve reusable templates
* Avoid unrelated calendars

The implementation SHOULD support transactional execution.

---

# 56. Booking Atomicity

Booking creation MUST prevent double booking.

The authoritative booking operation MUST use an atomic server-side mechanism.

A client-side check such as:

```text id="v8q3p5"
"Slot looked free"
```

is insufficient.

---

# 57. Race Condition Protection

Security and correctness MUST account for concurrent operations.

Example:

```text id="p3x9m1"
User A checks 10:00
User B checks 10:00

Both see free

A books
B books
```

The database/transaction layer MUST ensure that only valid bookings succeed.

---

# 58. Data Minimization

Workaholic SHOULD store only information necessary to provide the feature.

For example, notification delivery diagnostics SHOULD NOT retain unnecessary message content indefinitely.

Similarly, public access MUST expose the minimum information required.

---

# 59. Data Retention

Different categories MAY have different retention policies.

Examples:

```text id="k2v7p4"
Active domain data
Audit records
Notification history
Sync metadata
Deleted objects
Sessions
Expired public links
```

Retention policies MUST be documented before implementation.

---

# 60. Soft Delete and Recovery

Important user data SHOULD use soft deletion/trash where appropriate.

This protects against:

* Accidental deletion
* Client bugs
* Synchronization mistakes
* Human error

Permanent deletion MUST be a deliberate operation.

---

# 61. Backup Strategy

Production databases MUST be backed up.

Backups SHOULD support:

* Automated creation
* Retention
* Restore testing
* Point-in-time recovery where supported
* Disaster recovery procedures

A backup that has never been restored/tested MUST NOT be assumed reliable.

---

# 62. Backup Security

Backups MUST be protected with security comparable to the production data they contain.

Access MUST be restricted.

Backups MUST NOT become an uncontrolled copy of user data.

---

# 63. Disaster Recovery

The system SHOULD define:

```text id="s7k3p2"
Recovery Point Objective
Recovery Time Objective
Backup retention
Restore procedure
Failure escalation
```

Exact operational values MAY be defined during deployment planning.

---

# 64. Data Export

Users SHOULD eventually be able to export their data.

Supported formats may include:

```text id="p6v2k9"
JSON
CSV
ICS
```

depending on domain.

Export functionality MUST respect authorization and account ownership.

---

# 65. Account Data Deletion

Account deletion MUST be deliberate and confirmed.

The system MUST distinguish:

```text id="b8x2q4"
Logout
Session revocation
Workspace removal
Account deletion
```

These operations have different consequences.

---

# 66. Privacy of Notes

Notes may contain arbitrary private information.

Therefore:

* Notes MUST obey resource authorization.
* Search MUST respect note permissions.
* Attachments MUST respect note permissions.
* Public projections MUST never expose private note content.
* Notifications MUST avoid leaking private note content.

---

# 67. Privacy of Calendar Data

Calendar data is especially sensitive because it reveals user behavior.

The system MUST protect:

* Event titles
* Locations
* Attendees
* Schedules
* Private descriptions
* Task relationships

Availability sharing MUST reveal only the minimum required information.

---

# 68. Privacy of Academic Data

Academic schedules may reveal:

* Institution
* Class timings
* Subjects
* Instructor information
* Routine patterns

Academic calendar data MUST therefore obey the same authorization principles as other calendar data.

---

# 69. Privacy of Trusted Relationships

Trusted relationship information itself may be sensitive.

Unauthorized users MUST NOT be able to enumerate:

* Trusted users
* Share codes
* Permission configurations
* Relationship status

---

# 70. Privacy of Sessions

Session management information MUST be visible only to the account owner or authorized security administrators.

Session credentials MUST never be returned to ordinary client UI.

---

# 75. Security Acceptance Scenarios

At minimum:

### SEC-T01

User A cannot access User B's private task.

### SEC-T02

User A cannot access Workspace B.

### SEC-T03

Viewer cannot modify resources.

### SEC-T04

Revoked session cannot access protected API.

### SEC-T05

Trusted user receives only granted permissions.

### SEC-T06

Revoked trusted relationship blocks future access.

### SEC-T07

Old share code cannot authenticate indefinitely.

### SEC-T08

Private calendar details are not exposed publicly.

### SEC-T09

Revoked public calendar token fails.

### SEC-T10

Booking guest cannot access calendar details.

### SEC-T11

Attachment cannot bypass parent authorization.

### SEC-T12

Google refresh token never appears in client payloads.

### SEC-T13

Google authorization cannot grant Workaholic workspace access.

### SEC-T14

Workaholic permissions cannot grant Google API access without authorization.

### SEC-T15

Search cannot reveal unauthorized resources.

### SEC-T16

Notification cannot expose unauthorized information.

### SEC-T17

Offline stale client cannot bypass revoked permissions.

### SEC-T18

Academic semester-end operation cannot delete unrelated events.

### SEC-T19

Booking race conditions cannot produce duplicate reservations.

### SEC-T20

Malformed/rate-abusive public requests are safely rejected.

                     ▼

# 81. Final Security Principles

The implementation MUST preserve the following rules:

> **1. Being logged in does not mean being authorized.**

> **2. Knowing an ID does not grant access to the resource.**

> **3. A client interface is not a security boundary.**

> **4. External provider authorization is separate from Workaholic authorization.**

> **5. Public access is a controlled projection, not direct database exposure.**

> **6. Trusted access is explicit, granular, and revocable.**

> **7. Private information must remain private across search, notifications, synchronization, attachments, and public views.**

> **8. Offline capability must never become a permanent authorization bypass.**

> **9. Destructive operations must be scoped, deliberate, and recoverable where possible.**

> **10. Future AI and automation must operate through the same authorization and business-rule boundaries as ordinary users.**

This document establishes the security and privacy baseline against which Workaholic's authentication, authorization, synchronization, calendar, notification, collaboration, integration, and future AI features MUST be implemented.
