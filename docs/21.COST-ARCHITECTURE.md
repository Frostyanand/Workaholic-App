# `COST-ARCHITECTURE.md`

**Status:** FINAL
**Purpose:** Define the cost model, resource strategy, scaling philosophy, and cost-control rules for Workaholic without compromising correctness, security, reliability, or the ability to scale to thousands of users.

---

## 1. Purpose

Workaholic shall initially operate as a low-cost personal productivity platform suitable for approximately 10 to 20 users while maintaining an architecture capable of scaling to thousands of users without fundamental redesign.

Cost optimization shall be achieved primarily through:

1. Appropriate use of managed infrastructure.
2. Avoidance of unnecessary infrastructure components.
3. Efficient database and API design.
4. Controlled background processing.
5. Client-side processing where appropriate.
6. External storage reuse through Google Drive integration.
7. Incremental adoption of infrastructure only when measurable requirements justify it.

Cost optimization shall **not** override:

* Data integrity.
* Security.
* Authorization.
* Synchronization correctness.
* Reminder reliability.
* Backup and recovery.
* User privacy.
* Maintainability.

---

# 2. Cost Philosophy

## 2.1 Initial Principle

The initial deployment shall use the smallest practical infrastructure capable of satisfying the defined functional and non-functional requirements.

The system shall **not** introduce infrastructure solely because it is common in large-scale applications.

The following shall not be introduced during the initial implementation without an identified requirement:

* Redis.
* Kafka.
* RabbitMQ.
* Kubernetes.
* Dedicated microservices.
* Dedicated search clusters.
* Dedicated tracing infrastructure.
* Dedicated object-storage systems when existing Google Drive integration sufficiently satisfies the requirement.
* Dedicated worker fleets.
* Multiple database clusters.
* Complex distributed caching infrastructure.

---

## 2.2 Scale-Ready Does Not Mean Over-Engineered

Workaholic shall initially use a modular architecture rather than a distributed architecture.

The expected progression is:

```text
Initial
  |
  v
Managed Web/API
  |
  v
PostgreSQL
  |
  +---- Google APIs
  |
  +---- Client Applications
```

As usage grows:

```text
Higher Usage
     |
     v
Optimize queries
     |
     v
Pagination / indexing
     |
     v
Application caching
     |
     v
Managed background jobs
     |
     v
Database scaling
     |
     v
Specialized infrastructure only when justified
```

Infrastructure shall be introduced based on measured bottlenecks rather than anticipated ones.

# 4. Environment Strategy

Workaholic shall maintain at least:

```text
Development
     |
     v
Production
```

A separate staging environment MAY be introduced when deployment risk justifies its additional cost.

## 4.1 Development

Development infrastructure should minimize recurring costs.

Where practical:

* Developers may use local databases.
* Local services should replace paid infrastructure during development.
* External integrations should provide development/test credentials where supported.
* Large-scale production data shall never be copied into local development environments without appropriate sanitization.

---

## 4.2 Production

Production shall use managed infrastructure wherever practical.

Production infrastructure shall prioritize:

1. Reliability.
2. Data durability.
3. Security.
4. Operational simplicity.
5. Cost.

---

# 5. Web Hosting

The Workaholic web application shall initially use managed deployment suitable for the project's web stack.

The intended deployment target is:

**Vercel.**

The web application should remain stateless wherever possible.

Client-side assets should be:

* Bundled efficiently.
* Code-split where beneficial.
* Cached appropriately.
* Served through the hosting platform's CDN capabilities.

The application shall avoid unnecessarily large client bundles.

---

# 6. Backend/API Cost Strategy

The backend shall initially use managed/serverless-compatible execution where practical.

API endpoints should be designed to:

* Perform bounded work.
* Avoid unnecessary database queries.
* Return only required fields.
* Paginate large collections.
* Avoid repeated external API requests.
* Avoid long-running synchronous operations.

Long-running or asynchronous operations should use background execution rather than keeping API requests open unnecessarily.

Examples include:

* Large Google synchronization operations.
* Recurring-event generation.
* Large attachment metadata processing.
* Bulk notifications.
* Large imports.

---

# 7. PostgreSQL Cost Strategy

PostgreSQL shall remain the primary system-of-record database.

The initial database architecture shall favor:

```text
One production PostgreSQL database
```

rather than multiple specialized databases.

The database shall be optimized before scaling vertically.

Optimization priorities:

1. Correct schema design.
2. Correct indexes.
3. Query analysis.
4. Pagination.
5. Avoidance of N+1 queries.
6. Efficient projections.
7. Transaction correctness.
8. Connection management.
9. Only then, larger database resources.

---

# 8. Database Growth Controls

The following data categories can grow significantly:

* Task history.
* Activity logs.
* Calendar events.
* Sync records.
* Notification records.
* Audit records.
* Booking records.
* Device/session records.

The application shall distinguish between:

### Operational data

Required for normal application functionality.

### Historical data

Useful for history, analytics, debugging, or audit.

### Derived data

Can be regenerated from authoritative records.

This distinction shall guide retention and storage decisions.

---

# 9. Database Indexing

Indexes shall be added according to actual query patterns and defined requirements.

Common query dimensions include:

* `workspace_id`
* `user_id`
* `project_id`
* `board_id`
* `status`
* `due_at`
* `start_at`
* `end_at`
* `created_at`
* `updated_at`
* external provider identifiers
* synchronization state

Indexes shall not be created indiscriminately.

Every substantial index introduces:

* Storage cost.
* Write overhead.
* Maintenance overhead.

---

# 10. File Storage

## 10.1 Google Drive Strategy

Because Workaholic integrates with Google Drive, attachments should preferentially use Drive as the underlying file-storage system when the user has authorized the integration.

Workaholic should store metadata and relationships such as:

```text
Workaholic Attachment
        |
        +-- Workaholic resource
        |
        +-- Google Drive file ID
        |
        +-- Metadata
```

Workaholic shall not unnecessarily duplicate the binary file.

---

## 10.2 Attachment Ownership

Removing an attachment from a Workaholic resource shall not automatically delete the underlying Google Drive file.

The user must explicitly request deletion from Drive where supported.

This avoids:

* Accidental data loss.
* Duplicate storage.
* Unnecessary storage costs.

---

## 10.3 Future Native Storage

Native Workaholic object storage MAY be introduced later if requirements justify it.

Possible reasons include:

* Users without Google Drive.
* Organization-controlled storage.
* Offline upload requirements.
* Performance requirements.
* File-sharing requirements.
* Storage independence.

Such storage shall not be introduced merely for architectural symmetry.

---

# 11. Google API Cost Control

Google APIs shall be treated as external resources with potentially meaningful quota and latency constraints.

The application shall avoid unnecessary calls.

Examples:

### Bad

```text
User opens calendar
    |
    +-- Fetch Google Calendar
    +-- Fetch Google Calendar again
    +-- Fetch Google Calendar again
```

### Preferred

```text
User opens calendar
    |
    v
Determine freshness
    |
    +-- Data sufficiently fresh
    |       |
    |       v
    |    Use existing synchronized state
    |
    +-- Data stale
            |
            v
        Synchronize
```

The exact caching/synchronization strategy shall follow `SYNC-SPECIFICATION.md`.

---

# 12. Google Synchronization Cost

Synchronization shall be incremental wherever supported.

The system should prefer:

```text
Initial synchronization
        |
        v
Persist synchronization cursor/state
        |
        v
Fetch changes
        |
        v
Apply changes
        |
        v
Persist new cursor/state
```

rather than repeatedly performing full synchronization.

Full synchronization may be triggered when:

* No synchronization cursor exists.
* Provider state becomes invalid.
* A recovery operation requires it.
* The user explicitly requests a resync.
* The synchronization specification requires it.

---

# 13. Background Job Cost Strategy

Workaholic requires background processing for:

* Reminder processing.
* Recurring task/event generation.
* Google synchronization.
* Booking notifications.
* Academic calendar processing.
* Cleanup.
* Maintenance.

Initially these should use managed scheduled/background execution.

The system shall avoid maintaining permanently running worker processes when workload does not justify them.

---

# 14. Job Design

Background jobs should be:

* Idempotent.
* Bounded.
* Retryable.
* Observable.
* Safe to execute more than once where possible.

For example:

```text
Reminder job
    |
    v
Find due reminders
    |
    v
Claim/process
    |
    v
Deliver notification
    |
    v
Persist delivery result
```

The job shall not repeatedly perform the same expensive operation simply because a previous execution timed out.

---

# 15. Reminder Cost

Reminder processing is potentially high-frequency.

The system should avoid checking every user every minute if the infrastructure model does not require it.

Instead, reminder scheduling should be based on the smallest practical set of due work.

The exact implementation may evolve according to platform constraints.

Correctness takes precedence over minimizing execution count.

A missed reminder is a functional failure, not merely a cost optimization opportunity.

---

# 16. Client-Side Reminder Processing

Where platform capabilities permit, reminders should be scheduled locally on:

* Windows.
* Android.
* Web where supported.

This reduces unnecessary server-side polling while improving reminder responsiveness.

The server remains authoritative for reminder configuration and synchronization.

Conceptually:

```text
Server
  |
  | reminder configuration
  v
Client
  |
  v
Local scheduler
  |
  v
Notification/alarm
```

---

# 17. Search Cost Strategy

The initial search implementation shall use PostgreSQL/native database capabilities where practical.

A dedicated search engine shall not be introduced initially.

Possible future infrastructure includes:

* Elasticsearch/OpenSearch.
* Specialized hosted search.
* Dedicated indexing systems.

Such infrastructure requires evidence that database-native search is insufficient.

Indicators may include:

* Large datasets.
* Slow search queries.
* Complex ranking requirements.
* High search traffic.
* Advanced fuzzy search requirements.

---

# 18. Caching Strategy

Caching shall be introduced only where measurement demonstrates value.

Initial priorities:

1. Correct database queries.
2. Efficient API responses.
3. Client-side state management.
4. Browser/platform caching.
5. HTTP caching where appropriate.

Redis or another dedicated cache may be introduced later.

Caching shall never become the authoritative source of application data.

---

# 19. Redis Introduction Criteria

Redis SHOULD NOT exist in the initial architecture.

It may be justified later for:

* High-volume distributed caching.
* Distributed rate limiting.
* Short-lived coordination.
* Job queues.
* Session-related infrastructure where appropriate.

Before introducing Redis, the project should demonstrate:

1. A measurable bottleneck.
2. A requirement that cannot be adequately handled by existing infrastructure.
3. A clear invalidation strategy.
4. A defined operational owner.
5. A cost/benefit justification.

---

# 20. Messaging and Event Infrastructure

Kafka, RabbitMQ, or similar systems shall not be introduced initially.

Internal application events may be represented through:

* Database records.
* Transactional state changes.
* Managed background jobs.
* Simple event dispatch mechanisms.

A dedicated message broker may be introduced only when asynchronous workload, reliability, throughput, or decoupling requirements justify it.

---

# 21. Microservices

Workaholic shall initially remain a modular application rather than a microservice architecture.

Logical modules may include:

```text
Authentication
Tasks
Projects
Boards
Calendar
Academic Scheduling
Notes
Notifications
Bookings
Integrations
Synchronization
Collaboration
Public Access
```

These are **domain boundaries**, not necessarily independently deployed services.

This allows the application to evolve without paying the operational cost of distributed systems prematurely.

---

# 22. Analytics

Initial analytics should be lightweight.

The system should capture only metrics required to understand:

* Feature usage.
* Reliability.
* Performance.
* Errors.
* Adoption.

Advanced analytics infrastructure shall be deferred until meaningful usage exists.

---

# 23. Observability Cost

Observability can become expensive primarily through uncontrolled:

* Logs.
* Error events.
* Traces.
* High-cardinality metrics.
* Request payload capture.

Therefore:

```text
Useful telemetry
       |
       v
Controlled volume
       |
       v
Useful retention
```

rather than collecting everything indefinitely.

The rules in `OBSERVABILITY.md` are authoritative for telemetry behavior.

---

# 24. Logging Cost Controls

Application logs shall use structured logging.

Logs should avoid unnecessarily verbose production output.

Development may use more detailed diagnostics.

Production should generally record:

* Request identifiers.
* Operation names.
* Result status.
* Duration.
* Resource identifiers where safe.
* Error classifications.
* Integration outcomes.

Production should not continuously log complete objects merely for convenience.

---

# 25. Error Tracking

Application errors should be captured through a managed error-reporting mechanism where practical.

Errors should contain enough context to reproduce the problem without storing sensitive application content.

Error grouping should prevent thousands of identical failures from generating independent noise.

---

# 26. Metrics

Metrics should focus on operationally meaningful quantities.

Examples:

### API

* Request count.
* Error rate.
* Latency.
* Rate-limit events.

### Database

* Query latency.
* Connection usage.
* Errors.
* Resource utilization.

### Synchronization

* Sync attempts.
* Successful syncs.
* Failed syncs.
* Sync latency.
* Conflict counts.
* Provider API errors.

### Notifications

* Scheduled reminders.
* Delivered notifications.
* Failed notifications.
* Delayed notifications.

### Bookings

* Booking attempts.
* Successful bookings.
* Conflict rejections.
* Cancellation/rescheduling counts.

---

# 27. High-Cardinality Metrics

Metrics shall avoid unbounded dimensions.

For example, this is generally unsafe:

```text
api_latency{user_id="..."}
```

because potentially millions of unique values may exist.

Prefer:

```text
api_latency{route="/tasks",method="GET"}
```

with carefully controlled dimensions.

User/resource identifiers belong primarily in logs or diagnostics, not unrestricted metric labels.

---

# 28. Tracing

Distributed tracing is not required for the initial architecture.

Basic request correlation should be implemented first.

Tracing may be introduced later if:

* API latency becomes difficult to diagnose.
* Multiple external calls create complex latency chains.
* Background jobs become sufficiently distributed.
* Database/API/provider interactions require deeper performance analysis.

The system should not pay the complexity and telemetry cost of full tracing before it provides meaningful diagnostic value.

---

# 29. Request Correlation

Requests shall have a correlation mechanism.

Conceptually:

```text
Client Request
     |
     v
Request ID
     |
     +---- API log
     |
     +---- Database operation context
     |
     +---- Background job
     |
     +---- External integration
     |
     v
Diagnostic trail
```

This enables a failure such as:

> "Google Calendar synchronization failed"

to be traced through the relevant application operation without logging sensitive data.

---

# 30. Synchronization Diagnostics

Synchronization is a high-risk operational subsystem and requires stronger observability.

The system should record safe diagnostic information including:

* Provider.
* Integration/account reference.
* Sync direction.
* Sync operation type.
* Start/end timestamps.
* Duration.
* Number of records examined.
* Number created.
* Number updated.
* Number deleted.
* Number conflicted.
* Failure category.
* Retry state.
* External error classification.
* Correlation ID.

It shall not store raw OAuth credentials or unnecessarily duplicate provider payloads.

---

# 31. Google Integration Failures

Failures should be categorized rather than represented only as generic errors.

Examples:

```text
AUTHORIZATION_REVOKED
TOKEN_REFRESH_FAILED
PROVIDER_RATE_LIMIT
PROVIDER_UNAVAILABLE
INVALID_EXTERNAL_OBJECT
SYNC_CONFLICT
INVALID_MAPPING
PERMISSION_DENIED
NETWORK_FAILURE
UNKNOWN_PROVIDER_ERROR
```

This allows both users and operators to distinguish:

```text
"Google is temporarily unavailable"
```

from:

```text
"You revoked Workaholic's Google Calendar permission"
```

---

# 32. Academic Scheduling Observability

The Day Order/academic scheduling engine shall produce diagnostics sufficient to explain generated schedules.

A generated event should be traceable through:

```text
Semester
   |
   v
Academic Calendar
   |
   v
Working Day
   |
   v
Day Order
   |
   v
Schedule Template
   |
   v
Schedule Entry
   |
   v
Generated Event
```

This is particularly important when:

* A holiday shifts the Day Order.
* A working Saturday changes sequence.
* A class is cancelled.
* A class is rescheduled.
* A semester is ended.

The system should be able to explain why a generated event exists or why a future event disappeared.

# 33. Booking Diagnostics

Booking operations require concurrency diagnostics.

A booking attempt should be traceable through:

```text
Availability calculation
       |
       v
Booking request
       |
       v
Conflict check
       |
       v
Transactional reservation
       |
       v
Calendar event
       |
       v
Notification
```

The system should distinguish:

* User cancelled.
* Slot unavailable.
* Concurrent booking won.
* Validation failure.
* Calendar conflict.
* Notification failure.

---

# 34. Public Calendar Diagnostics

Public calendar access must not leak private information through observability systems.

Logs may record:

```text
public_calendar_id
access_time
request_status
duration
```

Logs must not contain private event titles, descriptions, notes, attendees, or other private metadata merely because the public endpoint accessed them internally.

---

# 35. Session and Security Events

Security-sensitive events should be observable.

Examples:

* Login success.
* Login failure.
* OAuth authorization.
* OAuth revocation.
* Session creation.
* Session termination.
* Trusted-device registration.
* Trusted-device revocation.
* Public-session expiration.
* Permission changes.
* Workspace membership changes.
* Suspicious rate-limit activity.

These events should be distinguishable from ordinary application logs.

---

# 36. Audit Events vs Logs

Logs and audit events serve different purposes.

### Logs

Used for:

* Debugging.
* Performance analysis.
* Operational troubleshooting.

### Audit events

Used for:

* Security history.
* Accountability.
* Resource-changing actions.
* Permission changes.

Example:

```text
LOG:
Task update request took 182 ms.

AUDIT:
User changed task priority from LOW to HIGH.
```

Audit records should follow the retention and authorization rules defined by the security and permissions specifications.

---

# 37. Database Monitoring

Production database monitoring should cover:

* CPU/resource utilization where available.
* Storage consumption.
* Connection utilization.
* Slow queries.
* Query errors.
* Transaction failures.
* Lock contention.
* Backup status.
* Replication status if replication is later introduced.

Database growth should be reviewed periodically.

---

# 38. Health Checks

The backend should expose appropriate health/status mechanisms.

At minimum, distinguish:

### Liveness

The application process can respond.

### Readiness

The application can safely serve requests requiring its dependencies.

A database outage should not necessarily be reported as a healthy ready state if the endpoint requires database access.

Health endpoints shall not expose sensitive infrastructure information publicly.

---

# 39. Dependency Health

External dependencies should be monitored where practical:

```text
PostgreSQL
Google APIs
Notification services
Authentication provider
Background execution
```

The application should distinguish:

```text
Application failure
```

from:

```text
Dependency failure
```

This is particularly important for Google synchronization and notifications.

---

# 40. Alerts

Alerts shall be based on actionable conditions.

Examples:

* Sustained API error rate.
* Database unavailable.
* Database storage approaching configured threshold.
* Repeated synchronization failures.
* Reminder processing backlog.
* Notification delivery degradation.
* Authentication failure spike.
* Booking transaction failures.
* Deployment causing elevated error rate.

Alerts should not trigger merely because a low-value metric fluctuates.

---

# 41. Alert Fatigue

Every alert should answer:

> "What action should someone take?"

If the answer is unclear, it should generally be a dashboard metric rather than an alert.

The initial project should favor a small number of high-value alerts.

---

# 42. Deployment Correlation

Production errors should be correlated with deployments.

The system should be able to determine:

```text
Error spike
    |
    v
When did it begin?
    |
    v
What deployment occurred immediately before it?
```

Deployment metadata should therefore be included in application diagnostics where practical.

## 43.3 Android

# 44. Offline Diagnostics

Offline-capable clients should expose enough information to diagnose:

```text
Local operation
      |
      v
Local persistence
      |
      v
Sync queue
      |
      v

```

# 45. Privacy and Data Minimization

Observability data shall follow data minimization principles.

The following should **never** be logged in plaintext:

* Passwords.
* OAuth access tokens.
* OAuth refresh tokens.
* Full session tokens.
* API keys.
* Client secrets.
* Recovery secrets.
* Authentication credentials.

---

# 46. Sensitive Application Content

The following should not be routinely logged:

* Full private note content.
* Full task descriptions.
* Private calendar event descriptions.
* Attachment contents.
* Private comments.
* Message contents if chat is later implemented.
* Complete request bodies for sensitive endpoints.
* Full provider payloads when unnecessary.

A diagnostic system must not become an accidental copy of the user's private workspace.

---

# 47. Personally Identifiable Information

PII should be minimized.

Safe identifiers may include internal:

```text
user_id
workspace_id
task_id
event_id
sync_id
booking_id
```

when necessary for debugging and access is controlled.

Email addresses, names, phone numbers, or other PII should not be logged unless genuinely necessary.

---

# 48. Secret Redaction

Redaction should occur before data reaches persistent telemetry.

Examples:

```text
Authorization: Bearer ********
refresh_token: ********
client_secret: ********
cookie: ********
```

The system shall not rely solely on operators remembering not to log secrets.

---

# 49. Environment-Specific Telemetry

### Development

May provide:

* Detailed logs.
* Verbose API diagnostics.
* Local debugging information.

### Production

Should provide:

* Structured logs.
* Controlled diagnostic detail.
* Errors.
* Metrics.
* Security events.
* Correlation identifiers.

Production telemetry should be intentionally less verbose than development telemetry.

---

# 50. Retention

Observability data should have explicit retention periods.

Retention should be based on:

* Operational usefulness.
* Security requirements.
* Legal requirements where applicable.
* Storage cost.
* Privacy considerations.

Logs should not be retained indefinitely simply because storage is inexpensive.

Long-lived audit information may require different retention rules from short-lived debugging logs.

---

# 51. Data Deletion and User Privacy

When application data is deleted according to the applicable privacy/data lifecycle rules, observability systems should not retain unnecessary copies of the deleted content.

This is another reason why logs must not contain full task, note, calendar, or attachment contents.

---

# 52. Cost-Aware Telemetry Sampling

If tracing or high-volume diagnostic events are introduced later, sampling may be used.

For example:

```text
Normal successful requests
        |
        v
Low sampling

Errors
        |
        v
High sampling

Rare critical operations
        |
        v
Targeted detailed diagnostics
```

Sampling must never suppress essential security or audit events.

# 54. Operational Debugging Workflow

When an issue is reported, debugging should follow:

```text
1. Identify affected feature
          |
2. Identify timestamp
          |
3. Identify safe user/workspace/resource ID
          |
4. Find correlation/request ID
          |
5. Inspect application logs
          |
6. Inspect related background jobs
          |
7. Inspect database/integration diagnostics
          |
8. Identify dependency/deployment relationship
          |
9. Reproduce
          |
10. Fix
          |
11. Add regression test
```

The final step is mandatory for confirmed application defects where a regression test is practical.

# 57. Example: Booking Race

Two users attempt to book the same slot.

```text

   |
   v

   |

   |
```

# 58. Cost Review

Infrastructure cost should be reviewed periodically as usage increases.

Review:

* Database usage.
* Bandwidth.
* API execution.
* External API quotas.
* Background execution.
* Logging volume.
* Error-reporting volume.
* Storage.
* Notification volume.

The objective is not to minimize every individual cost.

The objective is:

> **Provide the required reliability and user experience at the lowest reasonable total system cost.**

---

# 59. Scaling Triggers

Infrastructure changes should be triggered by evidence.

Examples:

| Observed problem            | First response                          |
| --------------------------- | --------------------------------------- |
| Slow query                  | Analyze query/index                     |
| High DB CPU                 | Optimize queries, then scale DB         |
| Large API payloads          | Reduce projection/paginate              |
| Slow frontend               | Bundle/render optimization              |
| Excessive API calls         | Improve client/data-fetch strategy      |
| Background backlog          | Optimize jobs/increase managed capacity |
| High sync traffic           | Improve incremental sync                |
| Search slowdown             | Optimize DB search                      |
| Cache-worthy repeated reads | Introduce targeted caching              |
| Very high async workload    | Consider queue/worker infrastructure    |
| Cross-module scaling limits | Reconsider deployment boundaries        |

---

# 60. Infrastructure Introduction Rule

Any new infrastructure component should answer all of the following:

1. **What problem does it solve?**
2. **What evidence demonstrates the problem?**
3. **Why can the current architecture not solve it?**
4. **What operational complexity does it introduce?**
5. **What recurring cost does it introduce?**
6. **How will it be monitored?**
7. **How will it be removed if no longer needed?**

If these questions cannot be answered, the component should generally not be introduced.

# 61. Cost Architecture by Growth Stage

## Stage 1: 10 to 20 users

Target architecture:

```text
Vercel
   |
   v
Managed API
   |
   v
Managed PostgreSQL
   |
   +---- Google APIs
   |
   +---- Managed background execution
   |
   +---- Web / Windows / Android clients
```

Focus:

* Correctness.
* Reliability.
* Security.
* Low operational burden.

---

## Stage 2: Hundreds of users

Priorities:

* Query optimization.
* Database indexes.
* Pagination.
* Background-job optimization.
* API efficiency.
* External API quota management.
* Observability improvements.

Do not automatically introduce distributed infrastructure.

---

## Stage 3: Thousands of users

Evaluate:

* Database scaling.
* Read optimization.
* Targeted caching.
* Background workload separation.
* Search improvements.
* More sophisticated rate limiting.
* More robust job processing.
* More detailed tracing.

Architecture changes should remain evidence-driven.

---

## Stage 4: Significant Scale

Only at substantial scale should the team seriously consider:

* Dedicated workers.
* Message brokers.
* Dedicated search infrastructure.
* Multiple application services.
* Read replicas.
* Advanced caching.
* Specialized data stores.

These are possible evolution paths, not initial requirements.

# 62. Cost and Reliability Trade-Off

Cost reduction must never create unacceptable failure modes.

The following shall be treated as high-priority reliability functions:

* Database durability.
* Backups.
* Authentication.
* Authorization.
* Data synchronization.
* Reminder delivery.
* Booking conflict prevention.
* Calendar correctness.
* Data recovery.
* Security event recording.

For these systems:

```text
Cheaper
```

is not sufficient justification for:

```text
Less reliable
```

---

# 63. Vendor Independence

The architecture should avoid unnecessary coupling to infrastructure vendors.

Provider-specific functionality should be isolated behind application boundaries where practical.

Examples:

```text
NotificationService
GoogleCalendarProvider
GoogleTasksProvider
GoogleDriveProvider
StorageProvider
```

This allows future providers to be introduced without rewriting core domain logic.

---

# 64. Free/Low-Cost Initial Operation

The initial deployment should aim to remain within available free tiers or very low-cost managed plans where those plans satisfy:

* Expected user volume.
* Database capacity.
* API execution limits.
* Notification requirements.
* Backup requirements.
* Security requirements.

Free tiers shall not be used when they materially compromise required reliability.

---

# 65. Cost Anti-Patterns

The following are explicitly discouraged during initial development:

### Premature Redis

```text
PostgreSQL
     +
Redis
```

without a measured caching requirement.

### Premature Kafka

```text
API
 |
Kafka
 |
Worker
```

when a simple managed background job is sufficient.

### Premature Kubernetes

A cluster should not exist merely because the application is intended to scale.

### Premature Search Cluster

Do not operate a separate search service while PostgreSQL search is sufficient.

### Duplicate File Storage

Do not store the same attachment unnecessarily in multiple systems.

### Excessive Polling

Do not repeatedly query APIs when synchronization state or push mechanisms can avoid it.

### Unbounded Logs

Do not log every request body, object, and provider payload.

# 66. Architectural Principle

The Workaholic cost architecture follows:

```text
Correctness
    >
Security
    >
Reliability
    >
Maintainability
    >
Performance
    >
Cost
```

subject to the requirement that cost remains sustainable.

Cost optimization should occur through **simplicity and efficiency first**, not through removing safeguards.
