# `API-SPECIFICATION.md`

**Status:** FINAL
**Version:** 1.0
**Product:** Workaholic
**Scope:** Backend API contracts, request/response conventions, authentication, authorization, resource operations, synchronization, integrations, public access, booking, errors, pagination, and idempotency

---

# 1. Purpose

This document defines the behavioral contract for the Workaholic application API.

The API provides the controlled boundary between:

```text
Web Client
Windows Client
Android Client
        │
        ▼
     Workaholic API
        │
        ▼
Application Services
        │
        ▼
PostgreSQL / External Providers
```

The API MUST enforce:

* Authentication
* Authorization
* Validation
* Business rules
* Resource isolation
* Data integrity
* Idempotency where required
* Synchronization semantics
* External integration boundaries

Clients MUST NOT communicate directly with the primary database.

---

# 2. API Design Principles

The API MUST follow:

1. **Server is authoritative.**
2. **Clients are untrusted.**
3. **Authentication and authorization are separate.**
4. **Resources are scoped to their workspace/user context.**
5. **Business rules are enforced server-side.**
6. **Responses expose only authorized information.**
7. **Mutations are explicit.**
8. **Destructive operations are deliberate.**
9. **Offline mutations are safely idempotent.**
10. **External provider operations remain isolated behind integration boundaries.**

# 4. Authentication

Protected API requests MUST carry the authenticated Workaholic identity using the application's supported session/token mechanism.

Conceptually:

```text
Request
  ↓
Authentication
  ↓
Workaholic User
```

The API MUST reject unauthenticated requests to protected resources.

---

# 5. Authorization

After authentication:

```text
User
 ↓
Workspace Membership
 ↓
Role / Permissions
 ↓
Resource Access
 ↓
Requested Action
```

must be evaluated.

The API MUST NOT trust:

* Client role fields
* Client workspace IDs
* Client ownership claims
* Client visibility claims
* Client permission claims

---

# 6. Request Context

The server SHOULD construct an internal request context containing information such as:

```text
Authenticated user
Session
Workspace context
Permissions
Device/session information
Request ID
```

The context MUST NOT be accepted wholesale from client-provided JSON.

# 7. Workspace Context

Where an operation is workspace-scoped, the API MUST determine the workspace through an authorized relationship.

Example:

```text
POST /api/v1/tasks
```

The client MAY provide a project or board identifier.

The server determines the associated workspace and validates membership.

A client-supplied workspace ID MUST NOT bypass this validation.

---

# 8. Resource Identifiers

Resources SHOULD use opaque identifiers.

Examples:


Identifiers MUST NOT themselves be treated as credentials.

# 9. Standard HTTP Semantics

The API SHOULD use conventional HTTP semantics.

Typical operations:

| Operation               | Method   |
| ----------------------- | -------- |
| Create                  | `POST`   |
| Retrieve                | `GET`    |
| Update                  | `PATCH`  |
| Replace where necessary | `PUT`    |
| Delete                  | `DELETE` |

Domain-specific actions MAY use explicit action endpoints where they better represent the operation.

Examples:

```text

POST /tasks/{id}/reopen
POST /bookings/{id}/cancel
POST /sessions/{id}/revoke
POST /semesters/{id}/end
```

Example:



The server MUST still validate the resulting resource as a whole.

# 15. Authentication Errors

Unauthenticated requests SHOULD return an appropriate authentication failure.

---

# 16. Authorization Errors

A user who is authenticated but lacks permission SHOULD receive a forbidden response.

The API MUST avoid unnecessarily revealing whether a protected resource exists.

---

# 17. Not Found vs Forbidden

For sensitive resources, the implementation MAY return `NOT_FOUND` rather than revealing that an inaccessible object exists.

The choice MUST be consistent and must not leak resource existence.

---

# 18. Validation Errors

Validation responses SHOULD identify the relevant field when possible.

Example:

```json

  "error": {
    "code": "VALIDATION_ERROR",
```

# 19. Conflict Errors

Conflict responses SHOULD be used when the requested mutation cannot safely be applied because the authoritative state differs.

Examples:

* Optimistic concurrency conflict
* Booking collision
* Sync conflict
* Duplicate constrained resource

# 24. Optimistic Concurrency

Mutable resources SHOULD use version information.

Example:

```json
{
  "id": "task_123",
  "version": 7
}
```

A mutation based on stale state may be rejected with a conflict.

---

# 25. Concurrency Example

Client A:

```text
version = 7
```

Client B:

```text
version = 7
```

A updates:

```text
version 8
```

B submits an update based on version 7.

The server MUST detect the stale version rather than silently overwriting A's change when the fields cannot safely be merged.

# 41.1. Today / Command Center API

The Today / Command Center API provides a unified, bounded contextual read model consolidating the user's daily focus, active execution schedule, and deadlines for a given calendar date and timezone.

Endpoint:

```text
GET /api/v1/today
```

Query Parameters:

* `date` (optional): `YYYY-MM-DD` target calendar date. Defaults to current calendar date in user's effective timezone.
* `timezone` (optional): IANA timezone string (e.g., `Asia/Kolkata`, `UTC`). Precedence: `request.query.timezone` → `authenticated user's timezone` → `UTC`.

Response Payload Envelope:

```json
{
  "data": {
    "date": "2026-09-07",
    "timezone": "Asia/Kolkata",
    "currentWork": null,
    "nextWork": null,
    "dueToday": [],
    "overdue": [],
    "important": [],
    "unscheduled": [],
    "calendarEvents": [],
    "workBlocks": [],
    "completedToday": [],
    "counts": {
      "dueToday": 0,
      "overdue": 0,
      "important": 0,
      "unscheduled": 0,
      "completedToday": 0,
      "calendarEvents": 0,
      "workBlocks": 0
    }
  }
}
```

Semantics:

* `currentWork`: Scheduled item currently containing NOW (`start_at <= now < end_at`). Task work block takes precedence over overlapping calendar event. Evaluates to `null` if nothing is scheduled (no arbitrary task fallback).
* `nextWork`: First scheduled item beginning strictly after NOW (`start_at > now`) within today's local day, ordered `start_at ASC`. Evaluates to `null` if no scheduled items remain.
* `dueToday`: Incomplete tasks with `day_start_utc <= due_at <= day_end_utc`.
* `overdue`: Incomplete tasks with `due_at < NOW()`.
* `important`: Active, incomplete P0/P1/P2 tasks.
* `unscheduled`: Active incomplete P0/P1/P2 or due tasks without an active work block.
* Tenant Isolation: Strictly scoped to authenticated workspace context.

# 61. Booking Race

```text

          ├── Server transaction
Client B ─┘
```

# 91. Final API Principles

The implementation MUST preserve these rules:

> **1. Every protected operation authenticates and authorizes the caller.**

> **2. The server, not the client, decides whether an operation is permitted.**

> **3. Resource IDs identify objects but never grant access.**

> **4. Business rules live in application/domain logic and cannot be bypassed through alternate endpoints.**

> **5. Offline retries must be safe and idempotent.**

> **6. External providers remain behind explicit integration boundaries.**

> **7. Public APIs expose projections, not private database records.**

> **8. Booking and other concurrency-sensitive operations require authoritative server-side validation.**

> **9. Bulk domain changes should be represented as domain operations rather than thousands of independent client mutations.**

> **10. Future AI and automation must use the same application actions, authorization, and business rules as ordinary clients.**

This API contract now provides the implementation boundary between the UX/domain specifications and the actual application code.
