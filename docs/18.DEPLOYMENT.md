````markdown
## 1. Purpose

This document defines how Workaholic is built, configured, tested, deployed, updated, monitored, and recovered across its supported platforms.

The deployment architecture must satisfy the following principles:

1. Minimize operating cost during the initial 10–20 user phase.
2. Avoid premature infrastructure complexity.
3. Preserve a clean path toward substantially larger workloads.
4. Keep development, staging, and production environments isolated.
5. Never expose server-side secrets or OAuth credentials to clients.
6. Require automated validation before production deployment.
7. Make deployments reversible where practical.
8. Preserve user data during application and schema changes.
9. Treat Web, Windows, and Android as separate deployment targets while sharing the appropriate backend and domain infrastructure.

---

# 2. Deployment Targets

Workaholic has three primary client targets:

| Target | Deployment |
|---|---|
| Web | Vercel |
| Windows | Desktop application distribution |
| Android | Android application distribution |

The backend and database are deployed independently of the clients.

Conceptually:

```text

                         │     Vercel      │
                         └────────┬────────┘
                                  │
┌──────────────┐                  │

Backend ───────────────► Google Calendar
Backend ───────────────► Google Tasks
Backend ───────────────► Google Drive
Backend ───────────────► Notification Services
````

# 3. Environment Model

Workaholic uses three primary environments.

```text
Local
  ↓
Staging / Test
  ↓
Production
```

## 3.1 Local

Used for:

* development;
* unit tests;
* integration tests;
* local database development;
* local client testing.

Local development must not use production credentials or production user data.

---

## 3.2 Staging

Used for:

* release-candidate testing;
* integration testing;
* E2E testing;
* external-service verification;
* migration testing;
* platform validation.

Staging should approximate production configuration sufficiently to expose deployment-related defects.

---

## 3.3 Production

Used exclusively for real users and real user data.

Production credentials, databases, OAuth secrets, and other sensitive configuration must never be committed to source control.

---

# 4. Environment Isolation

Each environment must have independent:

* database;
* application configuration;
* secrets;
* OAuth credentials where practical;
* storage configuration;
* external integration accounts where practical;
* notification configuration.

A staging failure must not affect production.

A test cleanup operation must never target production resources.

---

# 5. Source Control

The canonical source repository is hosted on GitHub.

The repository must contain:

```text
Application source
Database migrations
Tests
Configuration templates
Documentation
CI configuration
Deployment configuration
```

Secrets must not be committed.

Examples of prohibited repository contents:

```text
API keys
OAuth client secrets
Refresh tokens
Production database credentials
Signing keys
Private certificates
```

Environment-specific secrets must be injected through the deployment environment.

---

# 6. Branching Strategy

The project should use a simple branching model.

Recommended structure:

```text
main
  │
  ├── feature/*
  ├── fix/*
  └── chore/*
```

`main` represents the production-ready branch.

Feature branches must pass required validation before merging.

The project should avoid unnecessarily complicated release-branch structures during the initial development stage.

---

# 7. Continuous Integration

Every pull request should trigger CI.

Minimum pipeline:

```text
Checkout
   ↓
Install dependencies
   ↓
Static checks
   ↓
Lint
   ↓
Unit tests
   ↓
Domain tests
   ↓
Database tests
   ↓
API / Integration tests
   ↓
Build
   ↓
Relevant E2E tests
```

A pull request should not be merged when required checks fail.

---

# 8. Continuous Deployment

Production deployment should occur only after:

1. code review;
2. required CI checks;
3. successful build;
4. migration validation where applicable;
5. staging verification for release-critical changes;
6. explicit deployment approval where required by the chosen CI/CD configuration.

The exact deployment mechanism may evolve without changing this policy.

---

# 9. Web Deployment

The Web application is deployed to Vercel.

The deployment flow is:

```text
GitHub
   ↓
CI
   ↓
Build
   ↓
Vercel deployment
   ↓
Production Web application
```

The web application must use environment-specific configuration.

Client-exposed configuration must contain only values that are safe to expose publicly.

Server-side secrets must never be bundled into browser JavaScript.

---

# 10. Web Preview Deployments

Pull requests should use preview deployments where practical.

Preview deployments allow verification of:

* UI changes;
* responsive behavior;
* navigation;
* authentication flows;
* API integration;
* visual regressions.

Preview environments must not accidentally point at production databases unless explicitly designed and secured for that purpose.

---

# 11. Backend Deployment

The backend should initially use a managed deployment model rather than self-managed infrastructure.

The backend must support:

* API requests;
* authentication;
* authorization;
* database access;
* synchronization;
* notification scheduling;
* background jobs;
* integration adapters.

The initial deployment should avoid:

* Kubernetes;
* dedicated container orchestration;
* manually managed server clusters;
* Redis clusters;
* Kafka;
* service meshes;
* microservice decomposition.

These may be introduced later if actual scale or operational requirements justify them.

---

# 12. Database Deployment

The production database must be managed and backed up.

Database schema changes must be performed through version-controlled migrations.

The deployment sequence must be conceptually:

```text
Code
 ↓
Migration validation
 ↓
Migration
 ↓
Application deployment
```

Where backward compatibility is required, migrations and application releases should be designed to permit safe transition between versions.

---

# 13. Database Migration Rules

Every schema migration must:

* have a unique migration identifier;
* be committed to source control;
* be tested against representative data;
* be tested in staging;
* preserve existing data unless deletion is explicitly required;
* preserve referential integrity;
* have a documented recovery strategy where appropriate.

Destructive migrations require additional review.

---

# 14. Zero- or Low-Downtime Migration Principle

The initial product does not require elaborate zero-downtime infrastructure.

However, migrations should prefer additive changes.

Preferred sequence:

```text
Add new field
   ↓
Deploy compatible application
   ↓
Migrate/use data
   ↓
Remove obsolete field later
```

Avoid making an application version dependent on a schema change that has not yet been deployed.

---

# 15. Secrets Management

Secrets must be stored in the deployment platform's secure environment configuration or an equivalent secrets-management system.

Secret categories include:

* database credentials;
* OAuth client secrets;
* encryption keys;
* signing keys;
* notification credentials;
* storage credentials;
* deployment credentials.

Secrets must:

* never be logged;
* never be returned by APIs;
* never be embedded into client bundles;
* never be committed to Git;
* be rotated when compromise is suspected.

---

# 16. Google OAuth Configuration

Google integration requires separate configuration for each environment.

The backend owns server-side OAuth credentials.

The architecture must preserve the distinction between:

```text
Workaholic authentication
        ≠
Google API authorization
```

Google access tokens and refresh credentials must not be exposed unnecessarily to client applications.

Redirect URIs must be environment-specific and explicitly registered with Google.

---

# 17. OAuth Scope Management

Workaholic should request only the Google scopes required for enabled functionality.

Scopes must be reviewed whenever Google integration functionality changes.

The application must not request broad permissions merely because they may become useful in the future.

---

# 18. Client Configuration

Client applications may require configuration such as:

```text
API base URL
environment identifier
public application configuration
OAuth public/client identifiers where appropriate
feature configuration
```

Client configuration must be separated from secrets.

A value being present in an environment variable does not automatically make it secret.

Anything delivered to a browser or client application must be treated as potentially observable by the user.

---

# 19. Windows Deployment

The Windows application is distributed as a native desktop application.

The deployment process must support:

* application installation;
* version identification;
* update mechanism;
* startup behavior;
* background execution;
* system tray operation;
* notification functionality;
* application restart.

The installer/update system must preserve user configuration and local state where required.

---

# 20. Windows Updates

Updates must not intentionally destroy:

* authentication state where preservation is supported;
* local synchronization state;
* scheduled reminder state;
* user preferences.

An update failure must leave the application recoverable.

The exact update mechanism may be selected during implementation.

---

# 21. Android Deployment

The Android application is distributed as an Android application package through the appropriate distribution channel.

The release process must include:

* application signing;
* versioning;
* build validation;
* installation testing;
* upgrade testing;
* notification testing;
* background behavior testing.

Signing credentials must never be committed to source control.

---

# 22. Android Versioning

Android releases must maintain monotonically increasing release identifiers as required by the platform.

Application-visible version numbers should communicate meaningful releases to users.

A release must be identifiable from:

```text
version
build number
commit/release identifier
```

---

# 23. Application Versioning

Web, Windows, Android, backend, and database versions may evolve independently.

However, compatibility requirements must be documented when different client versions interact with the same backend.

The backend should avoid unnecessarily breaking older supported clients.

---

# 24. API Compatibility

API changes must consider:

```text
Current Web client
Current Windows client
Current Android client
Potential older clients
```

Breaking changes require deliberate versioning or a controlled migration strategy.

The API specification remains the authoritative contract.

---

# 25. Background Jobs

Background processing may initially be implemented using managed scheduling/job infrastructure.

Required job categories include:

* reminder processing;
* recurring occurrence generation;
* Google synchronization;
* Drive operations;
* booking notifications;
* cleanup;
* analytics where implemented.

The architecture must not require a permanently running dedicated worker fleet during the initial low-scale phase unless the chosen platform requires one.

---

# 26. Scheduled Job Safety

Background jobs must be:

* idempotent where possible;
* retryable;
* observable;
* failure-tolerant;
* safe against duplicate execution.

A job running twice must not silently create duplicate:

* tasks;
* events;
* reminders;
* notifications;
* synchronization records.

---

# 27. Deployment of Background Jobs

Application deployment must account for job version compatibility.

If a job depends on a database schema change, the schema must be compatible with both old and new job versions during transition where necessary.

---

# 28. Static Assets

Static assets should be served through the web deployment/CDN infrastructure provided by the selected platform.

Large assets should not unnecessarily be bundled into application JavaScript.

Images and other resources should be optimized according to the UX and performance requirements.

---

# 29. File Storage

Workaholic attachments use Google Drive as the external file-storage system where configured.

The Workaholic backend stores the required metadata and relationship information.

Deployment must not introduce an independent file-storage dependency unless explicitly approved by the architecture.

---

# 30. Public Calendar Deployment

Public calendar pages must be served through the web application.

Public endpoints must:

* use revocable identifiers;
* enforce public/private visibility rules;
* avoid exposing private metadata;
* remain independent of authenticated dashboard access;
* prevent accidental indexing unless explicitly enabled.

---

# 31. Booking Deployment

Booking endpoints must be deployed as production backend functionality.

The deployment must preserve database transaction guarantees for concurrent bookings.

Frontend availability checks must never be treated as the final concurrency protection.

The authoritative booking decision must occur server-side.

---

# 32. Production Database Safety

Production database operations must distinguish:

```text
Read
Write
Bulk mutation
Destructive operation
Migration
```

Destructive administrative operations must require stronger safeguards than normal application requests.

---

# 33. Data Protection During Deployment

Deployments must not:

* reset production data;
* recreate production databases;
* truncate tables;
* delete user resources;
* reset synchronization mappings.

Any deployment script capable of destructive operations must explicitly target the intended environment.

---

# 34. Deployment Rollback

Rollback must be considered at three levels:

```text
Application rollback
Database rollback/recovery
Client rollback/update recovery
```

Application rollback should be straightforward for compatible releases.

Database rollback is more complex and must not rely on blindly reversing migrations.

For destructive schema changes, restoration or forward-fix procedures may be safer than reverse migration.

---

# 35. Forward-Fix Principle

When a production defect occurs, prefer:

```text
Identify issue
   ↓
Stop further damage
   ↓
Deploy corrected version
   ↓
Verify
```

over unnecessary destructive database rollback.

Database restoration should be reserved for situations where data integrity cannot otherwise be recovered.

---

# 36. Deployment Health Checks

The backend must expose safe health information sufficient to determine whether core services are functioning.

Health verification should include:

* application process availability;
* database connectivity;
* required configuration;
* critical dependency availability where appropriate.

Health endpoints must not expose secrets or sensitive internal configuration.

---

# 37. Post-Deployment Smoke Tests

Immediately after a production deployment, verify:

```text
Web loads
   ↓
Authentication works
   ↓
API responds
   ↓
Database works
   ↓
Task creation works
   ↓
Task completion works
   ↓
Calendar loads
```

Release-specific smoke tests should then validate affected functionality.

---

# 38. Deployment Monitoring

After deployment, monitor:

* application errors;
* API latency;
* database failures;
* authentication failures;
* authorization failures;
* synchronization errors;
* notification failures;
* background-job failures;
* booking conflicts/failures;
* client crash/error reports where available.

Monitoring requirements are detailed further in `OBSERVABILITY.md`.

---

# 39. Production Rollout Strategy

For low-risk changes:

```text
CI
 ↓
Deploy
 ↓
Smoke test
 ↓
Monitor
```

For higher-risk changes:

```text
CI
 ↓
Staging
 ↓
Release candidate
 ↓
Production
 ↓
Smoke tests
 ↓
Focused monitoring
```

Feature flags may be introduced when a feature requires gradual enablement.

Feature flags should not become a permanent substitute for clean deployment architecture.

---

# 40. Feature Flags

Feature flags may be used for:

* incomplete functionality;
* controlled rollout;
* risky integrations;
* experimental UI;
* migration transitions.

Flags must have:

* an owner;
* a documented purpose;
* a known default;
* a removal plan.

Temporary flags should not accumulate indefinitely.

---

# 41. Cost Control

Initial infrastructure should favor managed/free-tier services where they satisfy reliability and security requirements.

The architecture should avoid paying for infrastructure that provides no meaningful value at initial scale.

Initial priorities:

```text
Managed services
Minimal always-on infrastructure
Serverless/on-demand execution where appropriate
Single primary database
No unnecessary distributed systems
```

Cost decisions are specified further in `COST-ARCHITECTURE.md`.

---

# 42. Scalability Principle

The initial deployment must be simple, but application boundaries must remain scale-ready.

The system should be able to evolve toward:

```text
Single backend
     ↓
More backend instances
     ↓
Dedicated workers where justified
     ↓
Specialized infrastructure where justified
```

without requiring a complete rewrite of the domain model.

The existence of a future scaling path does not justify deploying the future infrastructure prematurely.

---

# 43. Database Scaling

The database is expected to be the primary shared state system.

Scaling should proceed approximately as:

```text
Query optimization
    ↓
Indexes
    ↓
Pagination
    ↓
Connection/resource tuning
    ↓
Database scaling
    ↓
Read replicas / partitioning where justified
```

Redis, Kafka, sharding, or other infrastructure should not be introduced solely because they are common in large-scale systems.

---

# 44. CDN and Edge Usage

The web platform may provide CDN/edge capabilities automatically.

Workaholic should use these capabilities for:

* static assets;
* cacheable public resources;
* appropriate public pages.

Private authenticated application data must not be cached publicly.

---

# 45. Domain and TLS

Production traffic must use HTTPS.

The deployment must provide valid TLS certificates.

HTTP requests should redirect to HTTPS where supported.

Sensitive credentials and session information must never be transmitted over plaintext HTTP.

---

# 46. Custom Domains

Production web deployment should use a stable application domain.

Environment-specific domains should distinguish staging from production.

Example conceptual structure:

```text
app.<domain>
staging.<domain>
```

The exact domain is deployment-specific and is not defined by this document.

---

# 47. DNS

DNS configuration must be version/documentation controlled where practical.

Production DNS changes require review because incorrect DNS configuration can make an otherwise healthy application unavailable.

---

# 48. Deployment Documentation

Deployment procedures must document:

* required environment variables;
* required external services;
* deployment commands/process;
* migration procedure;
* rollback/recovery procedure;
* client build process;
* release verification;
* emergency recovery process.

A new developer should be able to reconstruct the deployment process from repository documentation without relying exclusively on undocumented personal knowledge.

Local setup should provide:

```text
Install dependencies

Configure local environment

Run migrations
   ↓

   ↓
```

Development seed data must be clearly distinguishable from real user data.

# 50. Seed Data

Development/staging seed data may include:

* sample user;
* workspace;
* projects;
* tasks;
* boards;
* events;
* recurring events;
* notes;
* academic semester;
* Day Order schedule;
* reminders;
* booking configuration.

Seed data must be deterministic where tests depend on it.

---

# 51. Production Seed Data

Production must not use development seed data.

Production initialization should be limited to required system configuration and migration-defined data.

---

# 52. Deployment Access Control

Production deployment permissions must be limited to authorized maintainers.

Production database access should be more restricted than normal application access.

Deployment credentials must not be shared through source code, chat, or documentation.

---

# 53. Auditability

Production deployments should be traceable to:

```text
Commit
↓
Build
↓
Deployment
↓
Version
```

It must be possible to determine which source revision is currently deployed.

---

# 54. Emergency Deployment

Emergency fixes follow the same fundamental principles as normal deployments but may use an accelerated review process.

Required minimum:

```text
Identify critical defect
   ↓
Implement minimal fix
   ↓
Run targeted tests
   ↓
Run security/data-safety tests where applicable
   ↓
Deploy
   ↓
Smoke test
   ↓
Monitor
   ↓
Add regression test
```

The emergency process must not permanently bypass normal CI.

---

# 55. Incident Recovery

If deployment causes a production incident:

1. identify affected functionality;
2. prevent further data damage;
3. determine whether application rollback is safe;
4. restore or forward-fix data where required;
5. deploy corrected application;
6. verify critical workflows;
7. inspect synchronization and notification state;
8. document the incident;
9. add regression coverage.

---

# 56. Client and Backend Compatibility

Because clients may update at different times, backend changes must consider mixed versions.

For example:

```text
Android v2
Windows v1
Web v3
       ↓
   Backend v4
```

must remain safe when such combinations are supported.

Breaking client compatibility requires either:

* coordinated client release;
* API versioning;
* compatibility layer;
* explicit minimum-version enforcement.

---

# 57. Minimum Supported Version

The project must eventually define minimum supported:

* Web browser versions;
* Windows versions;
* Android versions;
* client application versions.

Until formally defined, implementation must not silently assume unsupported versions.

---

# 58. Notifications and Deployment

Notification changes require additional deployment validation because scheduling may span multiple processes and devices.

A deployment must not unintentionally:

* duplicate reminders;
* cancel valid reminders;
* reset notification state;
* reschedule historical notifications;
* send notifications to incorrect recipients.

---

# 59. Synchronization and Deployment

Synchronization changes are high-risk.

Before deployment of sync logic changes:

* migration compatibility must be verified;
* duplicate prevention tests must pass;
* conflict tests must pass;
* external integration tests must pass;
* offline/reconnect tests must pass;
* regression tests must pass.

A sync deployment must not assume all clients reconnect simultaneously.

---

# 60. Academic Scheduling and Deployment

Changes to academic scheduling logic require dedicated regression testing before release.

Particular attention must be paid to:

* existing semesters;
* future generated events;
* Day Order mappings;
* holidays;
* special working days;
* rescheduled classes;
* End Semester behavior.

A deployment must not reinterpret historical calendar data unexpectedly.

---

# 61. Production Data Evolution

Production data may outlive multiple application versions.

Therefore:

```text
Application code
        ≠
Database lifecycle
```

The database schema and stored data must be treated as long-lived system state.

Business logic changes must explicitly consider existing records.

---

# 62. Backup Verification

Backups must be:

* automated where supported;
* retained according to the selected infrastructure policy;
* protected from unauthorized access;
* periodically tested for restoration.

Backup creation alone is insufficient.

The recovery procedure must be exercised periodically.

---

# 63. Disaster Recovery

The disaster recovery strategy must address:

* database failure;
* accidental data deletion;
* corrupted deployment;
* credential compromise;
* external integration failure;
* unavailable deployment provider.

The exact RPO/RTO targets may be refined as actual product usage and business requirements evolve.

---

Before production deployment:

```text
[ ] Application reachable
[ ] Authentication works

[ ] Database healthy
```

# 65. Release Failure Criteria

Deployment must be halted or rolled back/repaired when:

* production authentication fails;
* protected data becomes accessible to unauthorized users;
* database integrity is compromised;
* user data is unexpectedly deleted;
* synchronization produces destructive or widespread incorrect behavior;
* critical booking concurrency protection fails;
* critical notifications are sent incorrectly;
* the application cannot perform core task/calendar operations.

The preferred shape is:

```text
                    ┌──────────────┐
                    │    Vercel    │
                    │ Web frontend │

                           ▼
                    ┌──────────────┐

                    │ Managed API  │
                    └──────┬───────┘

                           ▼
                    ┌──────────────┐
                    │  PostgreSQL  │

  ├── Google Tasks
```

# 67. Infrastructure Evolution

Infrastructure may evolve only when justified by measurable requirements.

Examples:

```text
Higher traffic
→ more backend capacity

Long-running jobs
→ dedicated workers

Heavy synchronization
→ specialized job processing

Database bottleneck
→ database scaling

High-frequency realtime features
→ realtime infrastructure

Large search workload
→ dedicated search system
```

Infrastructure decisions must be documented through ADRs when they materially alter the architecture.

---

# 68. Deployment Invariant

The deployment system must preserve this fundamental property:

```text
New Code
   ↓
Validated
   ↓
Safely Deployed
   ↓
Observable
   ↓
Recoverable
```

A deployment is not complete merely because the application starts.

A production release is complete only when the deployed system has been validated, its critical behavior is observable, and a recovery path exists.

---

# 69. Final Deployment Principle

Workaholic should be deployed with the smallest reliable architecture that satisfies the current requirements while preserving clear paths for future scale.

The project must avoid two opposite failures:

```text
Under-engineering
→ fragile production system

Over-engineering
→ unnecessary cost and operational complexity
```

The deployment architecture therefore prioritizes:

* managed infrastructure;
* low initial cost;
* strong security;
* automated testing;
* simple operations;
* safe migrations;
* reliable recovery;
* independent client releases;
* observable production behavior;
* incremental scaling based on actual need.
