# `INTEGRATION-SPECIFICATION.md`

````markdown
# Workaholic Integration Specification

**Status:** FINAL  
**Document Type:** Engineering Specification  
**Scope:** Google Calendar, Google Tasks, Google Drive, OAuth, Notifications, External Services, Integration Adapters

---

## 1. Purpose

This document defines how Workaholic integrates with external services.

The primary integrations are:

- Google authentication;
- Google Calendar;
- Google Tasks;
- Google Drive;
- notification delivery services.

The integration architecture must preserve Workaholic's native domain model while allowing controlled interaction with external systems.

The core principle is:

```text
Workaholic Domain
       ↓
Integration Boundary
       ↓
External Provider
````

External APIs must not become the internal domain model.

---

# 2. Integration Principles

## 2.1 Native Domain Ownership

Workaholic owns its native domain objects.

Examples:

```text
Workaholic Task
Workaholic Event
Workaholic Note
Workaholic Project
Workaholic Reminder
```

External objects are representations or synchronized counterparts.

For example:

```text
Workaholic Event
       ↕
Google Calendar Event
```

Neither external identifiers nor external schemas should replace native Workaholic identifiers.

---

## 2.2 Native IDs and External IDs

Every synchronized external resource must preserve the distinction between:

```text
native_resource_id
external_resource_id
external_provider
```

Example:

```text
Workaholic Event
ID: wh_evt_123

Google Calendar Event
ID: google_evt_456
```

The values must never be assumed to be interchangeable.

---

# 3. Integration Boundary

External providers should be accessed through dedicated adapters.

Conceptually:

```text
Application Services
        │
        ▼
Integration Interfaces
        │
 ┌──────┼────────┐
 ▼      ▼        ▼
Google  Google   Google
Calendar Tasks   Drive
Adapter Adapter  Adapter
        │
        ▼
   Google APIs
```

Application domain logic should depend on integration interfaces rather than directly embedding provider-specific API calls throughout the application.

---

# 4. Authentication Versus Authorization

Workaholic must distinguish two separate concepts.

## Workaholic Authentication

Answers:

```text
Who is the user?
```

## Google Authorization

Answers:

```text
May Workaholic access this user's Google resources?
```

A user may be authenticated to Workaholic while having no Google integrations enabled.

Conversely, revoking Google authorization must not automatically delete the Workaholic account.

---

# 5. Google OAuth Lifecycle

The conceptual flow is:

```text
User
 ↓
Workaholic authentication
 ↓
Choose Google integration
 ↓
Google authorization
 ↓
Authorization callback
 ↓
Exchange authorization code
 ↓
Store required credentials securely
 ↓
Integration enabled
```

Credentials must be stored server-side where required.

---

# 6. OAuth Token Rules

The system must:

* protect refresh credentials;
* refresh expired access tokens;
* detect revoked authorization;
* handle invalid credentials;
* avoid exposing refresh credentials to clients;
* avoid logging tokens;
* securely remove credentials when the user disconnects an integration.

Access tokens should be treated as sensitive credentials even when they have limited lifetimes.

---

# 7. OAuth Scope Management

Workaholic should request the minimum Google scopes necessary for enabled functionality.

Conceptually:

```text
Calendar integration
→ Calendar-related permissions

Tasks integration
→ Tasks-related permissions

Drive integration
→ Drive-related permissions
```

A feature must not request unrelated permissions merely for future convenience.

---

# 8. Google Integration Configuration

Each environment must have independent Google OAuth configuration where practical.

At minimum, environment-specific configuration must distinguish:

```text
Development
Staging
Production
```

Redirect URIs must correspond to the appropriate environment.

Production OAuth configuration must never be used casually during local development.

---

# 9. Integration State

Each integration should have an explicit lifecycle.

Conceptually:

```text
DISCONNECTED
    ↓
AUTHORIZING
    ↓
CONNECTED
    ↓
SYNCING
    ↓
ERROR / REAUTH_REQUIRED
    ↓
CONNECTED
```

An integration may also be explicitly disabled by the user.

The UI must communicate when an integration requires reauthorization.

---

# 10. Google Calendar Integration

Google Calendar integration provides access to external calendars and events according to the user's granted permissions.

Supported behavior includes:

* importing Google calendar events;
* exporting Workaholic events to Google Calendar;
* updating synchronized events;
* deleting synchronized events;
* recurring events;
* timezone handling;
* synchronization state;
* conflict handling.

---

# 11. Calendar Source Identity

Every calendar must have a source/provenance.

Examples include:

```text
WORKAHOLIC
GOOGLE
COLLEGE
DAY_ORDER
HOLIDAY
BIRTHDAY
BOOKING
IMPORTED
```

The source determines which operations may safely affect the calendar.

A semester-ending operation must never assume that every event in the calendar belongs to the academic scheduling subsystem.

---

# 12. Google Calendar Mapping

A synchronization mapping should conceptually contain:

```text
provider
native_resource_type
native_resource_id
external_resource_type
external_resource_id
external_container_id
sync_state
last_synced_at
```

Additional metadata may be required depending on the implementation.

The mapping exists to establish identity across systems.

---

# 13. Calendar Synchronization Directions

Workaholic supports synchronization in both directions where configured.

```text
Workaholic
    ↕
Google Calendar
```

The synchronization engine must distinguish:

```text
Create
Update
Delete
No Change
Conflict
```

---

# 14. Workaholic-to-Google Create

When a configured Workaholic event is synchronized outward:

```text
Workaholic Event
      ↓
Google Calendar Adapter
      ↓
Google event creation
      ↓
External ID received
      ↓
Synchronization mapping stored
```

The native Workaholic event remains authoritative for its own identity.

---

# 15. Google-to-Workaholic Create

When a Google event is imported:

```text
Google Event
      ↓
Google Calendar Adapter
      ↓
External identity lookup
      ↓
Create/update Workaholic representation
      ↓
Store synchronization mapping
```

The imported event must retain Google provenance.

---

# 16. Calendar Update

Updates must determine whether the change originated from:

```text
Workaholic
Google
Synchronization process
```

The system must avoid interpreting its own synchronization write-back as an independent external modification.

---

# 17. Calendar Deletion

Deletion must distinguish:

```text
Delete native Workaholic event
Delete Google event
Remove synchronization relationship
```

These are not automatically equivalent.

The configured synchronization policy determines which side is affected.

---

# 18. External Calendar Deletion

If a synchronized Google event disappears externally, Workaholic must handle the condition according to synchronization policy.

Possible states include:

```text
Removed
Detached
Marked unavailable
Recreated
```

The selected behavior must be deterministic and documented by the synchronization implementation.

The system must never silently recreate deleted external resources without a defined rule.

---

# 19. Recurring Google Events

Recurring events require special handling.

The system must distinguish:

```text
Series
Occurrence
Exception
Cancellation
```

Synchronization must not flatten a recurring external series into unrelated events unless the internal representation explicitly requires it.

---

# 20. Calendar Timezones

External calendar timestamps must preserve the intended instant.

The system must correctly handle:

* timezone identifiers;
* UTC timestamps;
* all-day events;
* daylight-saving transitions;
* timezone conversion for display.

The user's configured timezone controls presentation where appropriate.

---

# 21. Google Tasks Integration

Google Tasks integration provides synchronization between Workaholic tasks and Google Tasks.

Supported behavior includes:

* create;
* update;
* completion;
* deletion;
* due dates;
* external changes;
* synchronization mappings;
* conflict handling.

---

# 22. Task Mapping

A synchronized task should conceptually map:

```text
Workaholic Task
      ↕
Google Task
```

The mapping must preserve both identities.

Google Tasks-specific fields must not become mandatory Workaholic fields unless the domain explicitly requires them.

---

# 23. Rich Metadata Preservation

Workaholic supports richer task metadata than external task systems may support.

When Google Tasks lacks an equivalent field, synchronization must not silently destroy native Workaholic information.

Example:

```text
Workaholic:
priority = HIGH
label = "Interview"
project = "Barclays"
dependency = Task B

Google Tasks:
may not support all of these fields
```

The unsupported Workaholic information remains native Workaholic state.

---

# 24. Task Completion Synchronization

Completion changes must be synchronized according to the configured two-way synchronization policy.

The system must distinguish:

```text
completed
incomplete
```

and must avoid repeatedly generating completion mutations caused solely by synchronization feedback.

---

# 25. Google Drive Integration

Google Drive acts as the external storage system for configured Workaholic attachments.

The relationship is:

```text
Workaholic Resource
       ↓
Attachment Relation
       ↓
Google Drive File
```

Workaholic stores the relationship metadata necessary to access the external file.

---

# 26. Drive File Ownership Principle

Workaholic must not assume ownership of the lifecycle of every Drive file merely because it references the file.

Removing an attachment from a Workaholic resource means:

```text
Remove Workaholic relationship
```

not:

```text
Delete Google Drive file
```

---

# 27. Explicit Drive Deletion

Actual Drive deletion must be a separate explicit operation.

The system must make the distinction clear:

```text
Detach from Workaholic
        ≠
Delete from Google Drive
```

This prevents accidental destruction of files that may be referenced elsewhere.

---

# 28. Drive Permission Failures

A Drive file may become:

* inaccessible;
* deleted;
* moved;
* permission-restricted;
* unavailable due to revoked Google authorization.

Workaholic must preserve the attachment relationship where appropriate while clearly representing that the external file is currently unavailable.

---

# 29. Drive Upload Flow

Conceptually:

```text
User selects file
      ↓
Validate upload
      ↓
Authorize Drive access
      ↓
Upload to Drive
      ↓
Receive Drive file identity
      ↓
Create Workaholic attachment relation
      ↓
Return attachment state
```

If the Workaholic relationship cannot be created after a successful Drive upload, recovery behavior must prevent an inconsistent user-visible state.

---

# 30. Integration Failure Model

External integrations must classify failures.

Examples:

```text
AUTHENTICATION_ERROR
AUTHORIZATION_ERROR
RATE_LIMIT
TIMEOUT
NETWORK_ERROR
NOT_FOUND
CONFLICT
INVALID_RESPONSE
PROVIDER_ERROR
UNKNOWN_ERROR
```

The application should translate provider-specific failures into stable internal error categories.

---

# 31. Retry Policy

Retryable errors may include:

* transient network failure;
* temporary provider failure;
* timeout;
* temporary rate limiting where appropriate.

Non-retryable errors include:

* invalid authorization;
* invalid resource;
* permanent validation failure.

Retries must use bounded attempts and appropriate backoff.

---

# 32. Idempotent Integration Operations

Operations that may be retried must avoid creating duplicate resources.

Examples:

```text
Create Google event
Create Google task
Upload attachment
Process synchronization mutation
```

The synchronization system should use stable identity and mutation information where required to detect repeated operations.

---

# 33. Rate Limiting

External APIs may impose quotas.

Workaholic must:

* respect provider rate limits;
* avoid unnecessary polling;
* batch operations where supported;
* back off when rate limited;
* expose synchronization health to the user where necessary.

Rate-limit failures must not be treated as permanent data failures.

---

# 34. Synchronization Scheduling

Synchronization may be triggered by:

* user action;
* application startup;
* background job;
* reconnect after offline operation;
* periodic synchronization;
* provider-supported event notification mechanisms where implemented.

The exact scheduling mechanism may evolve.

---

# 35. Synchronization Checkpoints

Synchronization should maintain enough state to determine:

```text
What was synchronized?
When?
From which provider?
What external revision/version was observed?
```

This prevents unnecessary full synchronization and supports reliable incremental updates where the provider permits it.

---

# 36. Conflict Handling

A conflict occurs when the same logical resource changes independently on both sides before synchronization can reconcile the changes.

Conceptually:

```text
Workaholic state
      │
      ├── changed locally
      │
      └── changed externally
               ↓
            CONFLICT
```

The resolution policy must be deterministic.

Possible strategies include:

* latest modification;
* Workaholic priority;
* provider priority;
* explicit user resolution;
* field-level merge.

The selected strategy must be defined by `SYNC-SPECIFICATION.md`.

---

# 37. Synchronization Loop Prevention

The system must prevent this cycle:

```text
Workaholic change
 ↓
Google update
 ↓
Google reports change
 ↓
Workaholic update
 ↓
Google update
 ↓
...
```

Synchronization metadata and revision/origin information must be used to identify changes produced by synchronization itself.

---

# 38. Duplicate Prevention

The following sequence must not produce duplicate logical resources:

```text
Create
Sync
Retry
Sync
Reconnect
Sync
```

The final state must contain one logical synchronized resource.

---

# 39. Disconnecting Google

When a user disconnects Google:

* Workaholic account remains active;
* native Workaholic resources remain;
* Google credentials are invalidated/removed as appropriate;
* synchronization stops;
* existing native resources are not automatically deleted;
* the user can reconnect later.

External data must not be destroyed merely because the integration is disconnected unless explicitly requested.

---

# 40. Reconnecting Google

After reconnection:

```text
Authorize
 ↓
Reconnect integration
 ↓
Discover external resources
 ↓
Restore valid mappings
 ↓
Synchronize according to policy
```

The system must avoid creating duplicates for resources that already have valid mappings.

---

# 41. Google Authorization Revocation

If Google authorization is revoked externally:

```text
API request fails
       ↓
Detect invalid authorization
       ↓
Mark integration as REAUTH_REQUIRED
       ↓
Stop futile retries
       ↓
Notify user appropriately
```

Native Workaholic data remains available.

---

# 42. Integration UI States

The UI must represent at least:

```text
Not connected
Connecting
Connected
Synchronizing
Synchronization failed
Reauthorization required
Disconnected
```

The user should be able to determine whether an integration is functioning without inspecting logs.

---

# 43. Manual Synchronization

Where supported, users should be able to explicitly request synchronization.

Manual synchronization must:

* execute through the same synchronization rules;
* respect authorization;
* remain idempotent;
* expose meaningful progress/error state where practical.

It must not create a separate synchronization implementation with different semantics.

---

# 44. Notification Integration

Notification delivery is treated as an external integration boundary.

The application domain determines:

```text
What
Who
When
Priority
```

The notification provider determines:

```text
How delivery occurs
```

Conceptually:

```text
Reminder Engine
      ↓
Notification Service
      ↓
Provider
      ↓
Device
```

---

# 45. Notification Provider Failures

The system must handle:

* unavailable provider;
* invalid device token;
* revoked permission;
* expired token;
* temporary delivery failure;
* permanent delivery failure.

Failure to deliver a notification must not corrupt the underlying reminder or task.

---

# 46. Notification Idempotency

A reminder must not produce duplicate notifications merely because:

* a background job runs twice;
* a device reconnects;
* synchronization retries;
* the application restarts.

Notification delivery should use stable notification identity where necessary.

---

# 47. Web Push

Where Web Push is supported:

* permission must be explicit;
* subscription state must be stored securely;
* invalid subscriptions must be removed;
* notification delivery must not expose private content to unauthorized recipients.

---

# 48. Android Push

Android push delivery must respect:

* notification permissions;
* device token lifecycle;
* application lifecycle;
* provider delivery constraints.

Push delivery complements local scheduling and must not be assumed to be the only reminder mechanism.

---

# 49. Windows Notifications

Windows notification integration must support the desktop reminder requirements.

The application must be able to associate a notification with the underlying Workaholic reminder so that interaction can:

* open the relevant resource;
* snooze;
* dismiss;
* complete where supported.

---

# 50. Integration Security

All external integrations must follow the security model defined in `PRIVACY-SECURITY.md`.

Required principles:

* least privilege;
* encrypted transport;
* secure credential storage;
* no secret logging;
* authorization checks;
* resource isolation;
* explicit user consent;
* revocable access.

---

# 51. External Data Minimization

Workaholic should retrieve and store only the external data required for its functionality.

External API responses must not automatically become permanent copies of all provider data.

The system should avoid unnecessary retention of:

* provider metadata;
* unrelated calendar information;
* unnecessary file metadata;
* unused user profile information.

---

# 52. External Provider Outage

If a provider becomes unavailable:

```text
Workaholic native functionality
→ remains available where possible

External integration
→ enters degraded/error state
```

A Google outage must not make native Workaholic tasks unusable.

---

# 53. Integration Observability

Integration operations should record safe diagnostic information such as:

```text
provider
operation
resource type
result
duration
error category
retry count
timestamp
```

Sensitive credentials and private resource content must not be logged.

---

# 54. Integration Testing

Every integration must have:

### Unit tests

For:

* data transformations;
* provider response parsing;
* error mapping.

### Integration tests

For:

* authentication;
* API requests;
* synchronization;
* provider failures.

### E2E tests

For:

* user authorization;
* visible synchronization state;
* complete user workflows.

### Regression tests

For every significant synchronization defect.

---

# 55. Mock Provider Contract

Provider mocks must represent realistic provider behavior.

Mocks should support:

```text
Success
Timeout
Rate limit
Unauthorized
Not found
Conflict
Malformed response
Temporary outage
```

Tests must not rely exclusively on idealized successful responses.

---

# 56. Provider Adapter Contract

Each external adapter should conceptually provide operations such as:

```text
authenticate
refreshAuthorization
create
get
update
delete
list
synchronize
disconnect
```

The exact method names are implementation-specific.

The important property is that provider-specific details remain behind the integration boundary.

---

# 57. Integration Data Flow

The general integration flow is:

```text
User Action / Background Job
             ↓
Application Service
             ↓
Integration Interface
             ↓
Provider Adapter
             ↓
External API
             ↓
Provider Response
             ↓
Adapter Normalization
             ↓
Application Service
             ↓
Native Database State
```

External provider response formats must not leak unnecessarily into the rest of the application.

---

# 58. Integration and Transactions

External API calls cannot generally participate in the same database transaction as Workaholic's database.

Therefore operations must account for partial failure.

Example:

```text
Google event creation succeeds
        ↓
Database mapping creation fails
```

The recovery strategy must reconcile the resulting state rather than assuming atomicity across systems.

---

# 59. Partial Failure Recovery

For cross-system operations:

```text
Database
   +
External Provider
```

the system must explicitly consider:

```text
Both succeed
Database succeeds / provider fails
Provider succeeds / database fails
Both fail
```

Each important operation must have a recoverable outcome.

---

# 60. Integration Data Ownership Matrix

| Resource            | Native Owner | External Representation            |
| ------------------- | ------------ | ---------------------------------- |
| Workaholic Task     | Workaholic   | Google Task                        |
| Workaholic Event    | Workaholic   | Google Calendar Event              |
| Native Calendar     | Workaholic   | Google Calendar where synchronized |
| Attachment relation | Workaholic   | Google Drive File                  |
| Drive File          | Google Drive | Workaholic reference               |
| Reminder            | Workaholic   | Notification provider delivery     |

This matrix prevents accidental transfer of ownership semantics.

---

# 61. Integration Scope Boundary

The following are explicitly outside the current integration implementation unless separately approved:

* arbitrary third-party calendar providers;
* arbitrary task providers;
* arbitrary cloud drives;
* enterprise identity providers beyond the defined authentication system;
* chat providers;
* AI providers.

The architecture should permit future adapters without requiring them now.

---

# 62. Future Integration Extensibility

Future providers should fit the same general model:

```text
Native Workaholic Resource
          ↕
Provider Adapter
          ↕
External Resource
```

A new provider should not require rewriting the native domain model merely because its API differs.

---

# 63. AI Integration Boundary

AI is Coming Soon and is not part of the current implementation.

When introduced, AI must interact through controlled application actions:

```text
LLM
 ↓
Validated Action
 ↓
Application Service
 ↓
Authorization
 ↓
Business Rules
 ↓
Database
```

The LLM must never receive unrestricted database access.

---

# 64. Chat Integration Boundary

Chat is Coming Soon and is not part of the current implementation.

Future chat infrastructure must not be introduced into the initial deployment solely to anticipate this feature.

The current integration architecture should simply avoid preventing its later addition.

---

# 65. Integration Release Checklist

Before releasing a change to an external integration:

```text
[ ] Authorization tested
[ ] Credential lifecycle tested
[ ] Success path tested
[ ] Failure path tested
[ ] Retry behavior tested
[ ] Idempotency tested
[ ] Duplicate prevention tested
[ ] Conflict behavior tested
[ ] External deletion tested where applicable
[ ] Disconnect/reconnect tested
[ ] Privacy/security verified
[ ] Relevant E2E tests passing
[ ] Regression tests passing
```

---

# 66. Final Integration Invariant

External services extend Workaholic.

They do not redefine Workaholic.

The architecture must therefore preserve:

```text
                 WORKAHOLIC
              Native Domain
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      Google      Google      Google
     Calendar      Tasks       Drive
```

with explicit identity mappings, controlled authorization, deterministic synchronization, failure recovery, and clear ownership semantics.

The system must remain useful when an external provider is unavailable, and disconnecting an integration must not destroy native Workaholic data.

---

# 67. Final Principle

The integration layer must make external systems feel like reliable extensions of Workaholic without allowing external API limitations, identifiers, failures, or schemas to leak uncontrollably into the core domain.

The desired property is:

```text
External Provider Changes
          ↓
      Adapter Layer
          ↓
Minimal Impact on Native Domain
```

This boundary is a core architectural protection for Workaholic's long-term maintainability.
