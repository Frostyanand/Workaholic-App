# `PERMISSIONS-MODEL.md`

**Status:** FINAL
**Version:** 1.0
**Product:** Workaholic
**Scope:** Authentication, authorization, workspaces, roles, permissions, trusted relationships, resource access, public access, and access revocation

---

## 1. Purpose

The Workaholic Permissions Model defines who may access which resources and what operations they may perform.

The system MUST enforce authorization independently of authentication.

```text
Authentication
= Who is this user?

Authorization
= What is this user allowed to do?
```

Successfully signing in MUST NOT imply unrestricted access to Workaholic resources.

---

# 2. Authorization Principles

The system MUST follow these principles:

1. **Deny by default.**
2. **Authorize server-side.**
3. **Scope access to the appropriate workspace/resource.**
4. **Separate viewing from modification.**
5. **Separate resource access from administrative access.**
6. **Do not trust client-provided permissions.**
7. **Revocation MUST take effect server-side.**
8. **Public access MUST use an explicit public-access mechanism.**
9. **Trusted relationships MUST NOT automatically grant broad access.**
10. **External-provider authorization MUST remain separate from Workaholic authorization.**

---

# 3. Authorization Hierarchy

The primary access hierarchy is:

```text
User
  ↓
Workspace Membership
  ↓
Role / Explicit Permissions
  ↓
Resource Access
  ↓
Operation
```

Additional access mechanisms include:

```text
Trusted Relationship
Public Calendar Link
External Provider Authorization
```

These MUST remain conceptually distinct.

---

# 4. User Identity

A Workaholic User represents an authenticated application identity.

A user MAY authenticate through:

* Google
* Future supported identity providers
* Other supported authentication mechanisms

The authentication provider does not determine the user's Workaholic permissions.

---

# 5. External Identity

An external identity represents the relationship between a Workaholic user and an identity provider.

Example:

```text
Workaholic User
      │
      └── Google Identity
```

The external identity MUST NOT itself contain workspace authorization.

---

# 6. Google API Authorization

Google API authorization is a separate concern from Workaholic login.

Example:

```text
Google Sign-In
     ↓
Authenticate Workaholic user

Google Calendar permission
     ↓
Authorize Workaholic to access Google Calendar
```

A user may therefore:

```text
Be logged into Workaholic
+
Not have authorized Google Calendar
```

Both states are valid.

---

# 7. Workspace

A Workspace is the primary multi-tenant authorization boundary.

Resources SHOULD belong to a workspace where appropriate.

Examples:

```text
Workspace
├── Members
├── Projects
├── Boards
├── Tasks
├── Calendars
├── Notes
└── Collaboration resources
```

Users MUST NOT gain access to resources in another workspace merely because they know the resource ID.

---

# 8. Workspace Membership

A user obtains workspace-level access through a membership.

Conceptually:

```text
User
   ↕
Workspace Membership
   ↕
Workspace
```

Membership MUST identify:

* User
* Workspace
* Role
* Membership status
* Relevant permission overrides
* Creation/update metadata

---

# 9. Membership States

Initial membership states:

```text
INVITED
ACTIVE
SUSPENDED
REMOVED
```

Only an appropriate active membership grants normal workspace access.

---

# 10. Roles

Roles provide reusable permission bundles.

Initial conceptual roles:

```text
OWNER
ADMIN
MEMBER
VIEWER
```

The exact default role definitions MAY evolve.

Roles MUST NOT be treated as the only possible authorization mechanism.

Granular permissions may override or supplement role capabilities.

---

# 11. Owner

The workspace owner has the highest workspace-level authority.

The owner MAY generally:

* Manage workspace settings
* Manage members
* Assign roles
* Manage permissions
* Manage important integrations
* Transfer ownership where supported
* Delete/archive the workspace where supported

Owner capabilities MUST still be implemented through explicit authorization rules.

---

# 12. Admin

An administrator MAY manage operational aspects of a workspace without necessarily possessing every ownership operation.

For example:

```text
Admin:
Manage members = YES
Manage projects = YES
Transfer ownership = NO
Delete workspace = NO
```

---

# 13. Member

A normal member MAY access resources according to workspace and resource permissions.

Typical capabilities include:

* View permitted projects
* Create permitted tasks
* Edit permitted tasks
* Comment
* Participate in collaboration

A member MUST NOT automatically obtain administrative rights.

---

# 14. Viewer

A viewer generally receives read-only access.

For example:

```text
View project = YES
View tasks = YES
Edit task = NO
Delete task = NO
Manage members = NO
```

---

# 15. Permission Model

Permissions SHOULD use stable capability identifiers.

Examples:

```text
workspace.view
workspace.manage
workspace.members.view
workspace.members.manage

project.view
project.create
project.edit
project.delete
project.manage_members

board.view
board.create
board.edit
board.delete

task.view
task.create
task.edit
task.delete
task.assign

calendar.view
calendar.create
calendar.edit
calendar.delete
calendar.share

event.view
event.create
event.edit
event.delete

note.view
note.create
note.edit
note.delete

booking.view
booking.manage

integration.view
integration.manage

public_calendar.manage

trusted_relationship.view
trusted_relationship.manage
```

Permission names MUST remain stable once used by implementation.

---

# 16. Permission Granularity

Authorization SHOULD support multiple levels:

```text
Workspace
   ↓
Project
   ↓
Board
   ↓
Task
```

and:

```text
Workspace
   ↓
Calendar
   ↓
Event
```

A user with broad workspace membership MUST NOT automatically receive access to every private resource when the resource has stricter access rules.

---

# 17. Resource-Level Authorization

The server MUST verify access to the target resource.

Example:

```text
GET /tasks/task_123
```

The server MUST verify:

```text
Authenticated user
        ↓
Workspace membership
        ↓
Task workspace
        ↓
Task access
```

It MUST NOT rely on:

```text
"Client says the task belongs to me."
```

---

# 18. Create Authorization

Creation requires permission for the parent scope.

Example:

```text
Create Task
    ↓
Can user create tasks in workspace/project?
```

A user who can view a project does not automatically have permission to create tasks there.

---

# 19. Edit Authorization

Editing requires explicit edit capability.

```text
View ≠ Edit
```

A user may therefore have:

```text
task.view = YES
task.edit = NO
```

---

# 20. Delete Authorization

Deletion SHOULD generally require a stronger permission than editing.

For example:

```text
task.edit
task.delete
```

are separate capabilities.

Soft deletion/trash SHOULD be preferred for important resources.

---

# 21. Assignment Authorization

Assigning a task to another user MUST require appropriate permission.

The system MUST verify that the proposed assignee is eligible for the relevant workspace/project/resource.

A user MUST NOT be able to assign arbitrary external users merely by supplying an identifier.

---

# 22. Project Membership

Projects MAY have explicit membership.

Example:

```text
Workspace:
20 users

Project:
5 members
```

Project-specific access MAY therefore be narrower than workspace membership.

---

# 23. Board Permissions

Boards MAY inherit permissions from their project/workspace.

Additional board-specific restrictions MAY be supported.

A user who can view a project does not automatically gain board administration privileges.

---

# 24. Task Permissions

Task access SHOULD consider:

1. Workspace membership
2. Project membership
3. Board permissions
4. Task-specific restrictions where supported

Task relationships MUST NOT leak information about inaccessible tasks.

Example:

```text
Task A:
Visible

Depends on:
Task B

Task B:
Private
```

The UI MUST NOT expose Task B's confidential details.

---

# 25. Calendar Permissions

Calendar permissions include:

```text
calendar.view
calendar.create
calendar.edit
calendar.delete
calendar.share
calendar.manage_visibility
calendar.manage_public_link
```

Calendar access MUST be independently evaluated.

---

# 26. Event Permissions

An event inherits appropriate calendar access but MAY have additional restrictions.

For example:

```text
Calendar:
View access

Event:
Private
```

A user may see that something occupies time without seeing its details.

---

# 27. Private Events

Private event access MUST protect:

* Title
* Description
* Attendees
* Location
* Related tasks
* Related projects
* Attachments
* Internal metadata

A user with availability-only access SHOULD see only:

```text
Busy
10:00 → 11:00
```

---

# 28. Notes Permissions

Notes SHOULD support:

```text
note.view
note.create
note.edit
note.delete
note.share
```

A note relationship MUST NOT grant access to the referenced resource automatically.

---

# 29. Attachments

Attachment access MUST be constrained by the parent resource.

Example:

```text
Private Task
   ↓
Private Attachment
```

A user cannot bypass task authorization by directly requesting the attachment.

---

# 30. Google Drive Authorization

Drive access has two independent layers:

```text
Workaholic authorization
+
Google Drive authorization
```

A user may have permission to attach files in Workaholic while still lacking Google Drive authorization.

The system MUST provide an appropriate authorization flow rather than treating one as the other.

---

# 31. Drive File Privacy

Workaholic MUST NOT expose a Drive file to an unauthorized Workaholic user merely because the attachment record exists.

The system MUST validate the relevant Workaholic resource permission.

---

# 32. Trusted Relationships

Trusted sharing is a separate authorization mechanism intended for explicitly trusted people.

Examples may include:

* Family members
* Personal assistants
* Other trusted users

A trusted relationship MUST NOT be equivalent to workspace administrator access.

---

# 33. Trusted Relationship Model

Conceptually:

```text
Owner User
    ↕
Trusted Relationship
    ↕
Trusted User
```

The relationship SHOULD contain:

* Owner
* Trusted user
* Status
* Granted permissions
* Creation time
* Revocation information
* Optional expiry
* Relevant metadata

---

# 34. Trusted Permissions

Trusted permissions MUST be granular.

Examples:

```text
trusted.calendar.view
trusted.reminders.receive
trusted.tasks.view
trusted.tasks.edit
trusted.availability.view
```

A trusted relationship MAY grant one capability without granting others.

---

# 35. Trusted Sharing Example

Valid configuration:

```text
Trusted User A:
View selected calendar = YES
Receive shared reminders = YES
Edit tasks = NO
View private notes = NO
```

The user receives only those permissions.

---

# 36. Share Codes

Share codes MAY be used for onboarding a trusted relationship.

A share code MUST NOT become a permanent authentication credential.

The conceptual flow is:

```text
Owner generates code
       ↓
Trusted person enters code
       ↓
Identity/account established
       ↓
Relationship created
       ↓
Code expires / becomes invalid
```

---

# 37. Share Code Security

Share codes SHOULD be:

* Random
* Short-lived
* Single-use where practical
* Rate-limited
* Revocable
* Stored securely
* Invalidated after successful redemption

A leaked historical code MUST NOT provide indefinite access.

---

# 38. Trusted Relationship Revocation

The owner MUST be able to revoke a trusted relationship.

Revocation MUST:

1. Prevent new access.
2. Prevent future protected notification delivery.
3. Invalidate or restrict relevant trusted sessions.
4. Remove effective permissions.
5. Preserve owner-owned data.

Revocation MUST NOT delete the owner's underlying resources.

---

# 39. Device and Session Authorization

A device and a session are different entities.

```text
Device
= known client/device

Session
= active authenticated access instance
```

A single device MAY have multiple sessions.

---

# 40. Session Management

Users SHOULD be able to view:

* Device
* Platform
* Last active time
* Session creation time
* Approximate location information where appropriate
* Session status

Users SHOULD be able to revoke:

```text
One session
```

or:

```text
All other sessions
```

---

# 41. Public Sessions

Public/temporary access sessions MAY use configurable expiration such as:

```text
12 hours
24 hours
```

The session MUST expire automatically.

Expiration MUST be enforced server-side.

---

# 42. Persistent Trusted Devices

Trusted devices MAY have persistent access where explicitly authorized.

Persistent access MUST still be revocable.

A persistent device MUST NOT become an irrevocable credential.

---

# 43. Public Calendar Access

Public calendar access is not normal user authorization.

It uses a dedicated:

```text
Public Calendar Link
```

The link MUST expose only the configured privacy projection.

It MUST NOT expose arbitrary authenticated resources.

---

# 44. Public Booking Access

Public booking pages MAY allow unauthenticated guests to:

* View bookable availability
* Select a booking type
* Enter required information
* Create a booking
* Cancel/reschedule according to policy

Guest access MUST remain constrained to the booking page.

A booking guest MUST NOT gain Workaholic account access merely by booking.

---

# 45. Booking Privacy

Guests MUST NOT see private calendar details used to calculate availability.

Example:

```text
Private event:
13:00 → 14:00

Booking page:
13:00 unavailable
```

The reason remains private.

---

# 46. External Provider Permissions

External providers have their own authorization systems.

For Google:

```text
Workaholic permissions
        ≠
Google Calendar permissions
        ≠
Google Drive permissions
        ≠
Google Tasks permissions
```

Workaholic MUST maintain these boundaries.

---

# 47. Permission Inheritance

Permissions MAY inherit downward.

Example:

```text
Workspace
   ↓
Project
   ↓
Task
```

However, inheritance MUST be explicit and predictable.

The system MUST NOT create accidental access through unrelated relationships.

---

# 48. Explicit Overrides

The permission system MAY support explicit membership permissions.

Example:

```text
Role:
MEMBER

Override:
calendar.manage_public_link = YES
```

Overrides MUST be auditable.

---

# 49. Deny Semantics

Where explicit deny rules are supported, their precedence MUST be deterministic.

The initial implementation SHOULD avoid unnecessary deny complexity.

A simpler model of:

```text
Role grants
+
Explicit grants
+
Resource restrictions
```

is preferred unless real requirements demand explicit denies.

---

# 50. Permission Evaluation

A conceptual authorization function is:

```text
authorize(
    actor,
    action,
    resource
)
```

It MUST evaluate:

```text
Authentication
      ↓
Account status
      ↓
Workspace membership
      ↓
Role
      ↓
Explicit permissions
      ↓
Resource ownership/access
      ↓
Relationship-specific rules
      ↓
Resource state
      ↓
Allow / Deny
```

---

# 51. Authorization Must Be Server-Side

The client MAY hide unavailable controls for UX.

However:

```text
Hidden button
≠
Security
```

Every protected API operation MUST independently enforce authorization.

---

# 52. IDOR Prevention

Resource identifiers MUST NOT function as access credentials.

Example:

```text
User A requests:
task_B
```

The server MUST check authorization even if:

```text
task_B
```

is a valid identifier.

This prevents insecure direct object reference vulnerabilities.

---

# 53. Cross-Workspace Isolation

If:

```text
User U
Workspace A

Resource:
Workspace B
```

the request MUST be rejected unless an explicit cross-workspace permission mechanism exists.

Resource IDs must not permit cross-tenant discovery.

---

# 54. Authorization Through Relationships

Relationships do not automatically grant access.

For example:

```text
Task A
linked to
Project B
```

does not mean anyone who can view Task A can automatically view every Project B detail.

Likewise:

```text
Event A
linked to
Private Task B
```

does not expose Task B.

---

# 55. Comments and Mentions

A user MUST have appropriate access to the parent resource before:

* Adding comments
* Reading comments
* Mentioning users
* Reading mentions

A mention MUST NOT be used to reveal a private resource.

---

# 56. Activity Logs

Activity entries MUST obey resource visibility.

An activity log entry such as:

```text
Anurag edited confidential project
```

must not be visible to someone who cannot access that project if that fact itself is confidential.

---

# 57. Search Authorization

Search results MUST be authorization-filtered.

The system MUST NOT:

```text
Search all resources
↓
Filter only after returning results to client
```

Sensitive resources must never be exposed through search indexing or result payloads.

---

# 58. Notifications and Authorization

Notification generation and delivery MUST respect current authorization.

If access is revoked before delivery:

```text
Pending notification
       ↓
Permission re-check
       ↓
No protected delivery
```

A notification cannot become a privilege-escalation channel.

---

# 59. Sync Authorization

Synchronization MUST respect current permissions.

If a device loses access to a workspace:

```text
Workspace access revoked
       ↓
Future synchronization denied
       ↓
Protected local data reconciled/invalidated
```

The client MUST NOT continue receiving new protected records.

---

# 60. Offline Authorization

Offline clients cannot independently redefine server permissions.

Local cached permissions MAY be used for UX, but server authorization remains authoritative.

Upon reconnection:

```text
Local state
   ↓
Server authorization
   ↓
Accept / reject / reconcile
```

---

# 61. Permission Revocation Propagation

Revocation MUST propagate across:

* Web
* Windows
* Android
* Active sessions
* Trusted relationships
* Sync queues
* Notifications
* Public projections
* Relevant cached authorization state

Exact propagation mechanisms are defined by the synchronization architecture.

---

# 62. Stale Permission Handling

If a client operates using stale permissions:

```text
Client thinks:
EDIT = allowed

Server:
EDIT = revoked
```

the server MUST reject the mutation.

The client SHOULD then refresh authorization state and update its UI.

---

# 63. Authentication Failure vs Authorization Failure

The UI MUST distinguish:

### Authentication failure

```text
You need to sign in.
```

### Authorization failure

```text
You do not have permission to perform this action.
```

These are fundamentally different conditions.

---

# 64. Sensitive Administrative Operations

High-impact operations SHOULD require stronger authorization.

Examples:

* Delete workspace
* Transfer ownership
* Manage members
* Change security settings
* Revoke all sessions
* Manage integrations
* Regenerate public links

Additional confirmation MAY be required.

---

# 65. Account Deletion

Account deletion MUST not be equivalent to merely revoking a session.

Account deletion affects the user's identity and associated data lifecycle.

The operation MUST follow the application's retention, ownership, collaboration, and legal requirements.

---

# 66. Workspace Ownership

Ownership transfer MUST be explicit.

The system MUST prevent accidental loss of ownership.

A workspace MUST NOT enter a state with no valid owner unless explicitly supported by the domain model.

---

# 67. Role Changes

Role changes MUST take effect for future authorization decisions.

Example:

```text
ADMIN
 ↓
MEMBER
```

The user MUST no longer be able to perform administrator-only operations after the change is effective.

---

# 68. Permission Auditability

Security-sensitive permission changes SHOULD create activity/audit records.

Examples:

```text
Member invited
Role changed
Permission granted
Permission revoked
Trusted relationship created
Trusted relationship revoked
Session revoked
Public link regenerated
```

---

# 69. Rate Limiting

Sensitive operations SHOULD be rate-limited, including:

* Login-related flows
* Share-code redemption
* Public calendar access
* Booking endpoints
* Permission changes
* Session management
* Public APIs

Rate limiting MUST NOT be implemented in a way that silently bypasses authorization.

---

# 70. Security Boundaries

The major Workaholic security boundaries are:

```text
                 ┌─────────────────┐
                 │ Authentication  │
                 └────────┬────────┘
                          ↓
                 ┌─────────────────┐
                 │ Workaholic User │
                 └────────┬────────┘
                          ↓
                 ┌─────────────────┐
                 │    Workspace    │
                 └────────┬────────┘
                          ↓
              ┌───────────┼────────────┐
              ↓           ↓            ↓
           Project      Calendar      Notes
              ↓           ↓
            Tasks        Events
              │           │
              └─────┬─────┘
                    ↓
              Resource Access

Additional isolated paths:
Trusted Relationship
Public Calendar Link
Booking Guest
Google OAuth/API Access
```

# 71. Permission Acceptance Tests

At minimum:

### PERM-T01

Unauthenticated user cannot access protected API.

### PERM-T02

Authenticated user cannot access another workspace.

### PERM-T03

Viewer cannot edit a task.

### PERM-T04

Member cannot perform owner-only operation.

### PERM-T05

Project-restricted user cannot access unrelated private project.

### PERM-T06

Private event details are hidden from availability-only users.

### PERM-T07

Attachment cannot bypass parent-resource authorization.

### PERM-T08

Search cannot expose unauthorized resources.

### PERM-T09

Notification cannot expose unauthorized resource details.

### PERM-T10

Revoked trusted relationship loses future access.

### PERM-T11

Trusted user receives only explicitly granted permissions.

### PERM-T12

Share code expires/is invalidated according to policy.

### PERM-T13

Revoked session cannot continue making authenticated requests.

### PERM-T14

Public calendar exposes only the privacy projection.

### PERM-T15

Public calendar revocation invalidates access.

### PERM-T16

Booking guest cannot access private calendar details.

### PERM-T17

Google API authorization does not grant Workaholic workspace permissions.

### PERM-T18

Workaholic workspace permissions do not grant Google API access.

### PERM-T19

Offline stale permissions cannot bypass server authorization.

### PERM-T20

Role downgrade removes previously available privileged operations.

# 72. Final Authorization Model

```text
                    ┌───────────────┐
                    │     User      │
                    └───────┬───────┘
                            │
                     authenticated
                            │
                            ▼
                    ┌───────────────┐
                    │   Workspace   │
                    │   Membership │
                    └───────┬───────┘
                            │
                    Role + Permissions
                            │
                            ▼
                    ┌───────────────┐
                    │    Resource   │
                    └───────┬───────┘
                            │
                     Requested Action
                            │
                            ▼
                    ┌───────────────┐
                    │ Authorization │
                    │    Decision   │
                    └───────┬───────┘
                       ┌────┴────┐
                       ▼         ▼
                     ALLOW      DENY
```

The central principle is:

> **Authentication establishes identity. Authorization establishes authority. Every protected Workaholic operation must independently verify that authority within the correct security boundary.**

This model also ensures that **workspace collaboration, trusted sharing, public calendars, bookings, Google integrations, notifications, offline synchronization, and future chat/AI capabilities can coexist without accidentally turning one access mechanism into another.**
