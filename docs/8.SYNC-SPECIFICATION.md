# 1. Purpose

This document defines synchronization behavior for Workaholic.

Synchronization exists across three primary boundaries:

```text
Device ↔ Workaholic Cloud
Workaholic Cloud ↔ Other Devices
Workaholic Cloud ↔ External Providers
````

The synchronization system MUST support:

* offline operation
* local persistence
* queued mutations
* reliable upload
* incremental download
* idempotency
* ordering
* version tracking
* conflict detection
* conflict resolution
* deletion propagation
* retries
* multi-device synchronization
* Google Calendar synchronization
* Google Tasks synchronization
* synchronization failure recovery

---

# 2. Synchronization Philosophy

Workaholic follows a local-first, cloud-synchronized model.

The conceptual flow is:

```text
USER
 ↓
LOCAL STATE
 ↓
MUTATION QUEUE
 ↓
CLOUD
 ↓
OTHER DEVICES
```

The cloud is the shared durable state across devices.

The client remains capable of useful operation when temporarily disconnected.

---

# 3. Important Terminology

## 3.1 Local State

Persistent representation of Workaholic data on a client device.

---

## 3.2 Cloud State

Authoritative Workaholic state stored in PostgreSQL and exposed through the backend.

---

## 3.3 Mutation

A requested change to domain state.

Examples:

```text
Create Task
Update Task
Complete Task
Delete Task
Move Task
Create Event
Update Reminder
```

---

## 3.4 Sync Operation

A persisted representation of a mutation waiting to be synchronized.

---

## 3.5 Version

A mechanism used to determine whether the state being modified is newer, older, or concurrent relative to another state.

---

## 3.6 Conflict

A situation where two independently produced changes cannot safely be merged without applying a defined conflict policy.

---

## 3.7 Tombstone

A durable indication that an entity was deleted.

Tombstones are required where deletion must propagate to devices that may have been offline.

---

# 4. Source of Truth

For native Workaholic data:

```text
PostgreSQL
    ↓
Authoritative cloud state
```

For local device operation:

```text
Client Database
    ↓
Local working state
```

For external objects:

```text
Google Calendar → Google
Google Tasks    → Google
Google Drive    → Google Drive
```

External systems remain authoritative for their external objects.

---

# 5. Native and External Synchronization

The system distinguishes:

```text
Native Synchronization
    Device ↔ Workaholic

External Synchronization
    Workaholic ↔ Google
```

These MUST NOT be treated as one indistinguishable process.

---

# 6. Basic Local Mutation Flow

When a user performs a mutation:

```text
User Action
    ↓
Validate locally
    ↓
Apply local state
    ↓
Persist local state
    ↓
Create Sync Operation
    ↓
Queue
```

The UI MAY immediately reflect the mutation.

---

# 7. Online Mutation Flow

When network connectivity is available:

```text
User Action
    ↓
Local persistence
    ↓
Mutation queued
    ↓
Upload
    ↓
Server validates
    ↓
Server applies mutation
    ↓
Server returns canonical state
    ↓
Client reconciles local state
    ↓
Mutation marked completed
```

---

# 8. Offline Mutation Flow

```text
User Action
    ↓
Local validation
    ↓
Local persistence
    ↓
Mutation queued
    ↓
No network
    ↓
Continue using application
    ↓
Network returns
    ↓
Synchronize
```

The mutation MUST remain durable across application restarts.

---

# 9. Local Mutation Queue

Each client MUST maintain a persistent mutation queue.

Conceptually:

```text
Sync Operation
├── id
├── device_id
├── entity_type
├── entity_id
├── operation_type
├── payload
├── base_version
├── idempotency_key
├── created_at
├── status
└── attempt metadata
```

The physical representation is implementation-specific.

---

# 10. Mutation States

A mutation MAY progress through:

```text
PENDING
   ↓
UPLOADING
   ↓
ACCEPTED
```

or:

```text
PENDING
   ↓
UPLOADING
   ↓
RETRYABLE_FAILURE
   ↓
PENDING
```

or:

```text
PENDING
   ↓
CONFLICT
```

or:

```text
PENDING
   ↓
PERMANENT_FAILURE
```

The user MUST be able to understand unresolved synchronization failures where they affect application state.

---

# 11. Idempotency

Every mutation that may be retried MUST have a stable idempotency key.

Example:

```text
device A
mutation ID = M123
```

If the same request reaches the server twice:

```text
M123
M123
```

the server MUST NOT create two Tasks or otherwise duplicate the operation.

---

# 12. Mutation Ordering

Mutations originating from one device SHOULD retain causal ordering.

Example:

```text
M1: Create Task
M2: Rename Task
M3: Complete Task
```

The server SHOULD process them in a manner that preserves their causal relationship.

A later mutation MUST NOT be applied against a state that makes its earlier prerequisite invalid without explicit resolution.

---

# 13. Dependency Ordering

If:

```text
M1 creates entity X
M2 modifies entity X
```

then:

```text
M1 → M2
```

M2 MUST NOT be submitted independently in a way that assumes X exists when X has not yet been created server-side.

---

# 14. Mutation Batching

The client MAY batch multiple mutations.

Batching MUST NOT alter their semantic ordering.

A batch MAY contain:

```text
Create Task
Create Label
Attach Label
```

provided dependency ordering remains valid.

---

# 15. Server Synchronization Endpoint

The exact API is defined separately, but the logical operation MUST support:

```text
Upload pending mutations
       ↓
Validate
       ↓
Apply
       ↓
Return:
    ├── Accepted mutations
    ├── Conflicts
    ├── Rejections
    └── Canonical changes
```

---

# 16. Incremental Download

Clients SHOULD avoid downloading the entire database on every synchronization.

Conceptually:

```text
Client last_sync_token
        ↓
Server
        ↓
Changes since token
        ↓
Client
```

The exact cursor/token implementation is deferred to the API specification.

---

# 17. Change Feed

The backend SHOULD expose a durable mechanism for determining changes relevant to a client.

Changes may represent:

* creation
* update
* deletion
* relationship changes
* permission changes

Only resources authorized for the client may be returned.

---

# 18. Initial Synchronization

For a new device:

```text
Authenticate
    ↓
Register device
    ↓
Download authorized baseline state
    ↓
Store locally
    ↓
Receive synchronization cursor
    ↓
Enable incremental synchronization
```

---

# 19. Re-Synchronization

After prolonged disconnection:

```text
Connect
    ↓
Upload local mutations
    ↓
Download remote changes
    ↓
Resolve conflicts
    ↓
Update local state
    ↓
Advance synchronization cursor
```

---

# 20. Server Versioning

The server SHOULD maintain a mechanism allowing clients to detect stale mutations.

Conceptually:

```text
Entity version = 17

Client mutation:
base_version = 16
```

If the authoritative object is now version 18, the mutation may require conflict evaluation.

---

# 21. Optimistic Concurrency

Workaholic SHOULD use optimistic concurrency for normal mutable resources.

Conceptually:

```text
Client reads:
Task version = 10

Client edits:
"Review SQL"

Server:
Current version = 10

→ Apply
→ New version = 11
```

If:

```text
Client base = 10
Server current = 11
```

the system evaluates whether the mutation can be safely merged.

---

# 22. Field-Level Merge

Some changes MAY be merged when they affect independent properties.

Example:

```text
Device A:
priority = High

Device B:
description = "Review joins"
```

If no business rule conflicts exist, the system MAY produce:

```text
priority = High
description = "Review joins"
```

---

# 23. Same-Field Conflict

Example:

```text
Device A:
priority = High

Device B:
priority = Low
```

This is a true concurrent conflict if neither mutation is causally newer.

The conflict policy MUST determine the resulting state.

---

# 24. Conflict Categories

Conflicts SHOULD be classified conceptually as:

```text
NON_CONFLICTING
MERGEABLE
CONFLICTING
INVALID
```

---

# 25. Non-Conflicting Changes

Independent changes SHOULD be automatically merged.

Example:

```text
Device A:
Task title changed

Device B:
Task priority changed
```

Result:

```text
new title
+
new priority
```

---

# 26. Mergeable Relationship Changes

Independent relationship changes SHOULD be merged when safe.

Example:

```text
Device A adds Label A
Device B adds Label B
```

Result:

```text
Label A
Label B
```

The exact semantics depend on the relationship type.

---

# 27. Destructive Conflicts

Destructive operations require special handling.

Example:

```text
Device A:
Delete Task

Device B:
Edit Task
```

The synchronization system MUST have an explicit policy for this case.

It MUST NOT accidentally resurrect deleted data or silently lose a meaningful edit without following that policy.

---

# 28. Delete vs Delete

If two devices delete the same object:

```text
Device A → Delete
Device B → Delete
```

the resulting authoritative state SHOULD remain deleted.

---

# 29. Delete vs Update

Default conceptual behavior:

```text
Delete
   vs
Update
```

requires conflict evaluation.

The system SHOULD favor explicit deletion semantics unless the update is causally newer according to the defined synchronization model.

The exact policy is finalized during implementation and MUST be documented.

---

# 30. Conflict Resolution Principles

Conflict resolution SHOULD prioritize:

1. data safety
2. predictable behavior
3. preservation of user intent
4. deterministic results
5. minimal user intervention
6. recoverability

---

# 31. User-Visible Conflicts

Conflicts SHOULD be surfaced to the user when automatic resolution could cause meaningful data loss or surprising behavior.

The user MAY be presented with:

```text
Keep mine
Keep latest
Review changes
Merge
```

depending on entity type.

---

# 32. Server Canonical State

After synchronization, the client MUST reconcile against server-returned canonical state.

The client MUST NOT assume its local state remains authoritative after a successful synchronization response.

---

# 33. Remote Changes

Remote changes follow:

```text
Server Change
    ↓
Change Feed
    ↓
Client Download
    ↓
Authorization Check
    ↓
Apply to Local DB
    ↓
Update UI
```

---

# 34. Local Changes During Sync

The client may receive remote changes while local mutations are pending.

The synchronization engine MUST safely reconcile:

```text
Local Pending
+
Remote Change
```

without dropping either side unintentionally.

---

# 35. Synchronization Locking

The client SHOULD prevent unsafe concurrent mutation processing.

It SHOULD avoid:

```text
Two workers
    ↓
Same mutation
    ↓
Concurrent submission
```

unless the implementation explicitly supports such execution safely.

---

# 36. Server Idempotency

The backend MUST retain sufficient idempotency information to recognize repeated mutation requests within the relevant retention period.

The exact retention policy is implementation-specific.

---

# 37. Retry Policy

Retryable failures MAY include:

* temporary network failure
* timeout
* rate limit
* temporary service unavailability
* transient database/API errors

Retries SHOULD use backoff.

---

# 38. Non-Retryable Failures

Examples:

```text
Invalid authorization
Invalid payload
Resource permanently deleted
Permission denied
Malformed external request
```

These MUST NOT be retried indefinitely.

---

# 39. Retry Backoff

Retries SHOULD use exponential or equivalent bounded backoff.

Example conceptual sequence:

```text
1st retry
2nd retry
4th retry
8th retry
...
```

A maximum retry interval MUST be enforced.

---

# 40. Failed Mutation Recovery

If a mutation permanently fails:

```text
Mutation
    ↓
PERMANENT_FAILURE
    ↓
Preserve relevant local state
    ↓
Notify user
    ↓
Offer recovery
```

The client MUST NOT silently discard the user's change.

---

# 41. Permission Changes

Permission changes require special synchronization handling.

Example:

```text
User has access
      ↓
Owner revokes access
      ↓
Device synchronizes
      ↓
Access removed
```

The client MUST stop presenting protected resources as accessible after authoritative revocation is received.

---

# 42. Workspace Membership Removal

If a user is removed from a workspace:

```text
Membership revoked
    ↓
Future synchronization
    ↓
Workspace resources become inaccessible
```

Local cached data MUST NOT bypass the new authorization state.

---

# 43. Trusted Access Revocation

Trusted relationship revocation follows:

```text
Owner revokes relationship
        ↓
Server updates authorization
        ↓
Sessions/devices invalidated as applicable
        ↓
Trusted user synchronization denied
```

---

# 44. Tombstones

Deletion of a synchronized object SHOULD create a tombstone or equivalent deletion record where necessary.

Example:

```text
Task 123 deleted

Tombstone:
Task 123 → deleted
```

This allows an offline device to learn that the object no longer exists.

---

# 45. Tombstone Retention

Tombstones MUST remain available long enough to cover the synchronization assumptions of supported clients.

The retention policy MUST be documented and monitored.

---

# 46. Local Deletion

A user deletes a Task offline:

```text
Task marked deleted locally
    ↓
Deletion mutation queued
    ↓
Device remains offline
```

The task MUST NOT reappear simply because the client restarts.

---

# 47. Remote Deletion

If another device deletes the Task:

```text
Device A:
Delete

Device B:
Offline

Device B reconnects
    ↓
Receives deletion
    ↓
Applies tombstone/deletion
```

---

# 48. Restore After Deletion

If the product supports Trash:

```text
Delete
    ↓
Soft delete
    ↓
Synchronize deletion state
```

Restoration is a new mutation:

```text
Restore
    ↓
Synchronize
```

Restoration MUST respect current permissions and conflict state.

---

# 49. Recurring Data Synchronization

Recurring objects SHOULD synchronize their series definition separately from occurrence-level exceptions.

Example:

```text
Recurring Event
      │
      ├── Series definition
      │
      └── Occurrence exceptions
```

Changing one occurrence MUST NOT unintentionally rewrite the entire series.

---

# 50. Calendar Synchronization Model

Calendar synchronization must distinguish:

```text
Native Workaholic Event
Google Event
Generated Academic Event
Imported Event
```

Source/provenance MUST remain available.

---

# 51. Google Calendar Mapping

A synchronized Google Calendar object has:

```text
Native Workaholic ID
        ↕
External Mapping
        ↕
Google Event ID
```

Neither identifier replaces the other.

---

# 52. Google Calendar Initial Sync

```text
Connect Google Calendar
    ↓
Discover calendars
    ↓
Create calendar mappings
    ↓
Retrieve supported events
    ↓
Create/update native representations
    ↓
Store external mappings
    ↓
Record synchronization cursor/state
```

---

# 53. Google Calendar Incremental Sync

```text
Google changes
    ↓
Provider change detection
    ↓
Resolve external mapping
    ↓
Translate supported changes
    ↓
Apply native state
    ↓
Update synchronization metadata
```

---

# 54. Workaholic to Google Calendar

```text
Native Event change
    ↓
Determine synchronization mapping
    ↓
Translate supported fields
    ↓
Send Google API mutation
    ↓
Store resulting provider state
```

---

# 55. Google Calendar Conflict

A conflict may occur when:

```text
Workaholic Event changed
        +
Google Event changed
        ↓
Both changes occurred before synchronization
```

The synchronization layer MUST evaluate provider versions/timestamps/ETags or equivalent provider mechanisms where available.

---

# 56. Unsupported Google Fields

Google may support fields that Workaholic does not expose.

Unsupported provider data SHOULD be preserved when required to avoid destructive synchronization.

Workaholic-specific fields that Google cannot represent MUST remain native Workaholic data.

---

# 57. Google Event Deletion

If Google deletes a mapped event:

```text
Google deletion
    ↓
Workaholic detects deletion
    ↓
Update native synchronization state
```

The system MUST NOT blindly interpret this as permission to delete unrelated native data.

---

# 58. Google Calendar Disconnect

Disconnecting Google Calendar:

```text
Disconnect
    ↓
Stop future Google synchronization
    ↓
Retain native Workaholic state
    ↓
Retain synchronization history as appropriate
```

Native objects MUST NOT be deleted merely because the integration was disconnected.

---

# 59. Google Tasks Synchronization

The same conceptual model applies:

```text
Native Task
    ↕
External Mapping
    ↕
Google Task
```

---

# 60. Google Tasks Unsupported Fields

Workaholic-specific task properties MUST remain available natively even if Google Tasks cannot represent them.

Synchronization MUST NOT erase unsupported native properties.

---

# 61. Google Drive Synchronization

Drive synchronization differs from Calendar/Tasks synchronization.

Workaholic generally stores:

```text
Attachment
    ↓
External File Reference
    ↓
Google Drive
```

rather than maintaining a complete mirrored copy of the external file.

---

# 62. Drive File Deletion

If a Drive file is deleted externally:

```text
Google Drive deletion
    ↓
Workaholic detects unavailable file
    ↓
Mark external file reference unavailable
    ↓
Preserve attachment history where appropriate
```

The system MUST NOT silently substitute a different file.

---

# 63. Drive Attachment Removal

Removing an Attachment:

```text
Workaholic
    ↓
Remove relationship
```

MUST NOT delete the Drive file.

---

# 64. External Provider Rate Limits

External synchronization MUST respect provider rate limits.

When rate-limited:

```text
Provider response
    ↓
Record retryable failure
    ↓
Backoff
    ↓
Retry later
```

---

# 65. External Token Expiration

If an external integration token expires:

```text
Sync
    ↓
Authorization failure
    ↓
Refresh if possible
    ↓
If refresh succeeds:
    Continue

If refresh fails:
    Mark integration requiring reauthorization
```

Native Workaholic data remains available.

---

# 66. External Provider Outage

A provider outage MUST NOT normally prevent users from using native Workaholic functionality.

Example:

```text
Google unavailable

Native:
Tasks       → available
Projects    → available
Notes       → available
Calendar    → available according to local/native state

Google sync → delayed
```

---

# 67. Multi-Device Synchronization Example

Initial state:

```text
Task:
status = TODO
priority = HIGH
```

Device A:

```text
status = IN_PROGRESS
```

Device B:

```text
priority = LOW
```

After synchronization:

```text
status = IN_PROGRESS
priority = LOW
```

when changes are independently mergeable.

---

# 68. Multi-Device Conflict Example

Initial:

```text
priority = HIGH
```

Device A offline:

```text
priority = CRITICAL
```

Device B offline:

```text
priority = LOW
```

Both reconnect.

The system MUST detect concurrent modification and apply the defined conflict policy.

It MUST NOT falsely treat either change as causally newer merely because it arrived at the server later.

---

# 69. Sync State Visibility

The client SHOULD communicate synchronization state when useful.

Possible states:

```text
Synced
Syncing
Offline
Changes pending
Sync conflict
Sync error
```

The user SHOULD NOT need to understand internal synchronization mechanics to use the application.

---

# 70. Offline Indicator

When offline:

```text
OFFLINE
```

The UI SHOULD make clear that:

* local work can continue where supported
* pending changes will synchronize later
* cloud-dependent operations may be unavailable

---

# 71. Pending Changes Indicator

The client MAY display:

```text
3 changes pending
```

or an equivalent unobtrusive indicator.

This SHOULD NOT obstruct normal work.

---

# 72. Sync Failure UI

When synchronization fails permanently:

```text
Sync problem
    ↓
Explain affected resource
    ↓
Provide action
    ├── Retry
    ├── Review
    └── Resolve
```

Technical stack traces MUST NOT be shown to ordinary users.

---

# 73. Synchronization Security

Synchronization endpoints MUST enforce:

* authentication
* workspace/resource authorization
* device/session validity
* payload validation
* rate limiting
* idempotency
* ownership checks

A valid mutation ID alone MUST NOT grant permission to modify a resource.

---

# 74. Synchronization and Audit

Security-sensitive synchronization actions SHOULD be auditable.

Examples:

* synchronization permission rejection
* remote access revocation
* integration authorization failure
* suspicious mutation attempts

---

# 75. Synchronization and Local Security

Local data may contain sensitive user information.

The client SHOULD protect local data using platform-appropriate security mechanisms.

Authentication/session credentials MUST NOT be stored insecurely.

---

# 76. Synchronization and Notifications

Synchronization of a Task/Event change MAY affect reminders.

Example:

```text
Task deadline changed
    ↓
Reminder trigger recalculated
```

The synchronization engine MUST ensure that stale reminder schedules do not continue indefinitely after authoritative changes.

---

# 77. Synchronization and Academic Scheduling

Academic schedule recalculation is a domain operation.

A device changing an academic holiday offline produces:

```text
Academic Calendar Mutation
    ↓
Synchronize
    ↓
Server validates
    ↓
Recalculate Day Order
    ↓
Update generated occurrences
    ↓
Return canonical state
```

The client MUST NOT independently assume that its Day Order calculation is authoritative.

---

# 78. Synchronization and Semester Ending

End Semester is a server-authoritative domain operation.

```text
Device
    ↓
End Semester mutation
    ↓
Server validation
    ↓
Semester state transition
    ↓
Affected future generated occurrences updated
    ↓
Canonical state returned
```

Other devices receive the resulting semester and calendar changes through synchronization.

---

# 79. Synchronization and Bookings

Bookings require stronger concurrency guarantees than ordinary offline mutations.

A client MAY display availability while offline only if the information is clearly understood as potentially stale.

A booking confirmation MUST require authoritative server validation.

Offline clients MUST NOT confirm a booking solely from cached availability.

---

# 80. Synchronization and Public Links

Public-link state is server-authoritative.

If a public link is revoked:

```text
Server revocation
    ↓
Public endpoint rejects token
```

Client cache MUST NOT cause the revoked link to remain valid.

---

# 81. Synchronization Cursor Recovery

If a client loses its synchronization cursor or the cursor becomes invalid:

```text
Cursor invalid
    ↓
Perform recovery synchronization
    ↓
Reconcile local pending mutations
    ↓
Download new authoritative baseline
    ↓
Resume incremental synchronization
```

The recovery process MUST avoid duplicate mutation effects.

---

# 82. Long-Term Offline Devices

A device may remain offline for an extended period.

When it reconnects:

```text
Upload pending mutations
       +
Download remote changes
       ↓
Conflict/reconciliation
```

The system MUST be designed so stale clients do not silently overwrite current cloud state.

---

# 83. Sync Recovery After Reinstall

A reinstalled client is treated as a new local replica.

```text
Install
    ↓
Authenticate
    ↓
Register device
    ↓
Download authorized state
    ↓
Initialize local database
    ↓
Begin normal synchronization
```

Previously synchronized cloud data is not dependent on the old local database.

---

# 84. Sync Recovery After Crash

If the client crashes during synchronization:

```text
Application restart
    ↓
Load local database
    ↓
Load mutation queue
    ↓
Identify incomplete operation
    ↓
Retry using same idempotency identity
```

The operation MUST NOT be duplicated because of the crash.

---

# 85. Sync Recovery After Server Restart

The server MUST derive synchronization state from durable storage rather than process memory.

A backend restart MUST NOT cause accepted mutations to disappear.

---

# 86. Sync Observability

The system SHOULD record:

* synchronization latency
* pending mutation count
* retry count
* conflict count
* permanent failure count
* external provider failure count
* synchronization throughput

This information is required for diagnosing real-world synchronization issues.

---

# 87. Synchronization Performance

Initial synchronization SHOULD prioritize:

1. current user/workspace state
2. active tasks
3. upcoming calendar events
4. reminders
5. recent notes/activity
6. less immediately relevant historical data

Large datasets SHOULD be paginated or incrementally synchronized.

---

# 88. Synchronization and Data Minimization

A client SHOULD synchronize only data required for its authorized operation.

The system SHOULD avoid downloading unrelated workspaces or inaccessible resources.

---

# 89. Canonical Reconciliation Rule

After successful synchronization:

```text
Server canonical state
        ↓
Client local state
```

The client MUST converge toward server-authoritative state.

---

# 90. Synchronization Completion

A synchronization cycle is complete only when:

```text
All eligible pending mutations
    ↓
Accepted / resolved / explicitly failed

AND

Relevant remote changes
    ↓
Applied

AND

Synchronization cursor/state
    ↓
Advanced safely
```

---

# 91. Synchronization Definition of Done

Synchronization functionality is considered complete only when:

* offline creation works
* offline editing works
* offline deletion works
* queued mutations survive restart
* retries are safe
* duplicate requests are safe
* remote changes arrive correctly
* stale writes are detected
* conflicts are handled
* deletions propagate
* permission revocation propagates
* Google Calendar sync works
* Google Tasks sync works
* Drive references remain safe
* external failures do not corrupt native data
* academic schedule changes synchronize
* semester ending synchronizes
* booking confirmation remains authoritative
* sync failures are observable
* regression tests exist for discovered synchronization bugs

---

# 92. Explicit Non-Goals

The initial synchronization architecture does NOT require:

* Kafka
* Redis
* distributed event streaming
* CRDTs for every entity
* multi-region active-active databases
* dedicated synchronization microservices

These may be introduced only if actual scale or product requirements justify them.

---

# 93. Future Evolution

If synchronization volume grows significantly, the architecture MAY evolve toward:

```text
Current
Modular Monolith
      ↓
Managed Background Jobs
      ↓
Queue where justified
      ↓
Dedicated sync processing
      ↓
Provider-specific workers
```

The domain model and synchronization semantics MUST remain stable during such infrastructure evolution.

---

# 94. Synchronization Authority

`SYNC-SPECIFICATION.md` is authoritative for synchronization semantics.

It defines how local, cloud, and external states converge.

It does not define:

* exact API endpoints
* exact SQL schema
* exact local database technology
* UI components
* OAuth implementation
* notification UI

Those concerns are specified elsewhere.
