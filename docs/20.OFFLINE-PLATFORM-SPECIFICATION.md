````markdown
# Workaholic Offline and Platform Specification

**Status:** FINAL  
**Document Type:** Engineering Specification  
**Scope:** Web, Windows 11, Android, Local State, Offline Operation, Synchronization, Background Processing, Notifications, Device Lifecycle

---

## 1. Purpose

This document defines platform-specific behavior for Workaholic across:

- Web;
- Windows 11 desktop;
- Android.

It also defines how clients behave when connectivity is unavailable, how local state interacts with the authoritative backend, and how platform lifecycle constraints affect synchronization and reminders.

The system must provide a consistent Workaholic experience across platforms while respecting the capabilities and restrictions of each platform.

---

# 2. Platform Principles

Workaholic follows these principles:

1. The backend remains the authoritative shared cloud state.
2. Clients may maintain local state for responsiveness and offline operation.
3. Local state must never permanently diverge from the synchronized server state.
4. Offline changes must be represented as pending mutations rather than silently discarded.
5. Synchronization must be deterministic and idempotent.
6. Platform-specific limitations must not corrupt domain data.
7. Native platform functionality should be used where it materially improves reliability.
8. The initial implementation must avoid unnecessary infrastructure complexity.

Conceptually:

```text
                 Workaholic Backend
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
        Web          Windows       Android
      Local State   Local State   Local State
          │             │             │
          └─────────────┴─────────────┘
                    Sync
````

# 4. Shared Client Architecture

Each client should conceptually contain:

```text
UI
 ↓
Application State
 ↓
Local Repository
 ↓
Sync Engine
 ↓
API Client
 ↓
Backend
```

The UI should not directly manage synchronization protocol details.

The local repository abstracts local persistence from UI components.

The synchronization engine handles:

* pending mutations;
* server reconciliation;
* retries;
* conflict handling;
* synchronization state.

---

# 5. Local State

Local state exists to provide:

* fast rendering;
* offline access;
* offline mutations;
* local reminder scheduling;
* temporary synchronization state.

Local state is not an independent permanent source of truth.

The backend remains the authoritative shared state.

---

Client-side persistence may contain:

### Cached domain data

Examples:

* tasks;
* projects;
* boards;
* events;
* notes;
* calendars;
* relevant reminder metadata.

### Pending mutations

Examples:

```text
CREATE
UPDATE
DELETE
COMPLETE
RESCHEDULE
```

### Synchronization metadata

Examples:

* local mutation ID;
* server revision;
* synchronization timestamp;
* external mapping metadata where necessary.

### Device configuration

Examples:

* user preferences;
* notification settings;
* local UI state.

Sensitive credentials must follow the security specification and must not be stored in ordinary application data stores.

# 7. Local Identifier Strategy

Offline-created resources require identifiers before they reach the backend.

The client must use collision-resistant temporary/native identifiers.

Conceptually:

```text
Offline:
client creates Task
ID = local/generated ID

Reconnect:
server accepts mutation
resource receives/retains canonical identity
mapping is reconciled
```

The implementation must ensure that the same logical task is not accidentally created twice.

---

# 8. Offline Mutation Queue

Offline mutations must be stored in a durable local queue where offline write support is enabled.

Conceptually:

```text
User Action
    ↓
Local State Updated
    ↓
Mutation Added to Queue
    ↓
Network unavailable
    ↓
Queue retained
    ↓
Network restored
    ↓
Synchronization
```

A queue entry should contain enough information to safely retry the operation.

---

# 9. Mutation States

A mutation may conceptually progress through:

```text
PENDING
   ↓
PROCESSING
   ↓
ACKNOWLEDGED
```

or:

```text
PENDING
   ↓
FAILED
   ↓
RETRYING
```

Permanent conflicts or invalid mutations must enter an appropriate terminal/error state rather than being retried indefinitely.

---

# 10. Offline Creation

When a supported resource is created offline:

1. validate locally;
2. generate local identity;
3. update local state optimistically;
4. enqueue mutation;
5. show the resource as pending synchronization where appropriate;
6. synchronize after connectivity returns;
7. reconcile server response.

The user should not lose work simply because the network is unavailable.

---

# 11. Offline Editing

Offline edits should update local state immediately.

The mutation must preserve enough information to determine what changed.

Where multiple edits to the same resource occur offline, the client may coalesce mutations where safe.

Example:

```text
Task title:
A
 ↓
B
 ↓
C
```

may be synchronized as the final state where intermediate states are not externally meaningful.

However, coalescing must not violate audit, synchronization, or conflict requirements.

---

# 12. Offline Completion

Completing a task offline must:

```text
local task → completed
```

and enqueue the corresponding mutation.

After reconnect:

```text
local completion
       ↓
server
       ↓
acknowledgement
```

If the server has conflicting state, the configured synchronization policy applies.

---

# 13. Offline Deletion

Offline deletion requires special handling because the resource may also be modified elsewhere.

The client must not simply assume that deletion is always safe.

The synchronization layer must detect relevant conflicts according to the synchronization specification.

Deletion mutations must remain identifiable after reconnect.

---

# 14. Reconnection

When network connectivity returns:

```text
Connectivity restored
        ↓
Validate local state
        ↓
Process pending mutations
        ↓
Fetch/reconcile server changes
        ↓
Resolve conflicts
        ↓
Update local state
        ↓
Mark synchronization complete
```

Synchronization must be safe if reconnection happens repeatedly.

---

# 15. Repeated Reconnection

The following sequence must remain safe:

```text
Offline
→ Online
→ Offline
→ Online
→ Offline
→ Online
```

No mutation may be silently lost because connectivity changes during synchronization.

---

# 16. Network Failure During Synchronization

If the network fails during synchronization:

* acknowledged mutations must not be submitted again incorrectly;
* unacknowledged mutations must remain retryable;
* local state must remain recoverable;
* the user must not be told that work is permanently synchronized when it is not.

The implementation must distinguish:

```text
sent
```

from:

```text
confirmed by server
```

where necessary.

---

# 17. Synchronization Idempotency

Synchronization operations must tolerate:

```text
retry
duplicate request
application restart
network timeout
partial response
```

Repeated processing must converge toward one correct state.

---

# 18. Conflict Handling

Conflicts occur when local and remote changes affect the same logical resource.

Conceptually:

```text
Server state
    │
    ├── changed remotely
    │
    └── Client changed while offline
             ↓
          Conflict
```

The resolution policy is defined by `SYNC-SPECIFICATION.md`.

Platform clients must not invent their own conflict semantics.

---

# 19. Conflict UI

Where user intervention is required, the client must clearly communicate:

* what resource conflicts;
* what changed locally;
* what changed remotely;
* available resolution choices;
* resulting state.

The client must not silently discard user work.

---

# 20. Sync Status

The application should expose meaningful synchronization state where useful.

Possible states:

```text
Synced
Syncing
Offline
Pending changes
Sync failed
Conflict requires attention
```

The UI should avoid displaying excessive technical detail during normal use.

Detailed diagnostics belong in appropriate troubleshooting views/logs.

---

# 21. Web Offline Architecture

The web client may use browser-supported persistent storage for offline functionality.

The implementation should use an appropriate browser persistence mechanism rather than assuming in-memory state survives refreshes.

Offline functionality must be treated as progressive capability.

If a browser does not support a required capability, the application must fail gracefully rather than pretending that offline writes are durable.

---

# 22. Web Connectivity Detection

The web application may use browser connectivity indicators as hints.

Connectivity detection must not be treated as authoritative proof that the backend is reachable.

For example:

```text
Browser says "online"
        ≠
Backend request guaranteed to succeed
```

Actual API responses remain authoritative for synchronization.

---

# 23. Web Refresh During Offline Mode

If supported offline state is persisted:

```text
Offline
→ create/edit
→ refresh browser
```

must preserve pending work.

If the browser cannot guarantee the required persistence, the UI must clearly communicate the limitation.

---

# 24. Web Multiple Tabs

Multiple Workaholic tabs may operate simultaneously.

The client should coordinate local state where practical.

Tests must cover:

```text
Tab A changes task
Tab B displays same task
```

The system must converge without corrupting state.

---

# 25. Web Service Worker

Where implemented, a service worker may support:

* asset caching;
* offline application shell;
* push notifications;
* selected background functionality.

The service worker must not become a second implementation of business logic.

Domain operations remain owned by application services and synchronization logic.

# 30. Windows Background Synchronization

Background synchronization should:

* run without requiring the main window;
* respect network availability;
* avoid excessive polling;
* retry transient failures;
* preserve pending mutations;
* recover after sleep/wake.

```text

 ↓

Re-establish connectivity
```

# 32. Windows Local Reminders

# 34. Windows Updates

# 40. Android Local Alarms

Important reminders should be capable of using local device scheduling where required.

Local alarm scheduling must survive:

* application backgrounding;
* normal process termination;
* device restart where supported and appropriate.

# 41. Android Push Notifications

Push notifications may be used for:

* server-generated reminders;

# 46. Simultaneous Device Changes

Example:

```text
Windows: task title → "A"
Android: task title → "B"
```

If both occur before synchronization reconciles them, the configured conflict policy applies.

Clients must not independently choose incompatible conflict rules.

---

# 47. Local Reminder Ownership

Reminder scheduling may be represented separately from the shared reminder domain state.

Conceptually:

```text
Shared Reminder
      ↓
Reminder Schedule
      ↓
Device-specific Delivery
```

This permits one user's device state to change without modifying another recipient's reminder.

---

# 48. Shared Reminder Isolation

For:

```text
Owner
Recipient A
Recipient B
```

each recipient may have independent local delivery state.

If Recipient A snoozes:

```text
Recipient A → snoozed
Recipient B → unchanged
Owner       → unchanged
```

This must remain true across synchronization.

# 49. Local Notification Actions

Where platform support exists, notification actions may include:

* open;
* complete;
* snooze;
* dismiss.

Actions must ultimately pass through appropriate application/domain authorization.

A notification action must not bypass backend permission checks.

---

# 50. Authentication State

Clients may persist authentication/session state according to the security architecture.

Authentication persistence must not allow a revoked session to remain permanently valid.

After session invalidation:

```text
Client
 ↓
API request
 ↓
Unauthorized
 ↓
Refresh/re-authentication flow
```

must occur safely.

---

# 51. Secure Local Storage

Sensitive information must use platform-appropriate secure storage.

Examples:

* Android secure storage mechanisms;
* Windows protected credential mechanisms;
* browser secure cookie/storage mechanisms according to the authentication architecture.

Refresh credentials and other highly sensitive secrets must not be placed in ordinary plaintext local databases.

---

# 52. Logout

Logout must appropriately clear:

* local authenticated state;
* access credentials;
* sensitive cached state where required;
* device-specific session state.

The server-side session must also be invalidated according to the authentication design.

---

# 53. Device Revocation

If a device/session is remotely revoked:

```text
Backend
 ↓
Session invalidated
 ↓
Client next contacts backend
 ↓
Access rejected
 ↓
Client transitions to signed-out/re-authentication state
```

The client must not continue operating indefinitely from stale authenticated state.

---

# 54. Offline Security

Offline access creates additional security considerations.

The client must determine what data may remain locally after:

* logout;
* session expiry;
* device revocation.

Sensitive cached information must be cleared or protected according to the security model.

---

# 55. Cache Policy

Local caching should prioritize data required for:

* current workflows;
* offline operation;
* synchronization.

The application should not indefinitely cache every resource.

Cache eviction may be used to control storage consumption.

---

# 56. Cache Versus Source of Truth

The client must distinguish:

```text
Cached server data
```

from:

```text
Locally modified pending data
```

A synchronization operation must not overwrite unsynchronized local changes merely because a remote snapshot was fetched.

---

# 57. Offline Search

If offline search is supported, it should search locally persisted data.

The UI should make it clear that offline search may not include data that has never been synchronized to the device.

---

# 58. Offline Calendar

Offline calendar functionality should support cached calendar data and permitted local modifications.

The client must preserve timezone and recurrence semantics while offline.

Generated calendar data must not be silently duplicated after reconnect.

---

# 59. Offline Academic Scheduling

Academic scheduling changes made offline must be treated as normal domain mutations.

If a user modifies:

* holiday;
* special working day;
* Day Order configuration;
* class schedule;

offline, the synchronization engine must reconcile those changes according to the same domain rules used online.

The client must not implement an alternate Day Order algorithm.

---

# 60. Offline Booking

Booking creation requires special handling.

A client must not guarantee a booking merely because a cached slot appears available.

Because booking availability depends on shared concurrent state:

```text
Cached availability
        ≠
Guaranteed availability
```

The authoritative booking decision must occur against the server.

If offline booking is not supported, the UI must clearly communicate that booking requires connectivity.

---

# 61. Offline Public Calendar

Public calendar access requires server-backed data unless an intentionally cached public representation is implemented.

Private calendar data must never be placed into public offline caches.

---

# 62. Platform Error Handling

Each platform must distinguish:

```text
Offline
Authentication expired
Permission denied
Server error
Conflict
External integration failure
Local storage failure
```

The UI should provide an actionable message where possible.

---

# 63. Local Storage Failure

If local persistence fails:

* do not falsely report durable offline success;
* notify the user where necessary;
* avoid silently dropping pending work;
* attempt recovery when possible.

Critical write operations should have explicit failure states.

---

# 64. Storage Limits

Clients must account for platform storage limits.

The application may remove:

* stale cached resources;
* obsolete synchronization metadata;
* unnecessary local copies.

It must not delete unsynchronized user mutations merely to free cache space.

---

# 65. Clock Changes

Users may manually change device clocks.

Client logic must not blindly trust local wall-clock changes for security-sensitive operations.

Reminder and synchronization systems must use server-authoritative timestamps where required.

---

# 66. Timezone Changes

A user may travel or change device timezone.

The application must correctly distinguish:

```text
Event instant
User timezone
Display timezone
```

Changing device timezone must not accidentally move an event to a different instant.

---

# 67. Daylight-Saving Changes

Where a supported timezone observes daylight saving:

* event instants must remain correct;
* recurring schedules must use timezone-aware rules;
* reminder calculations must remain correct;
* ambiguous/nonexistent local times must follow the calendar specification.

India does not currently observe DST, but the implementation must not assume that all supported timezones behave similarly.

---

# 68. Background Job Duplication

Platform clients may trigger synchronization from multiple mechanisms:

```text
Startup
Foreground resume
Network restoration
Periodic job
Manual refresh
```

These triggers must converge through the same synchronization mechanism.

They must not each implement independent mutation logic.

---

# 69. Manual Sync

The user may request synchronization where supported.

Manual synchronization should:

* use the normal sync engine;
* display meaningful status;
* respect retries;
* remain safe if another synchronization is already running.

Concurrent synchronization executions should be serialized or otherwise coordinated where required.

---

# 70. Sync Locking

The client should prevent conflicting synchronization executions against the same local state.

Conceptually:

```text
Sync A starts
     ↓
Sync B requested
     ↓
Queue / coalesce / safely reject B
```

rather than allowing uncontrolled simultaneous mutations.

---

# 71. App Upgrade and Local Schema

Local client databases may evolve.

Client upgrades must use versioned local migrations where required.

The upgrade process must preserve:

* pending mutations;
* cached data where compatible;
* reminder state;
* user settings.

---

# 72. App Uninstall/Reinstall

Uninstalling an application may destroy local state according to platform behavior.

The cloud backend remains the durable shared source.

After reinstall:

```text
Install
 ↓
Authenticate
 ↓
Initial synchronization
 ↓
Restore cloud state
```

Unsynchronized data that existed only locally before uninstall cannot be guaranteed unless the platform/application had already persisted it elsewhere.

The UI should communicate this risk where relevant.

---

# 73. Initial Synchronization

After first installation or reinstall:

```text
Authenticate
 ↓
Fetch permitted resources
 ↓
Initialize local database
 ↓
Initialize synchronization state
 ↓
Schedule relevant local reminders
 ↓
Application ready
```

The initial synchronization must respect workspace and resource permissions.

---

# 74. Partial Initial Synchronization

If initial synchronization fails halfway:

* already downloaded valid data may remain cached;
* missing data must not be represented as complete;
* synchronization must resume safely;
* duplicate resources must not be created.

# 82. Offline Safety Invariants

The following invariants are mandatory:

### Invariant 1

```text
Offline user work must not be silently discarded.
```

### Invariant 2

```text
Retrying synchronization must not create duplicate logical resources.
```

### Invariant 3

```text
A remote snapshot must not blindly overwrite unsynchronized local work.
```

### Invariant 4

```text
Platform-specific lifecycle events must not corrupt domain state.
```

### Invariant 5

```text
Local notification state must not alter another user's shared reminder state.
```

### Invariant 6

```text
Offline availability must never be treated as authoritative booking availability.
```

### Invariant 7

```text
Client-side offline state must remain subject to server-side authorization.
```

# 83. Architecture Boundary

Platform clients are responsible for:

```text
Presentation
Local persistence
Local scheduling
Platform integration
Synchronization orchestration
```

The backend remains responsible for:

```text
Authorization
Canonical shared state
Business-rule enforcement
Cross-user consistency
Booking concurrency
External synchronization
Security-sensitive operations
```

This prevents platform clients from becoming independent implementations of Workaholic's business rules.

```text
              │               │
```

The platform layer may optimize how Workaholic operates, but it must not redefine what Workaholic means.

# 87. Final Invariant

The fundamental client lifecycle is:

```text
USER ACTION
    ↓
LOCAL STATE
    ↓
PERSIST
    ↓
QUEUE MUTATION IF REQUIRED
    ↓
SYNCHRONIZE
    ↓
SERVER VALIDATION
    ↓
AUTHORITATIVE STATE
    ↓
RECONCILE CLIENT
    ↓
PLATFORM UI / NOTIFICATION
```

Whether the user is connected, offline, on Windows, on Android, or using the Web, this lifecycle must preserve the same underlying Workaholic data model, business rules, permissions, and synchronization semantics.
