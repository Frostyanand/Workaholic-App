````markdown
# 1. Purpose

This document defines the expected user journeys and system flows of Workaholic.

It describes:

- how users enter and use the system
- how major operations progress
- what the user sees conceptually
- what the system does in response
- important alternate paths
- failure and recovery behavior
- relationships between related workflows

This document defines behavior and flow rather than implementation.

Exact UI layouts, component design, API contracts, and database structures are defined separately.

---

# 2. Flow Conventions

The following notation is used:

```text
USER ACTION
    ↓
SYSTEM RESPONSE
    ↓
NEXT USER ACTION
````

System-side operations are explicitly identified where relevant.

# 45. Booking Conflict Flow

Two guests may select the same slot concurrently.

```text
Guest A sees slot
Guest B sees slot
        ↓
Both attempt booking
        ↓
Authoritative transaction
        ↓
First valid confirmation succeeds
        ↓
Second confirmation fails
        ↓
Second guest receives updated availability
```

Client-side availability display MUST NOT be treated as final authority.

# 54. Error Handling Flow

General failure:

```text
User Action
    ↓
Validation
    ↓
Operation
    ↓
Success?
  /       \
Yes       No
 ↓         ↓
Update    Preserve prior valid state
state       ↓
            Explain failure
            ↓
            Offer recovery
```

Errors MUST NOT result in silent data loss.

---

# 55. Authentication Failure Flow

```text
Protected action
    ↓
Authentication/session check
    ↓
Session invalid?
    ↓
Require re-authentication
    ↓
Restore authorized session
    ↓
Retry permitted operation where safe
```

Expired authentication MUST NOT be treated as authorization to continue.

---

# 56. Authorization Failure Flow

```text

 ↓         ↓
```

# 73. Flow Integrity Requirements

Every implemented user flow MUST account for:

* loading state
* empty state
* validation failure
* authorization failure
* network failure
* offline behavior where supported
* synchronization
* duplicate action handling
* cancellation
* retry
* success confirmation
* relevant notifications
* accessibility

A happy-path-only implementation is incomplete.

---

# 74. Destructive Action Requirements

The following operations SHOULD require explicit confirmation where accidental execution could cause meaningful data loss:

* permanent deletion
* account deletion
* public-link revocation where appropriate
* integration disconnection where consequences are significant
* semester termination
* destructive bulk operations
* deletion of external files
* revocation of trusted access

The confirmation MUST clearly communicate the affected scope.

# 76. Flow Authority

`USER-FLOWS.md` defines the intended end-to-end behavior of Workaholic.

It does not define:

* exact UI component hierarchy
* exact database schema
* API URL structure
* programming language implementation
* provider-specific infrastructure
* visual design tokens
* exact synchronization algorithms

Those concerns belong to subsequent specifications.

Where implementation behavior differs from a defined flow, the implementation MUST either conform to the flow or trigger an explicit requirements/design change.
