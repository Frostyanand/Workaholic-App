````markdown
**Status:** FINAL

## 1. Purpose

Workaholic is a multi-platform productivity system whose correctness depends not only on individual UI features but also on interactions between:

- users and workspaces;
- tasks and projects;
- boards and statuses;
- calendars and scheduled work;
- recurring tasks and events;
- academic Day Order scheduling;
- reminders and notifications;
- Google Calendar, Google Tasks, and Google Drive;
- offline clients and synchronization;
- public calendar and booking functionality;
- trusted-user sharing;
- permissions and resource isolation;
- multiple devices operating concurrently.

Accordingly, testing must validate the complete system rather than treating each feature as an isolated UI implementation.

The testing strategy has four primary objectives:

1. Verify that implemented behavior satisfies the approved requirements.
2. Detect regressions when existing functionality is modified.
3. Verify security, authorization, synchronization, and data-integrity invariants.
4. Provide sufficient confidence for deployment without requiring excessive infrastructure during the initial product stage.

---

# 2. Testing Principles

## 2.1 Requirements Are Testable Contracts

Every functional requirement marked `MUST` must have one or more corresponding tests.

Requirements marked `SHOULD` must have tests where the behavior is implemented.

Requirements marked `MAY` are tested only when implemented.

Deferred and Coming Soon functionality is not part of the current release test scope.

Each requirement should be traceable through:

```text
Requirement
    ↓
Business Rule / User Flow
    ↓
Implementation
    ↓
Test Case
````

---

## 2.2 Test Behavior, Not Implementation Details

Tests should primarily verify externally observable behavior and domain invariants.

Tests must not unnecessarily depend on:

* private implementation details;
* internal component structure;
* exact CSS classes;
* incidental database query ordering;
* framework-specific implementation choices.

Implementation-specific tests are appropriate when testing a low-level utility, adapter, repository, or security mechanism.

---

## 2.3 Test at the Lowest Appropriate Level

A behavior should normally be tested at the lowest test layer capable of proving it correctly.

For example:

* date calculation → unit test;
* permission invariant → database/domain test;
* API validation → integration/API test;
* task creation through UI → E2E test;
* Google Calendar synchronization → integration/sync test;
* Windows reminder delivery → platform test.

This keeps the test suite fast while reserving expensive E2E tests for actual user-critical flows.

---

## 2.4 Determinism Is Mandatory

Tests must be deterministic.

Tests must not depend on:

* the real current time;
* the developer's timezone;
* real external accounts;
* network availability unless network behavior is explicitly under test;
* execution order;
* random identifiers without controlled seeds;
* real notification timing;
* external service state.

Where randomness is necessary, tests must use controlled seeds or explicit fixtures.

---

## 2.5 Test Failure States, Not Only Happy Paths

Every important feature must test:

* valid input;
* invalid input;
* missing input;
* unauthorized access;
* conflicting state;
* duplicate operations;
* concurrent operations where relevant;
* network failure;
* external-service failure;
* stale client state;
* empty state;
* loading state;
* recovery behavior.

---

# 3. Test Pyramid

Workaholic should use a testing pyramid approximately structured as follows:

```text
                  /\
                 /  \
                / E2E\
               /------\
              / Platform\
             / Integration\
            /--------------\
           /  API / DB Tests \
          /------------------\
         /    Unit Tests      \
        /----------------------\
```

The majority of tests should be fast unit and domain tests.

Integration and database tests should validate interactions between real application components.

E2E tests should cover a smaller number of high-value user journeys.

Platform-specific tests should focus on behavior that cannot be reliably proven by backend or web tests.

The pyramid is a distribution principle, not a rigid numerical requirement.

# 6. Academic Day Order Testing

The academic scheduling subsystem requires dedicated testing because Day Order is not equivalent to ordinary weekday recurrence.

Tests must verify:

```text
Semester
    ↓
Academic Calendar
    ↓
Working Days
    ↓
Day Order Sequence
    ↓
DO Schedule Mapping
    ↓
Generated Class Events
```

Required scenarios:

### 6.1 Normal Sequence

Example:

```text
Monday → DO1
Tuesday → DO2
Wednesday → DO3
Thursday → DO4
Friday → DO5
```

Generated classes must correspond to the correct Day Order.

### 6.2 Weekend

Saturday and Sunday must not increment the Day Order sequence unless explicitly represented as working days.

### 6.3 Holiday

If a working day becomes a holiday:

```text
DO1
Holiday
DO2
```

The holiday must not consume a Day Order unless explicitly configured to do so.

All subsequent DO-linked classes must shift accordingly.

### 6.4 Special Working Day

A specially configured working Saturday must participate in the academic calendar and Day Order sequence according to its configured rules.

### 6.5 Cancelled Class

A cancelled class must not silently modify the underlying reusable schedule mapping.

### 6.6 Rescheduled Class

A rescheduled class must preserve the distinction between:

```text
original generated schedule
```

and:

```text
explicit exception/reschedule
```

### 6.7 End Semester

Ending a semester must:

* invalidate/remove future generated occurrences belonging to that semester;
* preserve past history;
* preserve the reusable schedule/template;
* preserve DO mappings;
* preserve unrelated personal events;
* preserve unrelated calendar sources.

A test must specifically prove that an End Semester operation cannot delete unrelated calendar data.

# 7. Database Testing

Database tests must validate persistence behavior independently of the UI.

Test:

* required fields;
* foreign keys;
* uniqueness constraints;
* cascading behavior;
* soft deletion;
* timestamps;
* indexes where behavior depends on them;
* transactional operations;
* relationship integrity;
* nullable versus required fields.

Examples:

```text
Task cannot reference a nonexistent workspace.

Workspace member cannot reference a nonexistent user.

Calendar event cannot reference an invalid calendar.

External synchronization record cannot reference an invalid native resource.
```

# 8. Authorization and Row-Level Security Testing

Authorization testing is mandatory.

Authentication proves:

```text
Who is the caller?
```

Authorization proves:

```text
What may the caller access?
```

Tests must verify both.

---

## 8.1 Workspace Isolation

User A must not be able to:

* read User B's private workspace resources;
* modify User B's tasks;
* delete User B's events;
* access User B's notes;
* retrieve User B's attachments;
* access User B's private metadata.

---

## 8.2 Membership Roles

Test every supported workspace role and permission combination.

Verify:

* permitted actions succeed;
* forbidden actions fail;
* read-only users cannot modify;
* removed members immediately lose access;
* revoked permissions do not remain effective through stale client state.

---

## 8.3 Resource-Level Authorization

Authorization must be tested for:

* task;
* project;
* board;
* note;
* calendar;
* event;
* attachment;
* booking;
* workspace;
* membership;
* trusted-user relationship;
* public calendar session.

A user authorized to access one resource must not automatically gain access to unrelated resources.

---

## 8.4 Negative Authorization Tests

Every sensitive endpoint should include explicit negative tests.

Example:

```text
Given User A owns Resource X
And User B is not authorized for Resource X

When User B requests Resource X

Then the request must fail
And no protected information must be returned.
```

Tests must also check that error responses do not leak sensitive metadata.

# 23. Booking Concurrency Testing

Booking requires special concurrency testing.

The system must prevent two users from successfully booking the same exclusive slot.

A concurrency test should execute:

```text
Guest A → booking request
Guest B → booking request
```

at approximately the same time.

Expected result:

```text
Exactly one booking succeeds.
The other receives a conflict/unavailability response.
```

This must be enforced by transactional/database behavior, not merely frontend validation.

# 24. Public Calendar Privacy Testing

Public calendar tests must verify:

### Private Event

Public viewer sees:

```text
Busy
```

but not:

* title;
* description;
* attendees;
* notes;
* attachments;
* private metadata.

### Public Event

Public viewer may see only the fields explicitly permitted by the public-calendar specification.

### Revocation

After revoking a public link:

```text
old link → inaccessible
```

A newly generated link must be independent of the revoked link.

Tests must verify that public access does not bypass normal private authorization boundaries.

# 31. Performance Testing

Performance testing should begin with realistic initial-scale workloads and expand as usage grows.

Initial testing should simulate realistic workloads for approximately:

```text
10–20 active users
```

without designing the test architecture around that number permanently.

The system must also be tested against larger synthetic datasets to identify obvious scalability problems.

Test areas include:

* API response latency;
* database query performance;
* task-list rendering;
* calendar rendering;
* large boards;
* large notes;
* global search;
* synchronization;
* notification processing;
* attachment metadata operations.

Synthetic datasets should be used to test:

* thousands of tasks;

# 35. Backup and Recovery Testing

Backup and recovery procedures must be periodically verified.

Tests should include:

* database backup creation;
* backup integrity;
* restoration;
* restoration into a clean environment;
* recovery of relationships;
* recovery of synchronization metadata;
* recovery of critical configuration.

# 36. Regression Testing

Every confirmed defect must result in a regression test when practical.

The required workflow is:

```text
Bug discovered
    ↓
Root cause identified
    ↓
Fix implemented
    ↓
Regression test added
    ↓
Full relevant suite executed
```

The regression suite should grow from actual defects rather than speculative test cases alone.

---

# 37. Property-Based Testing

Property-based testing should be used for complex deterministic logic where many input combinations exist.

Suitable candidates include:

* recurrence generation;
* date calculations;
* Day Order calculations;
* task dependency evaluation;
* permission combinations;
* synchronization transformations.

Example property:

```text
Adding a non-working holiday to an academic calendar must never
advance the Day Order sequence for that date.
```

Another:

```text
Running the same synchronization operation repeatedly must not
create additional logical resources.
```

---

# 38. Time Control

Tests involving time must use an injectable/fake clock.

The application must not directly depend on:

```text
Date.now()
new Date()
system clock
```

inside domain logic where deterministic testing is required.

Tests should be able to define:

```text
Current time = 2026-09-06 10:00 Asia/Kolkata
```

and reliably reproduce the same result.

---

# 39. Timezone Testing

Timezone behavior must be tested using multiple representative timezones.

At minimum, tests should cover:

* UTC;
* India Standard Time;
* a timezone with daylight-saving transitions;
* timezone conversion around midnight.

Example:

```text
Event created at 23:30 in timezone A
→ converted to timezone B
→ date may differ
```

The system must preserve the intended instant and display it according to the user's configured timezone.

# 41. Test Isolation

Each test should be independent.

A test must not depend on another test having:

* created a user;
* inserted a database record;
* configured a calendar;
* authenticated a session;
* modified global state.

Tests should create the state they require and clean up after themselves.

```text
Production
```

Production data must never be used casually for automated tests.

External integrations must use dedicated test accounts or sandbox environments where available.

---

# 47. Continuous Integration

Every pull request affecting application code must execute an appropriate automated test pipeline.

Minimum CI stages:

```text
Install dependencies
        ↓
Lint / static checks
        ↓
Unit tests
        ↓
Domain tests
        ↓
Database tests
        ↓
API/integration tests
        ↓
Build
        ↓
Relevant E2E tests
```

The exact pipeline may be optimized for speed, but a change must not bypass required validation merely because the affected feature appears small.

---

# 48. Test Selection for Changes

Not every code change requires the entire E2E suite locally.

Developers should run:

### During development

Relevant unit/domain tests.

### Before commit

Relevant unit, integration, and static checks.

### Pull request

Complete CI-required suite.

### Release candidate

Full regression and platform validation.

### Production deployment

Required release gates and smoke tests.

# 49. Smoke Testing

After deployment, smoke tests must verify that the system is fundamentally operational.

Minimum smoke coverage:

```text
Application loads
→ Authentication works
→ API responds
→ Database accessible
→ Task can be created
→ Task can be completed
→ Calendar loads
```

Critical integrations should have corresponding health checks.

---

# 50. Release Gates

A release must not proceed when:

* critical tests fail;
* authentication is broken;
* authorization isolation fails;
* data integrity tests fail;
* synchronization can duplicate or destroy data;
* critical notification behavior fails;
* migration fails;
* critical E2E flows fail.

Known non-critical failures may be accepted only when explicitly reviewed and documented.

---

# 51. Test Severity

Defects should be categorized approximately as:

### Critical

Examples:

* cross-user data exposure;
* destructive data corruption;
* authentication bypass;
* unauthorized resource modification;
* synchronization causing widespread duplication/deletion;
* booking allowing double allocation.

### High

Examples:

* major workflow unusable;
* reminders consistently fail;
* calendar synchronization broken;
* trusted-user permissions incorrect.

### Medium

Examples:

* feature partially broken;
* recoverable synchronization issue;
* significant UI workflow problem.

### Low

Examples:

* cosmetic issue;
* minor accessibility issue;
* non-critical visual inconsistency.

Severity determines release impact.

---

# 52. Testing of Destructive Operations

Destructive actions require dedicated tests.

Examples:

* task deletion;
* project deletion;
* calendar deletion;
* event deletion;
* semester ending;
* workspace removal;
* membership revocation;
* Drive file deletion.

Tests must verify:

1. correct resource is affected;
2. unrelated resources remain untouched;
3. authorization is enforced;
4. confirmation requirements are enforced where applicable;
5. soft-delete/trash behavior occurs where specified;
6. recovery works where supported.

---

# 53. End Semester Safety Tests

Because semester termination can affect many generated events, it requires dedicated regression coverage.

Test:

```text
Semester A
    ├── generated class events
    ├── personal events
    └── unrelated calendar events
```

After End Semester:

```text
Semester A future generated class events
→ removed/invalidated

Semester A past history
→ preserved

Reusable DO mapping
→ preserved

Personal events
→ preserved

Unrelated calendar events
→ preserved
```

This behavior is a mandatory release gate for academic scheduling functionality.

# 54. Test Coverage Requirements

Coverage metrics are useful indicators but are not sufficient by themselves.

The project should track:

* line coverage;
* branch coverage;
* function coverage;
* requirement coverage;
* critical-path coverage.

High numerical code coverage does not compensate for missing business-rule tests.

Critical domain logic must receive stronger coverage than incidental UI code.

Potential targets:

# 57. Definition of Done for a Feature

A feature is not considered complete until:

* requirements are implemented;
* business rules are implemented;
* authorization is verified;

* loading/empty/error states exist;
* unit/domain tests exist where applicable;
* database tests exist where applicable;

# 58. Definition of Done for a Release

A release is complete when:

* required test suites pass;
* critical and high-severity defects are resolved or explicitly accepted;

* synchronization regression tests pass;

* booking concurrency tests pass;

```text

  ↓

  ↓

  ↓

  ↓
```

Tests must not simply be weakened or deleted to make CI pass.

If a test is genuinely invalid, the reason must be documented.

---

# 62. Testing Philosophy

Workaholic should optimize for **confidence per unit of complexity**.

The project should not introduce expensive testing infrastructure prematurely.

The initial architecture should favor:

* fast local tests;
* reliable CI;
* realistic database tests;
* deterministic fixtures;
* controlled external-service mocks;
* targeted integration environments;
* a small but meaningful E2E suite;
* platform testing for behavior that genuinely depends on the platform.

As user count, feature count, and infrastructure complexity increase, testing infrastructure may evolve accordingly.

The goal is not to maximize the number of tests.

The goal is to make incorrect behavior difficult to introduce, easy to detect, and safe to recover from.

---

# 63. Final Testing Invariant

The following principle is mandatory throughout Workaholic development:

> **No feature is complete merely because it works once. It is complete when its intended behavior, failure behavior, permissions, persistence, synchronization, platform behavior, and regression safety have been verified at the appropriate testing layers.**
