# `DESIGN-SYSTEM.md`

**Status:** FINAL
**Version:** 1.0
**Product:** Workaholic
**Scope:** Visual design language, typography, color, spacing, surfaces, components, states, icons, motion, responsive design, and accessibility

---

## 1. Purpose

This document defines the visual and interaction design system for Workaholic.

The design system exists to ensure that Web, Windows, and Android implementations behave as parts of the same product while allowing each platform to follow appropriate interaction conventions.

The design system MUST prioritize:

* Clarity
* Consistency
* Accessibility
* Long-session comfort
* Information hierarchy
* Efficient interaction
* Performance

Visual styling MUST support the product rather than compete with it.

---

# 2. Design Philosophy

Workaholic should communicate:

```text
Calm
Focused
Modern
Structured
Reliable
Personal
Premium
```

The interface SHOULD feel polished without appearing ornamental.

The visual hierarchy should make important information immediately recognizable.

---

# 3. Design Principles

## 3.1 Hierarchy over decoration

Visual weight MUST communicate importance.

Example:

```text
Primary action
    ↓
Secondary action
    ↓
Supporting information
    ↓
Metadata
```

Decorative effects MUST NOT overpower the hierarchy.

---

## 3.2 Consistency over novelty

Equivalent concepts MUST look and behave consistently.

For example:

```text
Task priority
Event importance
Reminder priority
```

may have different meanings, but their controls SHOULD use consistent interaction patterns.

---

## 3.3 Progressive complexity

Basic workflows SHOULD remain simple.

Advanced functionality SHOULD appear through:

* Expansion
* Secondary panels
* Context menus
* Advanced settings
* Dedicated detail views

---

# 4. Design Tokens

The implementation MUST use centralized design tokens rather than arbitrary values scattered throughout the application.

Token categories SHOULD include:

```text
Color
Typography
Spacing
Radius
Elevation
Opacity
Motion
Breakpoints
Component dimensions
```

---

# 5. Spacing System

The design SHOULD use a consistent spacing scale.

A base scale MAY be:

```text
4
8
12
16
20
24
32
40
48
64
```

The implementation MUST avoid unnecessary one-off spacing values.

Spacing tokens SHOULD be semantically named where practical.

Example:

```text
space.xs
space.sm
space.md
space.lg
space.xl
```

---

# 6. Layout Grid

Desktop layouts SHOULD generally use a flexible grid rather than fixed-width positioning.

The system SHOULD support:

```text
Sidebar
Main content
Optional secondary panel
```

Example:

```text
┌──────────────┬──────────────────────┬───────────────┐
│ Navigation   │ Main Content         │ Context Panel │
│              │                      │               │
└──────────────┴──────────────────────┴───────────────┘
```

The secondary panel MAY disappear at smaller widths.

---

# 7. Responsive Breakpoints

Breakpoints SHOULD be defined centrally.

Conceptual ranges:

```text
Mobile
Tablet
Desktop
Large Desktop
```

Exact pixel values SHOULD be chosen during implementation based on actual layouts rather than arbitrary framework defaults.

---

# 8. Typography

Typography MUST prioritize readability.

The system SHOULD define:

```text
Display
Heading 1
Heading 2
Heading 3
Body Large
Body
Body Small
Caption
Label
```

Each level MUST have defined:

* Font family
* Size
* Weight
* Line height
* Letter spacing where required

---

# 9. Typography Hierarchy

A typical hierarchy:

```text
Page title
   ↓
Section title
   ↓
Primary content
   ↓
Secondary information
   ↓
Metadata
```

The system SHOULD avoid excessive font-weight variation.

---

# 10. Body Text

Normal body text SHOULD remain comfortable for long reading sessions.

The design SHOULD avoid:

* Extremely small text
* Excessive line length
* Very tight line spacing
* Low-contrast secondary text

---

# 11. Color System

The color system MUST distinguish semantic roles from literal colors.

Recommended token categories:

```text
background
surface
surface-elevated
text-primary
text-secondary
text-muted
border
accent
success
warning
danger
info
```

Components SHOULD reference semantic tokens.

---

# 12. Theme Support

The design system MUST support:

```text
Light
Dark
System
```

where the platform supports system theme detection.

Theme switching MUST preserve semantic meaning.

---

# 13. Dark Theme

Dark mode SHOULD not simply invert colors.

It SHOULD use a hierarchy of surfaces:

```text
Base background
   ↓
Surface
   ↓
Elevated surface
   ↓
Modal / overlay
```

Excessively bright surfaces SHOULD be avoided.

---

# 14. Light Theme

Light mode SHOULD preserve sufficient contrast while maintaining the calm visual character of the product.

Pure white may be used where appropriate, but the entire application SHOULD NOT rely on extreme white-on-white separation.

---

# 15. Accent Color

A primary accent SHOULD be used consistently for:

* Primary actions
* Selected navigation
* Focus indicators
* Active controls
* Important interactive states

Accent usage SHOULD remain restrained.

---

# 16. Semantic Colors

Semantic colors SHOULD communicate:

```text
Success
Warning
Danger
Information
```

They MUST NOT be the sole means of communicating state.

Example:

```text
Overdue
[Danger icon] Overdue
```

rather than simply changing text color.

---

# 17. Glass Surfaces

Workaholic MAY use glass-like surfaces.

A glass surface SHOULD combine:

```text
Translucency
Blur
Subtle border
Controlled elevation
```

It MUST maintain sufficient contrast with the content behind it.

---

# 18. Glass Usage

Glass effects SHOULD primarily be used for:

* Navigation
* Floating panels
* Dialogs
* Contextual surfaces
* Selected premium UI areas

The entire interface SHOULD NOT become a wall of translucent cards.

---

# 19. Performance of Visual Effects

Blur, translucency, shadows, and gradients MUST be used carefully.

The implementation SHOULD avoid excessive GPU cost, especially on:

* Windows laptops
* Android devices
* Lower-powered systems
* Battery-powered devices

Accessibility and performance take precedence over visual effects.

---

# 20. Border Radius

The system SHOULD use a consistent radius scale.

Conceptually:

```text
Small
Medium
Large
Pill
```

Examples:

```text
Small:
Inputs

Medium:
Cards

Large:
Dialogs / prominent panels

Pill:
Tags / compact controls
```

---

# 21. Elevation

Elevation SHOULD communicate hierarchy rather than decoration.

Possible hierarchy:

```text
Base
Surface
Elevated
Floating
Modal
```

Excessive shadows SHOULD be avoided.

---

# 22. Cards

Cards SHOULD group meaningful information.

A card SHOULD NOT exist merely because a rectangular container looks attractive.

Example:

```text
Task Card
├── Title
├── Priority
├── Deadline
└── Status
```

---

# 23. Task Card

Task cards SHOULD provide:

* Clear title
* Completion control
* Optional priority indicator
* Deadline/status information
* Context such as project or board

Secondary metadata SHOULD remain visually subordinate.

---

# 24. Event Card

Event representations SHOULD prioritize:

```text
Time
Title
Calendar/source
```

Additional information MAY include:

```text
Location
Attendees
Reminder
Related task
```

---

# 25. Calendar Event Colors

Calendar colors MAY identify calendar/source.

Color usage MUST remain accessible.

Events SHOULD retain readable text and clear boundaries even when color perception is unavailable.

---

# 26. Status Representation

Statuses SHOULD use:

* Label
* Optional icon
* Optional color
* Consistent shape

Example:

```text
[To Do]
[In Progress]
[Done]
```

---

# 27. Priority Representation

Priority SHOULD remain visually distinct from status.

Example:

```text
Status:
In Progress

Priority:
High
```

The UI MUST NOT rely on the same visual mechanism for both.

---

# 28. Labels and Tags

Tags SHOULD use compact pill/chip components.

Example:

```text
[College] [Urgent] [Backend]
```

Tag colors MAY be user-defined but MUST maintain readable text.

---

# 29. Buttons

Buttons SHOULD have clear hierarchy:

```text
Primary
Secondary
Tertiary
Destructive
Icon-only
```

Example:

```text
[Create Task]
[Cancel]
[More]
[Delete]
```

---

# 30. Primary Button

A primary button SHOULD represent the most important action in the current context.

A screen SHOULD avoid presenting multiple visually equal primary actions unless genuinely necessary.

---

# 31. Destructive Buttons

Destructive actions SHOULD be visually distinct.

Examples:

* Delete
* Remove access
* End semester
* Revoke access

High-impact destructive actions SHOULD require confirmation.

---

# 32. Icon Buttons

Icon-only controls MUST have:

* Accessible labels
* Tooltips where appropriate
* Adequate touch/click target size

An unfamiliar icon MUST NOT be the sole communication method for an important action.

---

# 33. Inputs

Inputs SHOULD have:

* Clear label
* Predictable focus behavior
* Validation state
* Error messaging
* Appropriate placeholder usage

Placeholder text MUST NOT replace the label.

---

# 34. Forms

Forms SHOULD be divided into logical sections.

Example:

```text
Task
├── Basic
├── Scheduling
├── Organization
├── Reminders
└── Advanced
```

---

# 35. Selectors

Dropdowns/selectors SHOULD be used when the number of choices is manageable.

For larger lists, the system SHOULD provide:

* Search
* Filtering
* Grouping
* Recent choices

---

# 36. Date and Time Pickers

Date/time pickers MUST support efficient keyboard/touch interaction according to platform.

Common choices SHOULD be quick:

```text
Today
Tomorrow
Next week
Custom
```

---

# 37. Calendar Picker

The calendar picker SHOULD make date selection easy without requiring users to navigate unnecessarily far.

---

# 38. Modals

Modals SHOULD be reserved for focused decisions or short forms.

A modal MUST NOT become a substitute for normal application navigation.

---

# 39. Drawers and Side Panels

Side panels SHOULD be used when users need context while retaining the underlying page.

Good use:

```text
Calendar
   ↓
Event details panel
```

The calendar remains visible.

---

# 40. Tooltips

Tooltips SHOULD explain unfamiliar controls.

They MUST NOT contain essential information that is inaccessible otherwise.

---

# 41. Context Menus

Context menus MAY expose secondary operations.

They SHOULD NOT contain the only way to perform critical operations.

---

# 42. Toasts

Toasts SHOULD communicate short-lived status.

Examples:

```text
Task completed
Saved
Changes synced
Copied
```

Important errors MUST NOT exist only as transient toasts.

---

# 43. Undo Notifications

For reversible operations:

```text
Task archived
[Undo]
```

is preferred where practical.

The undo window SHOULD be long enough for normal human reaction.

---

# 44. Loading Indicators

The system SHOULD use:

```text
Skeleton
Spinner
Progress indicator
Optimistic state
```

depending on operation type.

For predictable content-heavy pages, skeleton loading SHOULD be preferred where it improves perceived stability.

---

# 45. Skeleton Design

Skeletons SHOULD approximate the final layout.

They SHOULD NOT introduce excessive animation.

---

# 46. Empty States

Empty states SHOULD contain:

```text
What is empty
Why it matters
What the user can do
```

Example:

```text
No scheduled work today.

[Schedule a task]
```

---

# 47. Error Components

Errors SHOULD be represented consistently.

Example:

```text
Unable to load tasks.

[Retry]
```

Where appropriate:

```text
Your changes are saved locally.
They will sync when connection returns.
```

---

# 48. Inline Validation

Validation SHOULD occur near the affected field.

Example:

```text
Start time
[15:00]

End time
[14:00]
Error:
End time must be after start time.
```

---

# 49. Focus State

Interactive elements MUST have a clearly visible focus state.

Focus indication MUST remain visible in both themes.

---

# 50. Hover State

Desktop interactive controls SHOULD have subtle hover feedback.

Hover MUST NOT be required for understanding functionality on touch devices.

---

# 51. Pressed State

Buttons and interactive controls SHOULD communicate active/pressed state.

---

# 52. Disabled State

Disabled controls SHOULD clearly communicate their unavailable state.

The interface SHOULD avoid disabling controls without explaining why when the reason may be unclear.

---

# 53. Selection State

Selected items SHOULD have a clear state.

Examples:

```text
Selected board column
Selected calendar
Selected task
Selected navigation item
```

Selection MUST remain understandable without relying exclusively on color.

---

# 54. Drag State

Dragged objects SHOULD visually communicate:

```text
Being dragged
Potential destination
Invalid destination
```

Keyboard/touch alternatives MUST remain available.

---

# 55. Notification States

Notifications SHOULD distinguish:

```text
Unread
Read
Snoozed
Dismissed
Failed delivery
```

The visual distinction SHOULD remain subtle but discoverable.

---

# 56. Calendar States

Calendar events SHOULD visually support:

```text
Normal
Selected
Current
Conflict
Cancelled
Tentative
Private
External
```

Cancelled events SHOULD remain identifiable rather than simply disappearing when historical context matters.

---

# 57. Academic Calendar States

Academic dates SHOULD communicate:

```text
Working
Holiday
Special working
Cancelled class
Rescheduled class
```

The UI MUST avoid representing all of these merely as colored dots.

---

# 58. Data Density

Workaholic has inherently dense data.

The system SHOULD provide multiple density levels where useful:

```text
Comfortable
Compact
```

Default density SHOULD favor readability.

---

# 59. Long Lists

Long lists SHOULD support:

* Virtualization where necessary
* Sticky context where useful
* Search/filtering
* Pagination or incremental loading

The UI MUST remain responsive.

---

# 60. Tables

Tables SHOULD be used when users need to compare structured attributes.

They SHOULD support:

* Clear headers
* Row actions
* Responsive adaptation
* Horizontal scrolling where necessary
* Keyboard navigation

---

# 61. Mobile Cards

On small screens, tables MAY become stacked cards where comparison remains understandable.

---

# 62. Navigation Components

The system SHOULD define standard:

* Sidebar
* Bottom navigation
* Tabs
* Breadcrumbs
* Back navigation
* Section navigation

Equivalent navigation patterns MUST behave consistently.

---

# 63. Tabs

Tabs SHOULD represent related views within the same context.

They SHOULD NOT become a dumping ground for unrelated features.

---

# 64. Breadcrumbs

Breadcrumbs MAY be used on complex desktop workflows.

Example:

```text
Projects
  / Workaholic
    / Backend
      / API
```

They may be omitted from simple mobile screens.

---

# 65. Search Component

Search SHOULD support:

* Global search
* Recent searches where useful
* Result categories
* Keyboard navigation
* Clear query action

---

# 66. Command Palette Design

The command palette SHOULD feel lightweight.

Example:

```text
Search commands...

Create task
Create event
Open Today
Open Calendar
```

It SHOULD support keyboard navigation and accessible announcements.

---

# 67. Today Design

Today should have the highest visual priority in the application.

The interface SHOULD visually distinguish:

```text
Now
Upcoming
Due
Overdue
Important
Unscheduled
```

without turning every category into a competing visual alarm.

---

# 68. Today Priority Hierarchy

Recommended hierarchy:

```text
1. Current / imminent
2. Overdue
3. Due today
4. Scheduled work
5. Important
6. Unscheduled/backlog
```

The exact ranking may be refined through product testing.

---

# 69. Calendar Design

Calendar grids SHOULD prioritize:

* Time alignment
* Event readability
* Current time
* Drag interactions
* Conflict visibility

Decorative surfaces MUST NOT make event boundaries ambiguous.

---

# 70. Board Design

Kanban columns SHOULD remain visually distinct.

Example:

```text
┌────────────┐ ┌────────────┐ ┌────────────┐
│ BACKLOG    │ │ IN PROGRESS│ │ DONE       │
│            │ │            │ │            │
│ Task       │ │ Task       │ │ Task       │
│ Task       │ │ Task       │ │ Task       │
└────────────┘ └────────────┘ └────────────┘
```

---

# 71. Notes Design

The notes editor SHOULD prioritize writing.

Toolbar controls SHOULD not dominate the screen.

Editing mode SHOULD minimize distractions while preserving access to:

* Formatting
* Links
* Attachments
* Relationships
* Tags

---

# 72. Rich Text Editor

The editor SHOULD support:

```text
Headings
Bold
Italic
Lists
Checklists
Links
Tables
Code blocks
Images
Attachments
```

The exact editor library is an implementation decision.

---

# 73. Attachments UX

Attachments SHOULD show:

* File name
* Type
* Size where relevant
* Upload state
* Error state
* Open/download action
* Remove relationship action

The UI MUST distinguish:

```text
Remove attachment from Workaholic
```

from:

```text
Delete underlying Drive file
```

---

# 74. Integration UI

Connected services SHOULD use recognizable provider identity while keeping the Workaholic design consistent.

Each integration card SHOULD show:

```text

```

# 75. Sync Indicators

Sync status SHOULD use concise language.

Examples:

```text
Synced
Syncing…
Offline
Changes pending
Needs attention
```

Technical identifiers SHOULD remain hidden unless shown in diagnostics.

---

# 76. Security UI

Security-sensitive screens SHOULD prioritize clarity over visual experimentation.

Examples:

* Sessions
* Permissions
* Trusted users
* Integrations
* Public links

These screens MUST make consequences clear.

---

# 77. Privacy Indicators

Private resources SHOULD have consistent indicators where useful.

Example:

```text
🔒 Private
```

The actual iconography should follow the icon system.

---

# 78. Accessibility Contrast

Text and interactive elements MUST maintain appropriate contrast according to the accessibility target adopted by the implementation.

The design system MUST NOT sacrifice contrast for glass effects.

---

# 79. Reduced Motion

The application MUST support reduced-motion preferences.

When enabled:

* Decorative animations SHOULD disappear.
* Transitions SHOULD be shortened.
* Large motion effects SHOULD be avoided.
* Functional feedback MUST remain.

---

# 80. Screen Reader Semantics

Components MUST communicate:

* Name

# 81. Keyboard Accessibility

# 82. Touch Accessibility

Mobile interactions MUST support:

* Tap

# 83. Responsive Glass Effects

Glass effects MAY be reduced or removed on lower-powered devices if necessary.

# 84. Desktop Window Behavior

The Windows application SHOULD support:

# 85. Android System Integration

Android UI SHOULD respect:

* System back navigation
* System theme
* Safe areas
* Keyboard
* Notification conventions

---

# 86. Web Browser Integration

The web application SHOULD respect:

* Browser viewport
* Keyboard navigation
* Browser zoom
* Reduced motion
* Dark/light preference

---

# 87. Internationalization Readiness

The design system SHOULD avoid layouts that assume every string has a fixed length.

Components MUST tolerate:

```text
Longer translations
Different date formats
Different number formats
Different text directions
```

Right-to-left support MAY be implemented later but the design SHOULD avoid hard-coded directional assumptions.

---

# 88. Date Formatting

Date formatting SHOULD be localized according to user/platform preferences.

The system MUST preserve unambiguous formatting for dates where confusion is possible.

---

# 89. Icon System

Icons SHOULD come from a consistent icon library/system.

Mixing unrelated icon styles SHOULD be avoided.

Important actions SHOULD use recognizable symbols.

---

# 90. Illustration System

Illustrations MAY be used for:

* Onboarding
* Empty states
* Major feature introductions

They SHOULD NOT occupy excessive space in productivity workflows.

---

# 91. Microcopy

UI text SHOULD be:

* Clear
* Concise
* Human
* Action-oriented

Avoid unnecessarily technical language.

Poor:

```text
Mutation synchronization failure.
```

Preferred:

```text
Couldn't sync this change.
```

---

# 92. Confirmation Copy

Confirmations SHOULD explain consequence.

Example:

```text
End this semester?

Future generated class events will be removed or invalidated.
Past classes and your reusable schedule will remain.
```

---

# 93. Success Feedback

Success feedback SHOULD be proportionate.

Routine operations SHOULD use subtle feedback.

Examples:

```text
Task completed
Saved
Synced
```

Major operations MAY use stronger confirmation.

---

# 94. Error Copy

Error messages SHOULD be actionable.

Preferred:

```text
Couldn't connect to Google Calendar.
[Reconnect]
```

rather than:

```text
OAuthException: 401.
```

Technical diagnostics MAY be available separately.

---

# 95. Empty State Copy

Empty states SHOULD avoid blaming the user.

Preferred:

```text
No events today.
```

rather than:

```text
You haven't created any events.
```

---

# 97. Design-System Component States

Reusable components SHOULD define:


# 98. Component Documentation

Each reusable component SHOULD document:

* Purpose
* Variants
* States
* Accessibility requirements
* Responsive behavior
* Usage constraints

---

# 99. Design-System Governance

New UI components SHOULD first determine whether an existing component can satisfy the requirement.

The implementation SHOULD avoid creating:

```text
TaskButton
TaskActionButton
TaskPrimaryButton
TaskQuickButton
TaskSmallActionButton
```

when one reusable button system with appropriate variants is sufficient.

---

# 100. No One-Off Styling

Production screens SHOULD avoid arbitrary styling values unless the value is genuinely unique.

Repeated patterns MUST become reusable tokens/components.

---

# 101. UX/Design Boundary

This document defines the visual and interaction system.

`UX-SPECIFICATION.md` defines broader user workflows and behavior.

`CALENDAR-SPECIFICATION.md`, `NOTIFICATION-SPECIFICATION.md`, and other domain specifications define domain semantics.

Where they overlap:

```text
Domain behavior
    ↓
UX behavior
    ↓
Visual representation
```

Visual styling MUST NOT change domain semantics.

# 103. Final Design System Model

```text
                         DESIGN SYSTEM
                               │
          ┌────────────────────┼────────────────────┐
          │                    │                    │
          ▼                    ▼                    ▼
       Tokens             Components            Layout
          │                    │                    │
    ┌─────┼─────┐        ┌─────┼─────┐       ┌────┼────┐
    ▼     ▼     ▼        ▼     ▼     ▼       ▼    ▼    ▼
  Color  Type  Space    Button Input Card   Desktop Mobile
    │     │     │        │     │     │
    └─────┴─────┴────────┴─────┴─────┘
                         │
                         ▼
                   Product Screens
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
      Web             Windows            Android
```

The central principle is:

> **Workaholic should have one visual language, not one identical layout. The same concepts must remain recognizable across platforms while each platform is allowed to use the interaction patterns that make sense there.**

The design system therefore provides the visual grammar, while the UX specification defines how that grammar is used to make the product fast, understandable, accessible, and comfortable for everyday work.
