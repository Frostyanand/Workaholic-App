# 1. Purpose

This document defines the conceptual domain model of Workaholic.

It specifies:

- core entities
- entity responsibilities
- ownership
- relationships
- lifecycle boundaries
- source/provenance concepts
- distinction between similar concepts
- cross-domain relationships
- entities that belong to future subsystems

This document defines the domain independently of a particular database technology.

It MUST be used as the conceptual basis for database design, API design, synchronization, authorization, and application implementation.

---

# 2. Domain Modeling Principles

## 2.1 Native Workaholic Objects

Workaholic's core objects are native application entities.

Examples:

- Task
- Project
- Board
- Calendar
- Event
- Reminder
- Note
- Booking
- Semester

External objects such as Google Calendar events and Google Tasks are not treated as native Workaholic objects.

---

## 2.2 Stable Native Identity

Every persistent Workaholic entity MUST have its own stable native identifier.

External provider identifiers MUST be stored separately.

Example:

```text
Workaholic Task
    id = task_123

Google Task
    external_id = google_task_456
````

The two identifiers MUST NOT be conflated.

---

## 2.3 Ownership

Every persistent resource MUST have a clearly defined ownership context.

A resource may be:

* user-owned
* workspace-owned
* project-owned
* calendar-owned
* system-owned
* externally owned

Ownership and authorization are separate concepts.

---

## 2.4 Relationships

Relationships between entities SHOULD be explicit.

A relationship SHOULD NOT be represented solely through duplicated textual information when a structured relationship is required.

---

## 2.5 Lifecycle Independence

Entities that happen to be related MUST NOT automatically share the same lifecycle unless explicitly defined.

Examples:

* deleting a task does not necessarily delete its Drive attachment
* ending a semester does not delete the reusable class schedule
* disconnecting Google does not delete native Workaholic data
* completing subtasks does not automatically complete the parent task

---

# 4. Identity Domain

## 4.1 User

### Responsibility

Represents a Workaholic account holder.

### Core properties

A User may have:

* native user ID
* authentication identity mapping
* display name
* email
* profile image
* timezone
* locale
* preferences

### Relationships

A User may:

* own workspaces
* belong to workspaces
* own tasks
* own projects
* own calendars
* create events
* create notes
* create reminders
* own bookings
* register devices
* maintain sessions
* authorize integrations

---

## 4.2 External Identity

Represents an authentication identity supplied by an external identity provider.

Example:

```text
User
└── External Identity
      provider = Google
      provider_user_id = ...
```

External authentication identity MUST remain separate from the Workaholic User entity.

---

## 4.3 Device

Represents a physical or logical client installation associated with a user.

Examples:

* Windows laptop
* Android phone
* web browser
* future tablet

A Device may contain:

* device identifier
* platform
* application version
* push-token information
* last-seen information
* trust state

Devices are relevant to:

* synchronization
* notifications
* sessions
* local reminders

---

## 4.4 Session

Represents an authenticated access session.

A session belongs to a user and is associated with a device where applicable.

Sessions have an explicit lifecycle.

Possible states include:

```text
Active
Expired
Revoked
```

A revoked session MUST NOT remain authorized.

---

# 5. Workspace Domain

## 5.1 Workspace

A Workspace is the primary ownership boundary for collaborative resources.

A personal workspace may contain an individual's private productivity data.

A team workspace may contain shared work.

### Relationships

A Workspace may contain:

* memberships
* projects
* boards
* tasks
* calendars
* notes
* people
* collaboration resources

---

## 5.2 Workspace Membership

Represents a user's membership in a workspace.

A membership contains:

* user
* workspace
* role
* permission configuration
* membership status

Membership is distinct from the User entity.

---

## 5.3 Role

Represents a coarse authorization role.

Initial roles:

```text
Owner
Admin
Manager
Member
Viewer
Guest
```

Roles provide baseline permissions.

Fine-grained authorization MUST remain possible independently of role.

---

## 5.4 Permission

Represents an individual authorization capability.

Examples:

```text
task.create
task.edit
task.delete
task.assign
project.manage
calendar.view
calendar.share
workspace.manage
member.manage
```

The exact permission catalogue is defined by `PERMISSIONS-MODEL.md`.

---

# 6. Task Domain

## 6.1 Task

A Task represents actionable work.

A task is not inherently a calendar event.

### Core characteristics

A Task may have:

* title
* description
* status
* priority
* due date/time
* start date
* estimated duration
* completion state
* labels
* project relationship
* board relationship
* assignee
* creator
* parent task
* dependencies
* scheduled work blocks
* reminders
* attachments
* comments
* notes
* external mappings

### Ownership

A Task is owned by an appropriate user/workspace context.

### Lifecycle

Typical lifecycle:

```text
Created
    ↓
Planned / Inbox
    ↓
In Progress
    ↓
Completed
```

Additional custom statuses may exist.

---

## 6.2 Parent Task / Subtask

A Task may have another Task as its parent.

Therefore subtasks are modeled as Tasks with a hierarchical relationship rather than as an entirely unrelated entity type.

Example:

```text
Task: Prepare Barclays application
│
├── Update resume
├── Review SQL
├── Review OOP
└── Submit application
```

A parent Task MUST remain independently completable.

Completion of all children MUST NOT automatically complete the parent.

---

## 6.3 Task Status

Represents the current workflow state of a Task.

Statuses may be:

* system-defined
* board-defined
* workspace-defined where appropriate

A Board may provide a custom status workflow.

---

## 6.4 Priority

Represents task urgency/importance.

Initial priority levels:

```text
P0 Critical
P1 Urgent
P2 High
P3 Medium
P4 Low
```

Priority is independent of status.

---

## 6.5 Label

A Label is a reusable classification applied to one or more resources.

Labels may represent:

* category
* topic
* context
* department
* project type
* personal classification

Labels MUST NOT be confused with task status or priority.

---

## 6.6 Task Dependency

Represents a logical relationship between Tasks.

Initial relationship types:

```text
blocks
blocked_by
depends_on
related_to
```

Dependencies are distinct from parent/subtask relationships.

Example:

```text
Task A
   │
   └── blocks
          ↓
       Task B
```

A task being a subtask of another task does not inherently mean it is a dependency.

---

## 6.7 Scheduled Work Block

Represents a planned period of work assigned to a Task.

Example:

```text
Task:
Study Computer Networks

Work Block:
2026-09-07
19:00 → 21:00
```

A Task may have multiple work blocks.

A Work Block is not the same entity as the Task deadline.

---

# 7. Board Domain

## 7.1 Board

A Board represents a visual/workflow organization system.

A Board may belong to a workspace and/or be associated with a project.

Examples:

```text
College
Career
Personal
Project Alpha
```

---

## 7.2 Board Column

A Board Column represents a workflow state within a Board.

Example:

```text
Backlog
Todo
In Progress
Review
Done
```

Columns may map to Task statuses.

The exact relationship between Board Columns and Task Statuses will be finalized in the technical specification.

# 8. Project Domain

## 8.1 Project

A Project represents a larger body of related work.

A Project may contain or relate to:

* tasks
* boards
* notes
* files
* people
* calendar events
* milestones
* activity

A Task does not require a Project.

---

## 8.2 Milestone

A Milestone represents a significant checkpoint within a Project.

Examples:

```text
Project: Website Launch

Milestone:
Design Complete

Milestone:
Beta Release

Milestone:
Production Launch
```

Milestones are optional and may be implemented after the core Project/Task model.

---

# 9. Calendar Domain

## 9.1 Calendar

A Calendar is a container for events.

Calendars may represent:

* personal schedule
* work
* college
* holidays
* birthdays
* Google Calendar
* imported schedules
* bookings
* other sources

A user may have multiple calendars.

---

## 9.2 Calendar Source

A Calendar Source identifies the origin of calendar data.

Examples:

```text
WORKAHOLIC
GOOGLE
COLLEGE
DAY_ORDER
HOLIDAY
BOOKING
IMPORTED
```

Source information is required to safely perform source-specific operations.

---

## 9.3 Calendar Event

An Event represents something occurring during a defined period.

An Event may contain:

* title
* description
* start
* end
* timezone
* all-day state
* location
* meeting link
* attendees
* recurrence
* reminders
* privacy
* source
* related tasks
* related projects
* related notes
* related people
* attachments

Events are distinct from Tasks.

---

## 9.4 Event Visibility

Events may have visibility appropriate to their context.

At minimum, the domain must distinguish:

```text
Private
Shared
Public
```

Visibility controls what authorized viewers may see.

---

## 9.5 Recurrence Rule

A Recurrence Rule defines how an event, reminder, or other recurring object repeats.

The recurrence model should support:

* interval
* frequency
* weekdays
* monthly patterns
* yearly patterns
* end date
* occurrence count
* unlimited recurrence

A recurring series and its individual occurrences must be conceptually distinguishable.

---

# 10. Academic Scheduling Domain

## 10.1 Semester

Represents an academic period.

A Semester owns or references the academic scheduling configuration used during that period.

A Semester may have:

* name
* academic year
* start date
* end date
* status
* academic calendar
* Day Order configuration

---

## 10.2 Academic Calendar

Represents working/non-working academic dates.

It may contain:

* regular working days
* holidays
* special working days
* examinations
* academic events
* cancellations

---

## 10.3 Day Order

Represents an academic day-order value.

Example:

```text
DO 1
DO 2
DO 3
...
```

A Day Order is an abstract schedule value and is not itself a calendar event.

---

## 10.4 Day Order Sequence

Represents the mapping between calendar working dates and Day Orders.

Example:

```text
Monday     → DO 1
Tuesday    → DO 2
Wednesday  → Holiday
Thursday   → DO 3
Friday     → DO 4
```

The sequence MUST account for:

* holidays
* weekends
* special working days
* explicit academic exceptions

---

## 10.5 Class Schedule

Represents a reusable class schedule definition associated with one or more Day Orders.

Example:

```text
DO 1
09:00 → Computer Networks
10:00 → DBMS
11:00 → OOP
```

The reusable definition MUST remain independent from generated calendar occurrences.

---

## 10.6 Schedule Entry

Represents one entry within a reusable class schedule.

Example:

```text
Day Order: 1
Time: 09:00–10:00
Subject: Computer Networks
Room: ...
```

---

## 10.7 Generated Academic Event

Represents a calendar event generated from an academic schedule.

It MUST retain provenance sufficient to identify:

* semester
* academic schedule
* Day Order
* schedule entry
* generation source

This allows future generated occurrences to be safely removed or recalculated without affecting unrelated calendar events.

---

## 10.8 Academic Exception

Represents an explicit deviation from the normal academic schedule.

Examples:

* holiday
* cancelled class
* rescheduled class
* special working day
* special Day Order

Exceptions MUST NOT be represented merely as undocumented modifications to generated events.

---

# 11. Reminder Domain

## 11.1 Reminder

A Reminder represents an instruction to notify a user or authorized recipient about something at a particular time or according to a trigger.

A Reminder may be associated with:

* Task
* Event
* Booking
* other supported objects

---

## 11.2 Reminder Trigger

Represents when a Reminder should activate.

Examples:

```text
Exact time:
19:00

Relative:
30 minutes before event

Deadline:
At task deadline
```

---

## 11.3 Reminder Priority/Level

Represents the attention level of a Reminder.

Initial conceptual levels:

```text
Normal
Important
Alarm
Shared Important
Shared Alarm
```

---

## 11.4 Reminder Recipient

Represents an intended recipient of a Reminder.

A recipient may be:

* the owner
* an explicitly authorized trusted user
* another authorized participant

Recipients are independent notification targets.

---

# 12. Notification Domain

## 12.1 Notification

A Notification represents a delivered or deliverable user-facing alert generated from an event, reminder, collaboration action, or system activity.

A Notification is distinct from the Reminder that caused it.

Example:

```text
Reminder
    ↓
Notification
    ↓
Android / Windows / Web
```

---

## 12.2 Notification Delivery

Represents delivery through a particular channel/device.

Possible channels include:

* local device notification
* push notification
* in-app notification
* future email

Delivery state should be independently trackable where required.

---

# 13. Notes Domain

## 13.1 Note

A Note represents user-created knowledge or information content.

A Note may contain:

* rich text
* headings
* lists
* checklists
* links
* images
* code blocks
* tables
* attachments
* tags

---

## 13.2 Note Relationship

A Note may relate to:

* Task
* Project
* Event
* Person
* Board

Relationships are explicit.

A Note does not automatically become a Task because it contains a checklist.

---

# 14. File and Attachment Domain

## 14.1 Attachment

An Attachment represents a Workaholic relationship to a file.

The attachment relationship may point to an external storage object.

Example:

```text
Task
  ↓
Attachment
  ↓
Google Drive File
```

The Attachment and external Drive file have separate lifecycles.

---

## 14.2 External File

Represents the external file stored by an integration provider.

For Google Drive:

```text
External File
provider = Google Drive
external_id = ...
```

Removing the Workaholic Attachment relationship MUST NOT automatically delete the External File.

---

# 15. People Domain

## 15.1 Person

A Person represents another identifiable participant relevant to Workaholic.

Depending on context, a Person may be:

* workspace member
* trusted user
* collaborator
* booking guest
* event attendee

The domain SHOULD avoid creating duplicate person identities when an authenticated Workaholic user already exists.

---

## 15.2 Trusted Relationship

Represents an explicit relationship allowing one Workaholic user to grant another user controlled access.

The relationship includes:

* owner
* trusted user
* permissions
* status
* creation time
* revocation state

A Trusted Relationship is not equivalent to workspace membership.

---

# 16. Booking Domain

## 16.1 Booking Page

Represents a public-facing scheduling configuration.

A Booking Page may define:

* owner
* name
* description
* availability
* appointment types
* timezone
* public visibility
* booking rules

---

## 16.2 Availability Rule

Defines when appointments may be booked.

Rules may specify:

* weekdays
* time windows
* effective dates
* exceptions
* timezone

---

## 16.3 Booking Type

Represents an appointment offering.

A Booking Type may define:

* duration
* buffers
* minimum notice
* maximum booking horizon
* cancellation rules
* rescheduling rules
* location
* meeting link
* optional task creation

---

## 16.4 Booking

Represents a confirmed or pending appointment request.

A Booking may contain:

* guest information
* booking type
* start/end
* timezone
* status
* associated calendar event
* optional task

---

## 16.5 Booking Guest

Represents an external person making a booking.

A guest does not require a Workaholic account.

---

# 17. Integration Domain

## 17.1 Integration

Represents a connection between Workaholic and an external service.

Examples:

```text
Google
```

An Integration may have:

* provider
* authorization state
* account mapping
* scopes
* connection status
* synchronization state

---

## 17.2 External Account

Represents the external account authorized for an integration.

Example:

```text
Workaholic User
    ↓
Google Integration
    ↓
Google Account
```

---

## 17.3 External Object

Represents a mapping between a Workaholic object and an external provider object.

Example:

```text
Workaholic Task
    ↕
External Object
    provider = Google Tasks
    external_id = ...
```

External Object records SHOULD retain sufficient synchronization metadata to support two-way synchronization.

---

## 17.4 Sync Record

Represents synchronization state between native and external representations.

Potential information includes:

* native object ID
* external object ID
* provider
* object type
* synchronization version/state
* last synchronization time
* external modification time
* native modification time
* error state

The detailed synchronization model is defined in `SYNC-SPECIFICATION.md`.

# 18. Collaboration Domain

## 18.1 Comment

A Comment represents contextual discussion attached to a supported resource.

Comments may belong to:

* Task
* Project
* Event
* Note
* future collaboration objects

---

## 18.2 Activity Entry

An Activity Entry records a meaningful change or action.

Examples:

```text
Task created
Task assigned
Status changed
Priority changed
Comment added
Attachment added
Member removed
Permission changed
```

Activity is historical information and should not be confused with current entity state.

---

## 18.3 Mention

A Mention represents an explicit reference to another user in a collaborative context.

Example:

```text
@User please review this.
```

Mentions may generate notifications.

---

# 19. Chat Domain

Chat is a future subsystem.

## 19.1 Conversation

Represents a future direct, group, or project conversation.

---

## 19.2 Message

Represents a future chat message.

Potential properties include:

* sender
* conversation
* content
* timestamp
* attachments
* reply relationship
* edit state
* deletion state

Chat is not part of the initial implementation.

A document/realtime datastore such as Firestore MAY be used for this subsystem in the future.

# 20. Public Sharing Domain

## 20.1 Public Calendar Link

Represents a revocable public reference to a user's public calendar representation.

A public link MUST NOT itself grant authenticated Workaholic account access.

---

## 20.2 Public Calendar Projection

The public calendar representation is a privacy-filtered view of calendar data.

It MUST NOT expose information that the underlying event's visibility rules prohibit.

Example:

```text
Private Event
     ↓
Public Projection
     ↓
Busy
```

rather than exposing:

```text
Doctor Appointment
```

---

# 21. Search Domain

Search is conceptually a cross-domain capability rather than a primary business entity.

Search may index:

* Tasks
* Projects
* Boards
* Events
* Notes
* People
* Files
* Comments
* future Messages

Search indexes MUST NOT become an independent source of truth.

---

# 22. Synchronization Domain

Synchronization is a system capability operating across domain entities.

It applies to:

```text
Device ↔ Cloud
Cloud ↔ Device
Workaholic ↔ Google
```

The synchronization layer MUST preserve native entity identity and external identity separately.

Synchronization metadata is not part of the business meaning of the underlying object.

---

# 23. Relationship Rules

## 23.1 Task and Project

```text
Project
   └── Task
```

A Task MAY exist without a Project.

---

## 23.2 Task and Board

```text
Board
   └── Task
```

A Task MAY exist without a Board.

---

## 23.3 Task and Calendar

```text
Task
 ├── Deadline
 └── Scheduled Work Block
          ↓
       Calendar
```

A Task does not become an Event merely because it is scheduled.

---

## 23.4 Task and Reminder

```text
Task
  ↓
Reminder
  ↓
Notification
```

A Task may have zero or more reminders.

---

## 23.5 Event and Reminder

```text
Event
  ↓
Reminder
  ↓
Notification
```

An Event may have zero or more reminders.

---

## 23.6 Task and Note

A Task MAY relate to one or more Notes.

A Note MAY relate to one or more Tasks.

The relationship does not change either object's identity.

---

## 23.7 Project and Note

Projects MAY have associated Notes.

---

## 23.8 Project and Board

A Project MAY use one or more Boards.

A Board MAY exist independently of a Project.

---

## 23.9 Event and Task

An Event MAY be related to a Task.

The relationship does not make them the same object.

---

## 23.10 Booking and Event

A confirmed Booking MUST be capable of creating an associated Calendar Event.

The Booking and Event remain separate domain entities.

---

# 24. Lifecycle Independence Rules

The following relationships MUST remain lifecycle-independent unless an explicit rule says otherwise.

### Task → Attachment

Deleting the Task does not inherently delete the external file.

### Attachment → Drive File

Removing the attachment relationship does not delete the Drive file.

### Semester → Class Schedule

Ending a semester does not delete reusable schedule definitions.

### Semester → Past Events

Ending a semester does not delete historical academic events.

### Semester → Unrelated Events

Ending a semester does not delete unrelated calendar events.

### Google Integration → Native Data

Disconnecting Google does not delete native Workaholic data.

### Parent Task → Subtasks

Completing all subtasks does not automatically complete the parent.

### Overdue Task → Deadline

An overdue task retains its deadline until explicitly changed.

---

# 25. Source and Provenance Model

Entities generated or imported from external systems MUST retain provenance where necessary.

Example:

```text
Calendar Event
├── source = WORKAHOLIC
├── source = GOOGLE
├── source = DAY_ORDER
├── source = HOLIDAY
├── source = BOOKING
└── source = IMPORTED
```

For generated academic events:

```text
Event
├── source = DAY_ORDER
├── semester_id
├── day_order
├── schedule_id
└── schedule_entry_id
```

This provenance MUST be sufficient for safe bulk operations and synchronization.

---

# 26. Ownership Model

Conceptually:

```text
User
│
├── Personal Resources
│
└── Workspace Membership
       ↓
    Workspace
       │
       ├── Projects
       ├── Boards
       ├── Tasks
       ├── Calendars
       ├── Notes
       └── Collaboration
```

A resource MUST have an unambiguous authorization context.

The exact database ownership representation is defined separately in `DATABASE-DESIGN.md`.

---

# 27. Deletion Model

The domain distinguishes:

1. Active
2. Archived
3. Soft-deleted / Trashed
4. Permanently deleted

Not every entity requires every lifecycle state.

Permanent deletion MUST be used cautiously for entities that participate in historical, synchronization, or audit relationships.

---

# 28. Domain Distinctions

The following concepts MUST NOT be merged:

| Concept A      | Concept B            | Reason                                                   |
| -------------- | -------------------- | -------------------------------------------------------- |
| Task           | Event                | Work vs occurrence                                       |
| Task deadline  | Work block           | Due time vs planned work                                 |
| Reminder       | Notification         | Instruction vs delivery                                  |
| Board          | Project              | Workflow vs body of work                                 |
| Task status    | Priority             | State vs importance                                      |
| Subtask        | Dependency           | Hierarchy vs logical prerequisite                        |
| Note checklist | Task                 | Information vs actionable work                           |
| Booking        | Event                | Reservation transaction vs resulting calendar occurrence |
| Semester       | Academic calendar    | Academic period vs dates/rules                           |
| Day Order      | Calendar date        | Schedule value vs actual date                            |
| Class schedule | Generated event      | Reusable definition vs occurrence                        |
| User           | Workspace membership | Identity vs authorization relationship                   |
| Session        | Device               | Access instance vs client                                |
| Attachment     | External file        | Application relationship vs storage object               |
| Native object  | External object      | Workaholic state vs provider state                       |
| Reminder       | Shared recipient     | Trigger definition vs target                             |

These distinctions are fundamental to the domain model.

---

# 29. Future Domain Extensions

The model is intentionally extensible for:

* Chat
* AI actions
* smart scheduling
* advanced analytics
* additional integrations
* additional calendar providers
* additional storage providers
* billing/subscriptions
* enterprise administration

Future functionality MUST integrate with the existing domain model rather than bypassing established ownership, authorization, synchronization, and lifecycle rules.

# 30. Domain Model Authority

This document defines the conceptual meaning of Workaholic entities.

It does NOT define:

* exact database columns
* indexes
* foreign-key implementation
* API endpoints
* UI layouts
* synchronization algorithms
* notification transport details
* provider-specific implementation details

Those concerns belong to their respective technical specifications.

When implementation details conflict with the conceptual domain model, the implementation MUST be revised or the domain model explicitly changed through the project's documentation/change process.
