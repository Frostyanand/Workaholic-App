## 1. Purpose

This document defines the functional and non-functional requirements for Workaholic.

It establishes the required product behavior independently of implementation details.

The requirements in this document are authoritative for product development. Technical architecture, database design, API design, UI implementation, and testing must satisfy these requirements unless an explicit approved decision changes them.

---

# 2. Requirement Status

Requirements use the following status terminology:

- **MUST**: Required for the corresponding scope.
- **SHOULD**: Expected unless a documented technical or product reason prevents it.
- **MAY**: Optional or future-compatible behavior.
- **DEFERRED**: Intentionally excluded from the current implementation.
- **COMING SOON**: Part of the product direction but not part of the initial implementation.

Unless otherwise specified, a requirement marked **MUST** applies to the final product. Individual release plans may identify a subset of requirements for a particular release.

---

# 3. Product Principles

## REQ-CORE-001: Unified Productivity System

Workaholic MUST provide a unified ecosystem for:

- tasks
- projects
- boards
- calendar
- scheduling
- reminders
- notifications
- notes
- files
- people
- collaboration
- academic scheduling
- bookings
- external integrations

These systems MUST be interconnected where relationships are meaningful.

---

## REQ-CORE-002: Action-Oriented Experience

The primary productivity experience MUST answer:

> What do I need to do, when do I need to do it, and what requires my attention?

The primary interface SHOULD prioritize:

1. current work
2. today's work
3. overdue work
4. important work
5. upcoming work
6. scheduled calendar activity
7. unscheduled important work

The application SHOULD NOT primarily function as an undifferentiated data browser.

---

## REQ-CORE-003: Personal-First Product

The product MUST support individual productivity without requiring collaboration features.

Users MUST be able to use core task, calendar, reminder, note, and project functionality independently.

---

## REQ-CORE-004: Cross-Domain Relationships

Where appropriate, Workaholic MUST allow relationships between:

- tasks and projects
- tasks and boards
- tasks and calendar events
- tasks and notes
- tasks and files
- tasks and people
- projects and notes
- projects and files
- events and tasks
- events and notes
- events and people
- reminders and tasks
- reminders and events

---

# 4. Platform Requirements

## REQ-PLAT-001: Web

Workaholic MUST provide a functional web application.

The web application MUST support the core Workaholic experience and synchronize with the same user data as other supported platforms.

---

## REQ-PLAT-002: Windows 11

Workaholic MUST provide a native-capable Windows 11 desktop application.

The Windows application MUST support, subject to operating-system capabilities:

- desktop notifications
- local reminder scheduling
- background synchronization
- system tray operation
- startup launch
- close-to-tray behavior
- persistent local state

The Windows application MUST NOT be implemented merely as a browser page presented as the primary desktop experience.

---

## REQ-PLAT-003: Android

Workaholic MUST provide an Android application supporting:

- core productivity functionality
- persistent local data
- offline operation
- local reminders
- notifications
- synchronization

The implementation MUST account for Android background-execution and notification restrictions.

---

## REQ-PLAT-004: Future Apple Platforms

macOS and iOS SHOULD remain architecturally possible.

They are not required for the initial implementation.

---

## REQ-PLAT-005: Shared Application Model

The supported platforms MUST use a shared Workaholic product/domain model.

Platform-specific behavior MAY be implemented where operating-system capabilities require it.

---

# 5. Account and Identity Requirements

## REQ-AUTH-001: Account Creation

Users MUST be able to create and access a Workaholic account.

---

## REQ-AUTH-002: Google Authentication

Google authentication MUST be supported.

---

## REQ-AUTH-003: Authentication Identity

Workaholic MUST maintain its own application-level user identity even when Firebase Authentication is used.

External authentication identifiers MUST be stored as external identity mappings rather than becoming the entire domain identity model.

---

## REQ-AUTH-004: Authentication and Authorization Separation

Authentication MUST be separate from authorization.

Being authenticated MUST NOT automatically grant access to arbitrary Workaholic resources.

---

## REQ-AUTH-005: Session Management

Workaholic MUST support authenticated sessions across multiple devices.

The system MUST support:

- session creation
- session expiration
- session revocation
- individual session termination
- termination of all sessions

---

## REQ-AUTH-006: Device Management

Users MUST be able to view and manage recognized devices and sessions.

The system SHOULD distinguish trusted/persistent devices from temporary/public sessions.

---

## REQ-AUTH-007: Public Session Expiration

Temporary/public sessions MUST expire automatically.

The system SHOULD support configurable public-session lifetimes, including 12-hour and 24-hour options.

---

## REQ-AUTH-008: Secure Credentials

Authentication credentials, OAuth credentials, refresh credentials, API secrets, encryption keys, and other sensitive secrets MUST NOT be exposed to clients unnecessarily.

Server-side secrets MUST remain inaccessible to ordinary application clients.

---

# 8. Task Requirements

## REQ-TASK-001: Task Creation

Users MUST be able to create tasks.

A task MUST be capable of existing without a project or board.

---

## REQ-TASK-002: Inbox

Workaholic MUST provide an Inbox or equivalent uncategorized task location.

Tasks captured without an immediate project or board assignment MUST be able to remain in the Inbox.

---

## REQ-TASK-003: Task Editing

Users MUST be able to edit tasks after creation.

---

## REQ-TASK-004: Task Completion

Users MUST be able to complete and reopen tasks.

Completion state MUST be explicit.

---

## REQ-TASK-005: Task Title

Every task MUST have a title or equivalent primary identifier.

---

## REQ-TASK-006: Task Description

Tasks MUST support descriptions.

Rich-text capability SHOULD be supported.

---

## REQ-TASK-007: Subtasks

Tasks MUST support subtasks.

Subtasks SHOULD behave substantially like normal tasks.

---

## REQ-TASK-008: Parent Completion

Completing all subtasks MUST NOT silently complete the parent task.

The parent task MAY display an indication that all subtasks are complete.

The user MUST retain explicit control over parent completion.

---

## REQ-TASK-009: Task Status

Tasks MUST have a status.

Boards MAY define custom status workflows.

---

## REQ-TASK-010: Custom Statuses

Users MUST be able to define custom statuses for boards/workflows where applicable.

---

## REQ-TASK-011: Task Priority

Tasks MUST support priority.

The initial priority model is:

- P0 Critical
- P1 Urgent
- P2 High
- P3 Medium
- P4 Low

---

## REQ-TASK-012: Task Labels

Tasks MUST support labels/tags.

Users SHOULD be able to filter tasks using labels.

---

## REQ-TASK-013: Due Dates

Tasks MUST support due dates.

---

## REQ-TASK-014: Due Times

Tasks SHOULD support due times in addition to date-only deadlines.

---

## REQ-TASK-015: Start Dates

Tasks SHOULD support start dates where applicable.

---

## REQ-TASK-016: Estimated Duration

Tasks MUST be capable of storing an estimated duration.

---

## REQ-TASK-017: Actual Duration

The system SHOULD support actual time spent where time tracking is implemented.

---

## REQ-TASK-018: Scheduled Work Blocks

A task MUST be capable of having one or more scheduled work blocks.

A scheduled work block represents intended work during a specific time interval.

---

## REQ-TASK-019: Deadline vs Work Block

Task deadlines and scheduled work blocks MUST remain distinct concepts.

Moving a scheduled work block MUST NOT silently change the task's deadline.

---

## REQ-TASK-020: Task Attachments

Tasks MUST support attachments.

---

## REQ-TASK-021: Task Links

Tasks MUST support external or internal links.

---

## REQ-TASK-022: Task Comments

Tasks SHOULD support comments in collaborative contexts.

---

## REQ-TASK-023: Task Activity

Important task changes SHOULD be recorded in activity history.

---

## REQ-TASK-024: Task Dependencies

Tasks MUST support dependency relationships.

At minimum, the model MUST support:

- blocks
- blocked by
- depends on
- related to

More advanced dependency types MAY be introduced later.

---

## REQ-TASK-025: Task Relationships

Tasks SHOULD be able to relate to other Workaholic objects where meaningful.

---

## REQ-TASK-026: Task Assignment

Collaborative tasks MUST support assignment to authorized users where applicable.

---

---

## REQ-BACKLOG-003: Backlog Visibility

## REQ-BACKLOG-005: Rescheduling Suggestions

The system MAY suggest suitable future times for overdue tasks.

Suggestions MUST NOT automatically alter the task without user authorization.

# 16. Academic and Day Order Requirements

## REQ-DO-001: Academic Scheduling

Workaholic MUST support academic scheduling as a dedicated subsystem.

---

## REQ-DO-002: Semester

Academic schedules MUST be associated with a semester or equivalent academic period.

---

## REQ-DO-003: Academic Calendar

A semester MUST have an academic calendar capable of representing:

- working days
- holidays
- special working days
- relevant academic dates

---

## REQ-DO-004: Day Order

The system MUST support Day Order sequences.

---

## REQ-DO-005: Reusable Schedule

Day Order-based class schedules MUST be reusable definitions rather than being represented only as manually created individual calendar events.

---

## REQ-DO-006: Schedule Mapping

Users MUST be able to create and map class schedules to Day Orders.

---

## REQ-DO-007: Generated Events

Calendar occurrences generated from Day Order schedules MUST retain sufficient provenance to identify:

- semester
- Day Order
- schedule entry
- originating schedule

---

## REQ-DO-008: Holiday Shifting

When an academic holiday changes the sequence of working Day Orders, the system MUST be capable of shifting subsequent Day Orders and their associated generated class schedules appropriately.

---

## REQ-DO-009: Weekend Handling

Saturday and Sunday MUST normally be excluded from ordinary Day Order progression.

---

## REQ-DO-010: Special Working Days

Special working Saturdays or other exceptional working days MUST be explicitly representable.

---

## REQ-DO-011: Cancelled Classes

The system MUST distinguish cancelled classes from ordinary holidays.

---

## REQ-DO-012: Rescheduled Classes

The system MUST distinguish rescheduled classes from ordinary Day Order schedule changes.

---

## REQ-DO-013: Semester End

The system MUST provide an explicit semester-ending operation.

---

## REQ-DO-014: Semester End Behavior

Ending a semester MUST invalidate/remove future calendar occurrences generated by that semester's academic/Day Order schedules.

It MUST preserve:

- past academic history
- reusable Day Order mappings
- reusable class schedule definitions

---

## REQ-DO-015: Semester End Safety

Ending a semester MUST NOT delete unrelated personal, Google, booking, holiday, or other calendar data.

---

# 18. Offline Requirements

## REQ-OFF-001: Offline Operation

Workaholic MUST remain usable when network connectivity is unavailable for supported offline functionality.

---

## REQ-OFF-002: Local Persistent State

Clients MUST maintain persistent local application state.

---

## REQ-OFF-003: Offline Task Operations

Users MUST be able to perform supported task operations offline.

At minimum:

- view synchronized tasks
- create tasks
- edit tasks
- complete tasks

---

## REQ-OFF-004: Offline Notes

Users SHOULD be able to view and edit previously synchronized notes offline.

---

## REQ-OFF-005: Offline Calendar

Users SHOULD be able to view previously synchronized calendar information offline and perform supported local calendar operations offline.

---

## REQ-OFF-006: Offline Reminders

Reminders already synchronized to a device MUST remain capable of triggering locally without internet connectivity.

---

## REQ-OFF-007: Offline Mutation Queue

Offline changes requiring server synchronization MUST be persisted in a local synchronization queue or equivalent mechanism.

---

## REQ-OFF-008: Reconnection

When connectivity returns, locally persisted changes MUST be synchronized automatically or through an appropriate retry mechanism.

---

## REQ-OFF-009: No Silent Data Loss

Loss of connectivity MUST NOT silently discard valid locally accepted user changes.

---

# 19. Synchronization Requirements

## REQ-SYNC-001: Cross-Device Synchronization

Workaholic MUST synchronize supported application state between authenticated devices.

---

## REQ-SYNC-002: Synchronization State

The system SHOULD communicate synchronization state to the user where useful.

Examples:

- synchronized
- synchronizing
- pending changes
- synchronization failed

---

## REQ-SYNC-003: Idempotency

Synchronization operations MUST be designed to prevent duplicate application of the same logical mutation.

---

## REQ-SYNC-004: Retry

Transient synchronization failures MUST be retryable.

---

## REQ-SYNC-005: Conflict Detection

The synchronization system MUST detect relevant concurrent modifications.

---

## REQ-SYNC-006: Conflict Resolution

The synchronization system MUST apply deterministic conflict-resolution rules.

The exact resolution strategy MAY differ by data type.

---

## REQ-SYNC-007: Multi-Device Edits

The system MUST support concurrent edits from multiple devices.

---

## REQ-SYNC-008: Local Responsiveness

Ordinary local interactions SHOULD NOT require a successful network round trip before updating the user interface when the operation is safely applicable locally.

---

## REQ-SYNC-009: Cloud Role

Cloud services MUST provide synchronization, durability, cross-device continuity, collaboration, and remote capabilities.

The cloud MUST NOT be treated as the sole mechanism by which core client functionality can operate.

---

# 49. Critical Acceptance Scenarios

The following scenarios are considered high-priority acceptance scenarios.

## REQ-ACCEPT-001: Offline Task

A user creates a task without internet connectivity.

Expected:

1. Task appears immediately.
2. Task persists locally.
3. Task is queued for synchronization.
4. Connectivity is restored.
5. Task synchronizes successfully.
6. Other authenticated devices eventually receive the task.

---

## REQ-ACCEPT-002: Offline Reminder

A reminder is synchronized to a device.

The device subsequently loses internet connectivity.

Expected:

1. Reminder remains locally scheduled.
2. Reminder fires at the configured time.
3. Internet connectivity is not required for the local notification.

---

## REQ-ACCEPT-003: Google Calendar Synchronization

A synchronized Google Calendar event changes externally.

Expected:

1. Workaholic detects the external change.
2. The corresponding Workaholic representation is updated according to synchronization rules.
3. Native Workaholic-only relationships are not unnecessarily destroyed.

---

## REQ-ACCEPT-004: Google Drive Attachment

A Drive file is attached to a Workaholic task.

The attachment relationship is removed.

Expected:

1. Workaholic removes the relationship.
2. The Drive file remains intact.
3. Only an explicit Drive deletion operation can remove the external file.

---

## REQ-ACCEPT-005: Private Public Calendar Event

A private event exists during a publicly shared period.

Expected:

1. Public viewer can see the time as busy where applicable.
2. Public viewer cannot retrieve the private title.
3. Public viewer cannot retrieve private description or metadata.
4. Backend authorization enforces this behavior.

---

## REQ-ACCEPT-006: Trusted Access Revocation

A trusted user has access to another user's shared resources.

The owner revokes that access.

Expected:

1. Access is removed.
2. Associated sessions/devices are invalidated or otherwise prevented from continued unauthorized access according to the session model.
3. The trusted user cannot continue accessing protected resources.

---

## REQ-ACCEPT-007: Booking Conflict

Two guests attempt to book the same exclusive time slot concurrently.

Expected:

1. At most one booking succeeds.
2. The other booking fails safely.
3. The database remains consistent.
4. No duplicate calendar event is created.

---

## REQ-ACCEPT-008: Semester End

A semester contains future Day Order-generated events and unrelated personal events.

The user ends the semester.

Expected:

1. Future generated academic events are invalidated/removed.
2. Past academic history remains.
3. Reusable Day Order mappings remain.
4. Reusable class schedule definitions remain.
5. Personal events remain.
6. Google events remain.
7. Unrelated calendar data remains.

---

## REQ-ACCEPT-009: Overdue Task

A task passes its deadline without completion.

Expected:

1. Task remains incomplete.
2. Task becomes overdue.
3. Task appears in overdue views.
4. Deadline is not silently changed.
5. User may explicitly reschedule it.

---

## REQ-ACCEPT-010: Concurrent Device Edit

A task is edited differently on two devices before synchronization completes.

Expected:

1. The synchronization engine detects the relevant conflict.
2. The documented conflict policy is applied.
3. Data does not become silently corrupted.
4. The final state is deterministic.

---
